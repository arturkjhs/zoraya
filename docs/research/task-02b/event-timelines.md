# TASK-02b: event timelines (M6)

These are ordered event sequences across all processes, for three scenarios:

- W9a: Ctrl-C during a parallel recursive build;
- W9b: SIGTERM to the top-level make;
- W10: shell-level parallelism.

They are the input for designing a replacement event mechanism, so this document states who sends what to whom, who
waits on what, and what each process does on receipt.

**Sources.**

- The full per-event tables (every delivery, send, reap, deletion and exit, with pid and role) are generated by
  `analysis/parallel.py` into `tools/posix-surface/results/par/timelines.md`. The tables below condense them.
- The raw traces are `raw-par/strace/W9-*.txt` and `W10-*.txt` in the VM.

**Clock and order.**

- Times are milliseconds relative to the harness action (Ctrl-C written to the pty, or `kill(SIGTERM)`), on the
  `strace -ttt` clock. Harness actions are logged on the same clock.
- strace slows every process, so absolute gaps are longer than in an untraced run. The order of events *within* a
  process is exact. *Across* processes, it is the order in which strace observed them.
- A blocking call is placed at the time it returned.

**Roles.** `make@top` is the top-level make. `make@a` and `make@b` are level 1; `make@a/1` … `make@b/2` are the four
leaf makes. `mktab N @a/1` is the recipe running in leaf `a/1`. The shell is `dash -i`: session leader, controlling
process of the pty, job control on.

## State when the interrupt arrives (both W9 cases, delay 1.5 s)

- **Processes alive:** dash, make@top, make@a, make@b, the 4 leaf makes, and 4 `mktab 4` recipes, one per leaf, each
  writing `t4.h`.
- **Process groups:** make and everything below it form one process group, the foreground group of the terminal.
  The shell is in its own group.
- **What each process is blocked in:**
  - **Leaf makes:** `pselect6([jobserver fd], sigmask=[])`. They wait for a token or a child exit.
  - **make@top, make@a, make@b:** blocking `wait4(-1)`. Each has started all of its sub-makes and only waits for
    them.
  - **dash:** waiting for the foreground job.
- **Progress:** 12 of 32 tables complete.

## W9a: Ctrl-C (run `W9-int-d1.5-r1`)

| ms | What happens | Processes |
|---|---|---|
| 0.0 | The harness writes `^C` (VINTR) to the pty master | harness |
| +0.0 … +0.1 | **The tty driver sends SIGINT (`SI_KERNEL`) to every process in the foreground group at once** | all 4 `mktab`, all 7 makes |
| +0.1 | Each leaf make's `pselect6` returns `ERESTARTNOHAND`: the wait is interrupted by SIGINT and the handler `fatal_error_signal` runs | 4 leaf makes |
| +0.1 … +0.5 | The 4 `mktab` processes die of SIGINT (default action). Each leaf make receives SIGCHLD `CLD_KILLED` | mktab → leaf makes |
| +0.5 | make@top, in its handler, unlinks the jobserver FIFO `/tmp/GMfifo<pid>` | make@top |
| +0.5 | **Each leaf make deletes its partial target `t4.h`** (`unlinkat`, "Deleting file 't4.h'") | 4 leaf makes |
| +0.5 … +0.6 | Each leaf make, still inside the handler, reaps its `mktab`: `wait4` → `WIFSIGNALED, SIGINT` | 4 leaf makes |
| +0.8 … +1.0 | **Each leaf make re-raises SIGINT on itself** (`kill(getpid(), SIGINT)`, delivered as `SI_USER`) and dies of it | 4 leaf makes |
| +0.9 … +1.1 | make@a and make@b reap their leaves (`WIFSIGNALED, SIGINT`). They had been blocked in `wait4`, which returned `ERESTARTSYS` when SIGINT arrived. That call is never resumed: `fatal_error_signal` issues its own blocking `wait4` calls (`reap_children`) and never returns, because it ends by re-raising the signal | make@a, make@b |
| +1.4 … +1.5 | make@a and make@b re-raise SIGINT and die | level 1 |
| +1.5 … +1.7 | make@top reaps make@a and make@b | make@top |
| +2.0 … +2.1 | make@top re-raises SIGINT and dies | make@top |
| +2.1 … +2.2 | dash reaps make@top (`WIFSIGNALED, SIGINT`) and receives SIGCHLD `CLD_KILLED` | dash |
| +2.3 | **dash takes the terminal back** (`ioctl TIOCSPGRP` to its own group) | dash |
| +2.5 … +2.6 | **dash interrupts itself** (`tkill(self, SIGINT)`, `SI_TKILL`). Because the foreground job died of SIGINT, the rest of the command line is abandoned and the prompt returns | dash |
| +2.9 | The harness sees the prompt. The shell reports `$?` = 130 | harness |

Observations from this timeline:

- **Nobody forwards SIGINT.** The terminal driver delivers it to the whole foreground group, and every process
  handles it independently.
- **Each make's cleanup is ordered bottom-up by waiting.** A make cannot exit until it has reaped its children, so
  leaves finish first, then level 1, then the top.
- **All cleanup runs inside the signal handler,** including blocking `wait4` calls and `unlink`.
- **Exit status is the interface.** The shell's decision to abandon the line depends on make dying *by SIGINT*,
  which is why every make re-raises it rather than exiting with a code.

## W9b: SIGTERM to the top-level make (run `W9-term-d1.5-r1`)

| ms | What happens | Processes |
|---|---|---|
| 0.0 | The harness sends `kill(make@top, SIGTERM)` | harness |
| +0.2 | make@top receives SIGTERM (`SI_USER`); `fatal_error_signal` runs | make@top |
| +0.3 | make@top unlinks the jobserver FIFO | make@top |
| +0.3, +2.2 | **make@top sends SIGTERM to each child**: make@b, then make@a | make@top → level 1 |
| +2.2 … +2.3 | make@a and make@b each forward SIGTERM to their two leaf makes | level 1 → leaves |
| +2.3 … +2.6 | Each leaf make's `pselect6` is interrupted (`ERESTARTNOHAND`); its handler runs | leaves |
| +2.4 … +2.8 | **Each leaf make sends SIGTERM to its `mktab`**, which dies of it | leaves → mktab |
| +2.6 … +2.9 | Each leaf make deletes its partial `t4.h` and reaps its `mktab` | leaves |
| +2.9 … +3.4 | The leaf makes re-raise SIGTERM on themselves and die | leaves |
| +3.1 … +3.9 | make@a and make@b reap their leaves (+3.1 … +3.5), re-raise SIGTERM, die | level 1 |
| +3.8 … +4.4 | make@top reaps both (+3.8, +4.0), re-raises SIGTERM (+4.2), dies (+4.4) | make@top |
| +4.7 | dash takes the terminal back (`TIOCSPGRP`). **No self-interrupt**: the job died of SIGTERM, not SIGINT. The shell reports `$?` = 143 | dash |

Observations:

- **SIGTERM goes to one process, not a group.** Propagation is make's own code: each make sends it to its direct
  children (`commands.c:544`), so it travels down the tree one level at a time and the deaths come back up.
- **The cleanup is the same as for Ctrl-C:** delete the partial target, reap, re-raise.
- **SIGTERM needs milliseconds to travel down the tree, and lower makes keep starting jobs meanwhile.** In
  `W9-term-d3.0-r2`, a leaf make started a new recipe (`sh -c './mktab 8 > t8.h'`) 9.7 ms after the harness's SIGTERM,
  just before the forwarded SIGTERM reached it at 9.9 ms. It then killed that `sh` before `t8.h` existed, so that run
  deleted 3 partial targets instead of 4. Ctrl-C has no such window: the tty signals every process at once.
- **Nested signals inside the handler.** In 4 of 9 SIGTERM runs, including this one (`W9-term-d1.5-r1`), a leaf
  make's `writev` of the "Deleting file" message, inside `fatal_error_signal`, returned `ERESTARTSYS`. The cause is
  SIGCHLD `CLD_KILLED` from the `mktab` the same make had killed about 0.07 ms earlier. SIGCHLD can arrive there
  because the handler was entered from `pselect6` and runs with that call's empty mask. The `writev` is then
  restarted (`SA_RESTART`).
  - This never happens with Ctrl-C (0/9): there the tty kills the recipes first, so their SIGCHLD arrives before the
    handler writes anything.
  - The condensed table above omits it.

## W10: background jobs, `wait`, concurrent pipelines (run `W10-parallel-r1`)

Times are relative to the script's first syscall. The script is `workloads/w10/w10.sh parallel`, run by
non-interactive dash, so there is no job control.

| ms | What happens | Processes |
|---|---|---|
| +0.6 … +1.1 | dash installs handlers for SIGCHLD and SIGINT | dash |
| +1.6 … +16.1 | `tcc -o mktab` (vfork + exec); dash reaps it and receives SIGCHLD | dash, tcc |
| +16.5 … +17.2 | **Three background jobs**: `fork` ×3 (`./mktab 1 &`, `./mktab 2 &`, and the subshell `( ./mktab 3 …) &`) | dash → children |
| +16.9 … +17.5 | **Each background child sets SIGINT and SIGQUIT to `SIG_IGN` before exec** (non-job-control shell, POSIX) | the 3 children |
| +18.2 | The subshell vforks and execs `mktab 3` | subshell |
| — | `wait $p1`: dash sleeps in `rt_sigsuspend` | dash |
| +432.6 | `mktab 1` exits. **dash's `rt_sigsuspend` returns `ERESTARTNOHAND`**, the SIGCHLD handler runs and returns, and dash reaps `mktab 1` with `wait4` | dash |
| +432.7 … +433.1 | `mktab 2` and `mktab 3` exit within 0.3 ms. dash reaps `mktab 2`; the subshell reaps `mktab 3` and exits; non-blocking `wait4(WNOHANG)` calls drain the rest | dash, subshell |
| +433.4 … +433.5 | `rt_sigsuspend` returns again, on the subshell's exit. dash reaps it. The final `wait` returns | dash |
| +433.7 … +435.4 | **Pipeline `./mktab 4 \| sort \| wc -l`**: two `pipe2`, three `fork`s, three execs. The stages run concurrently | dash → 3 children |
| +838.5 … +841.4 | `mktab 4` exits; `sort` and then `wc` see EOF and exit. dash reaps each as its SIGCHLD arrives | |
| +841.6 … +842.8 | **Pipeline `yes w10 \| head -n 3`**: `pipe2`, two `fork`s | |
| +847.8 | `head` exits after 3 lines | head |
| +847.9 | **`yes` receives SIGPIPE** on its next write to the closed pipe. strace reports it as `SI_USER` with `yes`'s own pid, which is how Linux reports the kernel-generated SIGPIPE. `yes` is killed by SIGPIPE | yes |
| +848.0 | dash gets SIGCHLD `CLD_KILLED` and reaps `yes` (`WIFSIGNALED, SIGPIPE`). The pipeline status is `head`'s (0) | dash |
| +848.4 … +855.2 | `cat \| wc -l`, then dash exits 0 | |

Observations:

- **The shell's `wait` is `sigsuspend` + SIGCHLD + `wait4`.** Every child exit is a signal to the shell, followed
  by a reap. Pipelines and background jobs use the same mechanism.
- **Background jobs are protected from Ctrl-C by an inherited ignore**, set in the child before exec. They are not
  protected by being outside the terminal's process group, because this shell has no job control.
- **Early-closing pipelines terminate the writer by SIGPIPE.** The shell treats that death as normal; only the last
  stage's status counts.

## Stability across repetitions (W9, strace, 9 runs per case)

The generated stability tables (`results/par/timelines.md` → "W9 stability") list every event kind and the number
of runs in which it occurred. Event kinds are e.g. "a leaf make receives SIGINT from the tty" and "a leaf make
deletes a partial table".

| Behaviour | Ctrl-C | SIGTERM |
|---|---|---|
| tty SIGINT to all processes of the job | all 9 | — |
| SIGTERM forwarded parent → child at every level | — | all 9 |
| every make deletes the partial target of its running recipe | all 9 | all 9 |
| every make re-raises the signal and dies by it | all 9 | all 9 |
| `pselect6` interrupted in leaf makes; blocking `wait4` interrupted in top and level-1 makes (abandoned: the handler never returns) | all 9 | all 9 |
| shell retakes the terminal; self-`SIGINT` | all 9 | retake only, all 9 |
| some `mktab` had already exited normally before the interrupt | 6/9 (delays 1.5 and 3.0 s only) | 6/9 (same) |
| a leaf make's `writev` ("Deleting file" message, inside the handler) interrupted by SIGCHLD and restarted | 0/9 | 4/9 (all delays) |
| a leaf make starts a new recipe after the interrupt and kills it (`recipe-sh` killed by SIGTERM; 3 deletions instead of 4) | 0/9 | 1/9 (3.0 s) |

The untraced runs (interposer mode) gave the same outcome as the strace runs in every one of the 36 runs:

- exit status 130 or 143;
- 4 "Deleting file" messages (3 in the one strace run above; 4 in all untraced runs);
- no partial target left behind;
- no process left over.

They differed only in how far the build had got (`parallel-tables.md` → "W9 outcomes"). **Stable:** the order and
kinds of events, the cleanup, and the exit statuses. **Timing-dependent:** which recipes had already finished, and
whether a nested SIGCHLD interrupted the handler's own `writev`, and (SIGTERM only) whether a lower make started a
new recipe before the forwarded SIGTERM reached it.
