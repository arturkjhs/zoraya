# TASK-02b: impact of the parallel-build measurements on the TASK-01 conflicts

This document updates [`../task-02/conflict-impact.md`](../task-02/conflict-impact.md) for the question it left
open: parallel `make -j`, the jobserver, readiness calls and interrupting a running build. For each conflict the
new data touches, it records what the measurements show, which options they rule in or out, and what stays unknown.
**It makes no decisions.**

**Sources.** Figures come from:

- [`parallel-surface.md`](parallel-surface.md), [`event-timelines.md`](event-timelines.md),
  [`callsite-analysis.md`](callsite-analysis.md) and [`syscall-delta.csv`](syscall-delta.csv);
- `tools/posix-surface/results/par/*.md`, generated by the pipeline.

They were checked by the independent review (`research-log.md` → "Independent review"). M7 classes and the
event-model sentences are estimates.

**Scope of the evidence:**

- GNU make 4.4.1 at `-j2`/`-j4` with pipe and fifo jobservers, and pdpmake, which stays serial at any `-j`;
- Lua and SQLite builds, a synthetic two-level recursive build (W8);
- dash running background jobs and concurrent pipelines (W10);
- Ctrl-C and SIGTERM during a parallel build (W9), at three points of the build, 3 repetitions each, traced and
  untraced;
- one Alpine aarch64 VM with 4 vCPUs.

"Rules in" means the data does not contradict an option. "Rules out" means the data contradicts the premise an
option depends on, for these programs.

## X-3: no asynchronous interruption (CP-10) vs POSIX signal semantics

### What the data shows

- **Signals delivered during uninterrupted parallel builds.** SIGCHLD only, `CLD_EXITED`, to the make that started
  the child (W2-j, W3-j, W8, all styles). The same holds for pdpmake. No other signal was delivered in any
  non-W9 build run.
- **Under `-j`, SIGCHLD becomes make's main wake-up.**
  - Each waiting make sits in `pselect6(jobserver fd, sigmask=[])`. SIGCHLD is blocked everywhere else and
    unblocked only inside that call.
  - In W8 `-j4`, 55–60 of the 72–100 `pselect6` calls per build ended because SIGCHLD arrived (`ERESTARTNOHAND`,
    then `rt_sigreturn` `EINTR`). Only the rest ended because a token became readable.
  - The signal handler itself does almost nothing: it increments a counter (`child_handler`, `job.c:615`).
  - SIGCHLD is used as a *wake-up for a wait*, exactly as in TASK-02's serial runs, now hundreds of times per build.
- **Handler and mask set-up is identical at every `-j`.** Serial and parallel GNU make runs have the same
  `rt_sigaction` and `rt_sigprocmask` counts (W8: 1698 and 592). Parallelism changes delivery, not configuration.
- **Interrupting a build (W9)** produced two fixed cascades, each identical in all 9 runs (`event-timelines.md`):
  - **Ctrl-C.** The tty driver delivers SIGINT to every process of the foreground job at once. Nobody forwards it.
    Each make, inside its `fatal_error_signal` handler, then:
    1. deletes the partial target of its running recipe;
    2. reaps its children (a blocking `wait4` inside the handler);
    3. re-raises SIGINT on itself.

    Deaths propagate bottom-up. dash then retakes the terminal and interrupts itself (`tkill(SIGINT)`) to abandon
    the rest of the command line.
  - **SIGTERM to the top make.** make forwards SIGTERM to its direct children, level by level (`kill` from each
    make). The cleanup is the same, and the deaths again propagate bottom-up.
  - **Outcomes,** in 36/36 runs (traced and untraced): status 130 or 143, no partial target left behind, no stray
    processes. 35 runs deleted 4 partial targets; one SIGTERM run deleted 3 (next point).
  - **Timing-dependent:**
    - which recipes had already finished;
    - (SIGTERM only, 4/9) whether a nested SIGCHLD interrupted the handler's own message `writev`. The handler,
      entered from `pselect6`, runs with an empty mask;
    - (SIGTERM only, 1/9) whether a lower make started a new recipe in the milliseconds before the forwarded SIGTERM
      reached it. It then killed that recipe at once.

    Ctrl-C reaches all processes at once and showed neither effect.
- **Interrupted system calls.** They appear only where the program asked for interruption (`pselect6` with its
  atomic mask, the shell's `sigsuspend`). They also appear as one restart under `SA_RESTART` (the handler's
  `writev`), and as blocking `wait4` calls that the never-returning handler abandons. No program
  saw `EINTR` as an error it had to retry.
- **Shell-level parallelism (W10)** adds two mechanisms:
  - `wait` is `rt_sigsuspend` woken by SIGCHLD, then `wait4`.
  - Background jobs of a non-job-control shell set SIGINT and SIGQUIT to `SIG_IGN` before exec, so Ctrl-C does not
    reach them.

  An early-closing pipeline (`yes | head`) kills the writer with SIGPIPE, and the shell treats that as normal.
- **M7 (estimate).**
  - GNU make has 27 restructure sites (about 45 lines). Almost all exist to make asynchronous signals safe: blocked
    SIGCHLD, the empty mask for `pselect`, blocking the fatal signals around edits of the children list, and a
    handler that performs a whole shutdown, including blocking waits.
  - What stays `emulate` in make is one thing: dying *by* the signal (`commands.c:600`). The parent's behaviour
    depends on it: dash abandons the command line only after death by SIGINT.
  - dash's 37 emulate sites are the shell language: `trap`, `kill`, job control, `wait` returning on trapped
    signals, inherited ignores.

### Rules in / rules out

- **Out: "parallel builds need asynchronous signal delivery to user code during normal operation."** In
  uninterrupted `-j` builds the only signal is SIGCHLD, and its only use is to end a wait (`pselect6`) early. That
  is the role of an exit event on a process handle in a waitable-object model (CP-06, CP-08). The parallel data
  extends TASK-02's serial finding to `-j`, the normal case on a many-core host.
- **Out: "user interrupt needs signal forwarding by programs."** Ctrl-C reaches every process of the job directly
  from the terminal, and no process forwards it. Forwarding of a termination request to one process (make →
  children, one level at a time) leaves a window of milliseconds in which lower makes keep starting jobs (1/9 runs);
  group delivery has no such window.

  SIGTERM to one process does need forwarding, and make implements it. In both cases each process's reaction is the
  same three steps: delete partial output, wait for children, exit "by interrupt".
- **In: a native ABI without asynchronous interruption, plus a POSIX personality** that delivers:
  1. child exit as an event that also wakes a pending readiness wait;
  2. terminal interrupt to every process of the foreground job;
  3. termination requests to single processes;
  4. an exit reason "terminated by signal N" that parents can read.

  The data shows that make's handler body runs only cleanup code. That code could run from the main wait, but this
  is an estimate (M7 restructure).
- **In: emulating the POSIX semantics for unmodified make and dash.** This requires everything the timelines
  exercise:
  - handler execution interrupting `pselect6` and a blocking `wait4`. The `wait4` is never resumed: the handler does
    not return;
  - blocking `wait4` calls inside a handler, and a nested SIGCHLD interrupting the handler itself (empty mask
    inherited from `pselect6`), with `SA_RESTART` restarting the interrupted `writev`;
  - `kill(getpid(), sig)` with the disposition reset to default;
  - `tkill` self-interrupt in the shell;
  - inherited `SIG_IGN` for background jobs;
  - kernel-generated SIGPIPE.

  None of it is exotic, but all of it is asynchronous on the POSIX side.
- **Constrained: the exit status as an interface.** Exit-by-signal must be distinguishable from exit-with-code at
  every level (make → make → shell). It was used in every interrupted run.

### Unknown

- **Interrupts that arrive while a make is in other states.** For example, during `fork`/`exec`, during an
  `$(shell)`, or with `-l` load waits. Only three delays were tried, and in all of them the makes were in
  `pselect6` or `wait4`.
- **Higher concurrency.** `-j` above 4 (this VM's core count), and many more recursive makes, were not measured.
- **Other jobserver clients.** Tools that join the jobserver by reading `MAKEFLAGS` (other make versions, other build
  tools) were not part of the workloads.
- **Line editors and full-screen programs** receiving SIGWINCH/SIGTSTP during a build: not exercised.
- **Behaviour without strace.** Event *order* is only observable under strace. Untraced runs were checked for
  outcome only.

## X-4: completion-native async (CP-08) vs readiness for POSIX

### What the data shows

- **Parallel GNU make is the first readiness user in TASK-02/02b core workloads.** It makes exactly one kind of
  call: `pselect6` on a single fd (the jobserver read side), no timeout, empty signal mask. That is 1 to 100 calls per
  build, depending on its shape (W8 `-j4`: 72–100). No `poll`, `ppoll`, `select`, `epoll_*` or `waitid` appeared in any TASK-02b run.
- **What the readiness wait is for.**
  - It waits for "a job token is available" **or** "a child exited". The second arrives as a signal that interrupts
    the wait.
  - When the fd is ready, a non-blocking `read` follows. It can lose the race to another make (`EAGAIN`: 9 times in
    two W8 `-j4` fifo runs).
- **Token traffic** depends on the build's shape:
  - 34–38 token reads per Lua build;
  - 2 per W8 `-j2` build: every make runs its first job on the implicit slot it was started with, so only two leaf
    makes run at a time;
  - 17–26 per W8 `-j4` build.
- **The jobserver object** is a FIFO in `/tmp` (default) or an anonymous pipe. It is published as a path or as fd
  numbers in `MAKEFLAGS`, which every recipe inherits. In pipe style, `-2,-2` marks non-recursive recipes.
- **pdpmake** makes no readiness calls at any `-j`, because it is serial.
- **dash** waits for children with `sigsuspend` + `wait4`, not with a readiness call.
- **M7 (estimate).**
  - The `pselect` + blocked-SIGCHLD construction is `restructure`, about 10 lines. In a model with one waitable
    object per process and one per token pool, it is a single wait on two objects.
  - The jobserver's token handling is `direct`: a counting semaphore or token pipe passed explicitly.
  - The auth string (fd numbers or a FIFO path in `MAKEFLAGS`) is `emulate`, because other programs read it.

### Rules in / rules out

- **Rules in either native model for the toolchain.** The only readiness use is one fd plus "child exited",
  multiplexed in one wait. A readiness-native model provides it directly. So does a completion-native model, with a
  pending read on the token object plus an exit notification on the child objects. The data does not favour either.
- **Out: "the POSIX layer needs a general readiness multiplexer for the toolchain."** One fd per wait, never more
  than one fd, and no `poll`/`epoll` were observed. The layer must provide `pselect` with atomic signal-mask
  semantics on pipe and FIFO fds, and non-blocking `read` with `EAGAIN`.
- **In: a pipe or FIFO in the POSIX layer** whose readiness can be waited on together with child exit. That is the
  minimum the parallel toolchain needs from X-4.

### Unknown

- **Readiness needs beyond the toolchain.** Interactive programs (line editors, `less`, terminal multiplexers) and
  network software were out of scope. TASK-02's only other readiness call was busybox sh's `ppoll` in its line
  editor.
- **Whether other jobserver clients use other calls.** For example `poll` in ninja or cargo. They were not measured.
- **Throughput.** Whether one wake-up per child exit, plus one per token, matters at high `-j` was not measured.

## Other conflicts the data touches

### X-1: capability-only access vs POSIX porting

- **FIFO-style jobserver.** The default jobserver adds a **global name in `/tmp`** (`/tmp/GMfifo<pid>`, created with
  `mknodat`, unlinked by the top make, also from its signal handler). Every sub-make opens it *by path*, read from
  `MAKEFLAGS`.
- **Pipe style** avoids the global name but passes fd numbers through the environment. It has to invalidate them
  (`-2,-2`) for recipes that are not recursive makes.
- **Shown:** parallel make works with either an inherited object (pipe) or a global name (FIFO). The default uses
  the name. Both styles gave the same behaviour.
- **Not shown:** whether third-party jobserver clients accept only one of the two.

### CP-25 / CP-07: terminal rights and job containment

- **Ctrl-C reaches the whole build through the terminal's foreground process group,** set up by dash with
  `setpgid` and `TIOCSPGRP` in both the parent and the child before exec. That is POSIX's race avoidance, visible in
  the traces.
- **After the job died, dash took the terminal back** (`TIOCSPGRP`) in every run.
- **The build's processes formed one group,** which the terminal interrupted as a unit. That group served as the
  "whole tree" unit for Ctrl-C.
- **SIGTERM to one process did not reach the tree** until make forwarded it.
- **Shown:** the "kill the whole tree" operation that CP-07 asks for is used by the toolchain only through the
  terminal's process group. A termination request to one process relies on make's own forwarding.

### X-15: environment as configuration

- The jobserver's existence and address are passed through `MAKEFLAGS` in the environment. That is the
  environment carrying a capability-like reference: fd numbers, or a path that grants access.
- It is the clearest case so far where a POSIX environment variable is part of an inter-program protocol, not just
  configuration (`emulate` in M7).

### X-2: no fork

- Parallel GNU make created every child vfork-style through `posix_spawn`: clone counts were identical serial vs
  parallel (W8: 78 and 78).
- The forks in W10 are dash's background jobs, subshell and pipeline elements, as in TASK-02.
- **No new fork users appeared with parallelism.**

## Open questions the data frames but cannot answer

1. An interrupt arriving while a make is in `fork`/`exec` or `$(shell)` (X-3). Only waits were hit.
2. `-j` above 4, and jobserver clients other than GNU make (X-3, X-4, X-1).
3. Whether make's cleanup can run outside signal context unchanged. M7 estimates it can, at about 30 lines; the
   only way to check is a patch, as TASK-02 M4 did for spawn.
4. Event order without strace: only outcomes were checked untraced.
