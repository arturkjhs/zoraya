# Network implementation outline

Non-binding, part of TASK-23. It orders the work; the ADRs decide. Numbers refer to proposed ADR-0220 to ADR-0230 in
`docs/adr/`. Nothing here starts before the architect accepts the ADRs a task depends on, and every task ends with
`make test` passing from a clean checkout. The tasks are cut to comparable size (each a few thousand lines of code
and tests, by estimate) and so that each has a visible result on its own: something the architect can watch happen.

**Dependencies outside this plan.** On stage 6: `libposix`'s fd table, `pselect` and the bootstrap record (6c, 6d,
built), the ports' build (6b, built) for curl and BearSSL, and `zosh` running POSIX programs with grants (6e, TASK-22,
running now) for every `+net` example; on stage 7: the panel, rooms and the compositor's pills (7d to 7f and the rooms
task) for the desktop half of ADR-0224, which can land after the shell half; on ADR-0056 (proposed): nothing below
needs it, and N6 states what it would add. The first task (N1) also settles two facts the ADRs leave open: whether
`ID_AA64ISAR0_EL1` reports `RNDR` under HVF on the architect's Mac, and the crypto provider (ADR-0228's Decision):
ring built with the toolchain's clang against the sysroot for `aarch64-unknown-none`, else BearSSL for native
programs too. One decision gates N6's desktop half: with the GUI on, the four virtio-mmio pages are taken (ADR-0091),
and the architect deferred ADR-0221 item 8, so `--net` and `--gui` stay refused together and N6's desktop half waits
for the revisit "before the network on the desktop"; N1 to N5 run without the GUI, where pages 1 and 2 are free.

Order of risk: N1 carries the device and the ID-register fact, so it goes first and is small; N2 is where smoltcp
meets Zoraya's loop and is the largest unknown in code; N3 is the design's centre (the capability, the protocol and
the resolver together) and its visible result is the one the task names; N4 is library work on known ground; N5 builds
on N1's provider answer (ring, else BearSSL), which is why that check is in N1; N6 depends on stage 7's rooms and, for its desktop half with the network, on the deferred ADR-0221 item 8; its
shell and restart halves can run in parallel with N4 and N5.

What each task measures on the way, for `docs/design.md` and the task report: N1 the receive path's latency from the
interrupt to the frame in `netd`'s slot; N2 a ping's round trip through two processes under HVF and TCG; N3 the time
to fetch a 16 MiB file over HTTP and the copies' share of it; N4 the same through `libposix`; N5 a TLS handshake's
time and the random service's round trip; N6 the restart's duration and what the window shows.

What is deliberately not in this plan: IPv6 beyond smoltcp's support being compiled in (`proto-ipv6` on, no
configuration, no test), a server program (a Zoraya HTTP server, `hostfwd` into a listener), SNTP and setting the
clock (ADR-0226 Option C), client certificates (ADR-0228 Option D), DNS over TLS, wireless, a second interface,
raw sockets and `ping` as a command, `ssh`, and the quotas themselves (ADR-0056). Each has a revisit trigger in its
ADR.
