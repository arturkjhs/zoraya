# ADR-0339: git: the repository of the current directory, its own directory and the host of a typed URL; remotes are data and need `+net`

- **Status:** accepted
- **Date:** 2026-11-13
- **Depends on:** ADR-0107, ADR-0109, ADR-0153, ADR-0156, ADR-0172, ADR-0224, ADR-0225, ADR-0228, ADR-0287, ADR-0310, ADR-0311, ADR-0312, ADR-0331, ADR-0335, ADR-0337, ADR-0341, ADR-0342
- **Evidence:** CP-01, CP-05, CP-27, CP-28, DM-009, GR-008, alternatives-postmortem.md#plan-9--inferno, stage-10/survey.md#files-git-touches-unasked, stage-10/survey.md#git-licence-and-alternatives, stage-10/survey.md#how-git-starts-other-programs, stage-10/survey.md#pattern-c-a-trusted-helper-with-a-fixed-policy, stage-10/survey.md#the-name-devtty, stage-10/survey.md#the-network-as-built, stage-10/survey.md#what-git-needs

## Context

A working day ends in `git commit` and `git push`. git names almost nothing it touches on its command line: it
finds its repository by walking up from the current directory, reads configuration from three places, takes the
address of a remote from the repository's own configuration, and starts an editor, a pager, hooks and a transport
helper (`stage-10/survey.md#files-git-touches-unasked`, `stage-10/survey.md#how-git-starts-other-programs`). A
Zoraya program gets what its line says (ADR-0153). This ADR decides which git is ported and what the line
`git ...` gives it: files, network and credentials, and what `grants` shows.

**What is known.**

- git is GPL-2.0-only. Permissive alternatives: Game of Trees (ISC; its own commands on git's repository format;
  pushes over ssh only; built around `pledge`, `unveil` and helper processes that parse with no authority);
  gitoxide (MIT or Apache-2.0; no push; runs the external `ssh`); libgit2 (a library)
  (`stage-10/survey.md#git-licence-and-alternatives`).
- git builds without Perl, Python, Tcl, gettext, iconv, expat, `mmap`, Unix sockets and `setitimer`; it needs zlib,
  and libcurl for https. 149 commands are built into the one binary; `git-remote-https` is a separate program it
  starts. It locks by creating `FILE.lock` exclusively and renaming, and needs no record locks
  (`stage-10/survey.md#what-git-needs`, `stage-10/survey.md#files-git-touches-unasked`).
- A repository's own configuration names programs that git runs: hooks, the editor, the pager, the ssh command, a
  file-system monitor that runs on `git status`, credential helpers, filters. git's documentation treats the
  global configuration as protected from attackers and the repository's as not. Walking up for `.git` and then
  running what the found repository names was a vulnerability on machines with several users (CVE-2022-24765);
  git's fix compares owners, which says nothing where there is one identity
  (`stage-10/survey.md#files-git-touches-unasked`; the monitor and the protected scopes were read in git's
  documentation by the review).
- An https clone may be redirected to another host on its first request; by default git writes its global
  configuration to `~/.gitconfig` and stored credentials to `~/.git-credentials`
  (`stage-10/survey.md#files-git-touches-unasked`).
- git asks for a password on `/dev/tty` when no helper is set; the `store` helper keeps credentials in a plaintext
  file; the `cache` helper needs a Unix socket (`stage-10/survey.md#the-name-devtty`,
  `stage-10/survey.md#files-git-touches-unasked`).
- In Zoraya a child of a POSIX program has no network connection (ADR-0287 item 3, accepted) and no random
  service; ADR-0225 item 9 decides how a socket is inherited, not how a child gets a connection of its own. A
  POSIX program holds at most two connections. The report and hint for a refused host are decided and not built
  (`stage-10/survey.md#the-network-as-built`). A `url` operand of an image description designates its host
  (ADR-0224 item 2); the shell derives a file name from a URL under a strict rule (ADR-0311).
- `got` confines itself to the repository and the work tree, read-write, and starts the editor unconfined
  (`stage-10/survey.md#pattern-c-a-trusted-helper-with-a-fixed-policy`).

**What is assumed.** That https is the transport people need first, and that typing a token at a prompt is
acceptable until a key agent exists (ADR-0228 item 5).

## Decision drivers

1. **It is git**: the commands, the options and the scripts people know (CP-27: port, do not rewrite;
   `stage-10/survey.md#git-licence-and-alternatives`).
2. **The common lines need no grant words**, or people will work in `+w ~` (ADR-0153 driver 2).
3. **git reaches the repository and nothing beside it** (CP-01, CP-05, DM-009; GR-008's warning about programs
   that open paths late).
4. **No data makes a grant**: what a repository's files say cannot give git a host or a path (INV-0153-3,
   INV-0224-1, CP-28).
5. **What a repository can make git run gets no more than the repository**: not git's credentials, and no way to
   change git's configuration for other repositories (`stage-10/survey.md#files-git-touches-unasked`).
6. **What is given is shown** by `grants`, in the same words as everything else (ADR-0153 driver 5).

## Considered options

### Option A: git with the person's files (Unix)

- **Description:** git gets the home directory and the network.
- **Evidence for:** Everything in git's documentation works, including ssh transport, submodules anywhere and any
  helper.
- **Evidence against:** DM-009: a hook or a configured command in any cloned repository runs with all of it
  (`stage-10/survey.md#files-git-touches-unasked`). Target 2 is precluded.
- **Cost:** *(estimate)* The port alone.
- **Precedent:** Every Unix.

### Option B: git, given only what the line or the room says

- **Description:** No rule for git. The person writes `+w ~/proj git commit`, or works in a room that holds the
  project and its hosts.
- **Evidence for:** ADR-0153 unchanged: rule 2 says a description cannot widen the current directory, and `make`
  is run exactly so (`+w . make`). The hint of rule 11 names the directory to grant, so the person need not work
  out the repository's root. A project room is ADR-0172's answer to a grant on every line, and it is where daily
  git work belongs anyway.
- **Evidence against:** Driver 2 outside a room: the first experience of git is a refusal and a hint, and every
  line carries a grant until the person makes a room.
- **Cost:** *(estimate)* The port alone.
- **Precedent:** `make` in Zoraya today; WASI's `--dir`.

### Option C: git, with the repository found and given by the shell

- **Description:** git's description says that its implicit operand is the repository containing the current
  directory. The shell looks for it within what it holds and gives it; a typed URL gives its host; git's own files
  are ADR-0341's directory. Remotes read from the repository give nothing.
- **Evidence for:** Drivers 1 to 4 and 6. The shell, not git, does the upward search, inside its own table. It is
  the shape of `got`'s self-confinement, decided by the launcher instead of trusted to the program
  (`stage-10/survey.md#pattern-c-a-trusted-helper-with-a-fixed-policy`). ADR-0311 already lets the shell derive
  what a line means from a description key.
- **Evidence against:** It gives write access the line does not spell out, against ADR-0153 rule 2's words. Any
  program that could ever write the repository can plant configuration that git later runs (driver 5 then rests
  on what those programs are given). `fetch` and `push` still need a `+net`, which surprises people who cloned
  without one.
- **Cost:** *(estimate)* A description key and 200 lines in the shell's planner, beside the port.
- **Precedent:** `got`'s `unveil` of repository and work tree; nothing in a shell.

### Option D: As Option C, but only the `.git` directory to write

- **Description:** The shell gives the repository's `.git` as a tree and the work tree to read. Commands that
  change work files (`checkout`, `merge`, `pull`, `reset`, `stash`, `rebase`) need `+w` or a room.
- **Evidence for:** `status`, `log`, `diff`, `add`, `commit`, `fetch` and `push` write only inside `.git`, so the
  common lines still need no words, with much less authority than Option C: git cannot change a work file the
  line did not give.
- **Evidence against:** `git checkout` and `git pull` are also everyday lines and would be refused with a hint.
  What a planted configuration can run is the same as under Option C. Two entries and two rules to explain.
- **Cost:** *(estimate)* As Option C.
- **Precedent:** None surveyed.

### Option E: Game of Trees instead of git

- **Description:** Port `got`, whose design already separates parsing from authority.
- **Evidence for:** ISC licence; helpers with no file-system access; the parent holds the network descriptor
  (`stage-10/survey.md#git-licence-and-alternatives`). Its structure fits handles well.
- **Evidence against:** Driver 1: it is not git; scripts and habits that call `git` do not work, and it pushes
  over ssh only. Its confinement calls (`pledge`, `unveil`) do not exist here and its helpers assume descriptor
  passing over Unix sockets.
- **Cost:** *(estimate)* A port of a different design, and a second tool for people to learn.
- **Precedent:** OpenBSD.

### Option F: A native client (Plan 9's way), or gitoxide

- **Description:** Write, or adapt from gitoxide's crates, a native program that takes the repository as a
  directory handle and the remote as a scoped connection.
- **Evidence for:** Drivers 3 to 6 by construction; permissive; no child processes. Plan 9 wrote its tools new
  (`alternatives-postmortem.md#plan-9--inferno`).
- **Evidence against:** Driver 1 and CP-27: gitoxide has no push and still runs an external `ssh`
  (`stage-10/survey.md#git-licence-and-alternatives`); a new client is years behind git's behaviour.
- **Cost:** *(estimate)* A project of its own.
- **Precedent:** None at git's completeness.

## Recommendation

**Recommendation (not a decision): Option C.** Options B and D are both defensible and narrower; the architect is
asked to choose among the three. Everything from item 4 on holds under each.

1. **The port.** git, the release current when its implementation part starts, pinned in `ports/sources.lock`;
   GPL-2.0-only, a
   separate program in the image as `wget` (GPL-3.0-or-later) is. Built with `NO_PERL`, `NO_PYTHON`, `NO_TCLTK`,
   `NO_GETTEXT`, `NO_ICONV`, `NO_EXPAT`, `NO_MMAP`, `NO_UNIX_SOCKETS` and `NO_SETITIMER`, with zlib, the library of
   the pinned curl and the one OpenSSL of ADR-0312. Installed: `/bin/git` and `/bin/git-remote-https`. Not
   installed: the Perl and shell-script commands, `gitk`, the ssh transport, the credential helpers.
2. **The repository.** The description carries a new key, `repository`. Before git starts, the shell looks for a
   *directory* named `.git` in the current directory, then in each parent, **inside its own table**, and stops at
   the first it finds or at the edge of what it holds. If it finds one, git receives that directory with the
   rights the shell holds there, as a `tree` entry with the reason `the repository of the current directory`
   (`grants` says `read` when that is all the shell holds). Two cases refuse the line before git starts, with a hint:
   a `.git`
   that is a file (a work tree or submodule whose repository is elsewhere), and a repository whose root is the
   shell's home directory or the volume's root, which would hand git everything; for those the person writes the
   grant. (Starting git there without the entry would still let it find the repository through the current
   directory and run what its configuration names.) `-C DIR` moves the starting point to `DIR`. If nothing is found,
   nothing is added. The entry is
   automatic because git is a base-system command (ADR-0153's Decision). The shell also sets
   `GIT_CEILING_DIRECTORIES` for git to the parent of what it found, or of the current directory, so that git's
   own search ends there and names no path outside the table.
3. **Operands.** `git init DIR` and the `DIR` of `git clone URL DIR` are a new operand kind, `create-tree`: the
   parent narrowed to the name, where a directory of that name may be created, and everything inside it; `grants`
   words it `create NAME, and change anything in it`. `git clone URL` without `DIR` gets the directory named by
   ADR-0311's rule from the URL's last segment, with a final `.git` cut; a URL that gives no plain name is refused
   with the hint to write `DIR`. `git init` with no operand needs `+w .`.
4. **git's own files** are ADR-0341's: `data git as ~/.config/git`, holding its global configuration and nothing
   secret. The port is built so that the global configuration is `~/.config/git/config` always (never
   `~/.gitconfig`). The image's `/etc/gitconfig` (read-only, in the toolchain set) sets what the system needs: no
   detached garbage collection (there is no `setsid`), no identity guessed from the user database
   (`user.useConfigOnly`).
5. **What a repository can make git run gets the repository, and git's configuration to read.** Hooks, the
   editor (`vi`), the pager (`less`) and any program a repository's configuration names are children: they get
   git's table, with git's own directory lowered to read (ADR-0341 item 7) and the network the line gave. So a
   planted hook or monitor can do to that repository what git can, can read git's configuration, and can reach
   the hosts of the line; it cannot change git's configuration, and there are no stored credentials for it to
   read (item 9). Who can plant one is whoever was given the repository to write.
6. **The network: a typed URL gives its host; a remote does not.** The `URL` of `git clone` and `git ls-remote`
   is a `url` operand (ADR-0224 item 2): written on the line, it designates that host and port, with
   `/system/tls` to read (ADR-0311 item 4). `git fetch`, `pull` and `push` take their address from the
   repository's configuration, which is data: they get **no** network from it. The person gives it on the line
   (`+net example.org:443 git push`) or holds it in the project's room. A redirect to another host is refused
   by `netd` like any host the line does not give. In both cases the refusal is shown and the grant named as
   ADR-0224 item 5 and ADR-0337 say. `ssh://` and `HOST:PATH` addresses are refused by the description (a `url`
   operand is `http` or `https`), with a hint that says so: git over ssh waits for a way to give a started `ssh`
   its own directory.
7. **A child's network: decided here.** `git-remote-https` is a child that must connect. Accepted ADR-0287 item 3
   gives a child no network, and nothing accepted gives it the random service. This ADR changes that for the
   children of a line's program: at `fork` and at `spawn`, `libposix` asks `netd` for a second connection with the
   parent's own scope (ADR-0220's `narrow` to the same scope) and the random service for a share, and passes both
   to the child. The scope cannot grow on the way; the shell's budget of two connections for a POSIX program
   (`POSIX_NET_BUDGET` in `zosh`) counts the parent's
   and its children's together `[assumption: enough for git; the implementation part measures]`.
8. **Certificates and the environment.** The git port takes ADR-0310 item 6 whole, with the same libcurl and
   OpenSSL: no file and no variable decides what is trusted or which program runs. `http.sslVerify`, the
   `http.ssl*` keys, `http.proxy`, and the variables `GIT_SSL_*`, `GIT_CONFIG_COUNT` and its companions,
   `GIT_SSH`, `GIT_SSH_COMMAND` and `GIT_ASKPASS` are compiled out or ignored. So are the ways a repository could
   take the secret the person types: `credential.helper` in any scope (git would run it through the shell and hand
   it the user name and the token), `core.askPass` and `SSH_ASKPASS` (which would replace the prompt on
   `/dev/tty`). The prompt is always git's own, on the terminal.
9. **Credentials are typed to git itself, and not stored.** git asks for the user name and the password or token on
   the terminal
   (`/dev/tty`, ADR-0331), every time. No credential helper is built: a stored secret in git's directory would be
   readable by every program a repository makes git run (item 5). A key agent is the later answer (ADR-0228
   Option D).
10. **What must exist first.** `poll` (ADR-0342); the refusal report for hosts (ADR-0224 item 5); item 7.

**Examples.**

```
~/proj/src> git status
On branch main
nothing to commit, working tree clean
~/proj/src> grants git commit -m 'fix the length check'
git gets (a POSIX program):
  in, out, err         the terminal
  keys                 the terminal, while this line is in front
  ~/proj/src           read (current directory)
  ~/proj               change anything in (the repository of the current directory)
  /data/home/git       its own files (it sees them as ~/.config/git)
  /bin /usr /etc       read (system)
  /proc/self/exe       read (system)
  /tmp                 change anything in (this line's own)
  /dev/null
~/proj/src> git commit -m 'fix the length check'
~/proj/src> git push
fatal: unable to access 'https://example.org/ada/proj.git/': Could not resolve host: example.org
  hint: git tried to reach example.org:443, which it was not given
  to allow it: +net example.org:443 git push
~/proj/src> +net example.org:443 git push
Username for 'https://example.org': ada
(git then asks for the password and does not show it)
~> grants git clone https://example.org/ada/proj.git work
git gets (a POSIX program):
  in, out, err             the terminal
  keys                     the terminal, while this line is in front
  random                   the random service
  ~                        read (current directory)
  ~                        create work, and change anything in it (operand DIR)
  net: example.org:443     reach (operand URL)
  /system/tls              read (with the network)
  /data/home/git           its own files (it sees them as ~/.config/git)
  ...
```

(`...` stands for the four system lines; git's messages are its own and shortened here.) In a room made with
`room new proj +w ~/proj +net example.org:443`, `git push` needs no word. On the desktop the terminal's window
carries the room's pills, `+w ~/proj` and `+net example.org:443`, and the refusal of a `push` outside a room shows
on the terminal's status line while git runs. In `~` itself, if the home directory is a repository, `git status`
is refused before git starts, with `hint: this repository is your whole home directory; to allow it: +w ~ git
status`.

**Tensions with accepted ADRs.**

- *ADR-0153 rule 2* ("a description ... cannot widen the current directory: authority comes only from what the
  person typed"). The `repository` key widens it, upward, to the repository's root, with the rights of a `tree`.
  This is a real exception, and the architect refused a narrower-sounding one for curl (ADR-0311's `cwd read`).
  Its bounds: image descriptions only; only the nearest directory with a `.git` directory inside what the shell
  already holds, so a room bounds it; never the home directory or the root; shown by `grants` with its reason. If
  the architect declines it, Option B is the design and item 2 becomes a hint: `to allow it: +w ~/proj git commit
  ...`.
- *ADR-0153 rule 2's table of kinds and ADR-0156*: a new kind, `create-tree` (item 3), and two new keys in all
  (`repository` here, `data` in ADR-0341). The shell also sets an environment variable for a program
  (`GIT_CEILING_DIRECTORIES`), which ADR-0153 rule 10's note limits to `PATH` and `HOME`.
- *ADR-0224 item 2* is used as written; *INV-0224-1* is kept by item 6: a remote's address never designates.
- *ADR-0311*'s name rule gains a second user and the `.git` suffix cut.
- *ADR-0287 item 3* ("a child, spawned or forked, gets no network") and *ADR-0310 item 3* (only the shell shares
  the random service): item 7 replaces both for the children of a line's programs. ADR-0225 item 9 covers only an
  open socket and is not what this needs.
- *ADR-0310 item 6* is extended to git's own names (item 8).
- *ADR-0109*: a second GPL program in the image, separate, with its source pinned.

### Effect of the vision

For target 2 (once ADR-0268's gate lets untrusted rooms run): an agent's git in an untrusted room has the room's
project and the room's hosts, an empty
configuration and no credentials at all. A hostile repository can make git run its programs, and they get that
repository, the line's hosts and git's configuration to read: nothing to steal that outlives the line, and no way
to alter git for the next repository. The typed-URL rule and the refusal of remotes as grants are what keep a
cloned repository from choosing where data goes. Target 3: git works from the first line in a repository.
Networking: the first program whose helper process uses the network. Threads: git may use them; nothing here
depends on it.

## Consequences

- **Positive.** Real git; local work with no grant words; clone from a typed URL with none; the repository is
  the boundary for git, its hooks and its children; git's configuration cannot be changed by what a repository
  runs; no secret is stored; remotes cannot widen anything.
- **Negative.** A write grant that the line does not spell out. `fetch` and `push` outside a room need `+net`
  each time, and a password each time. No ssh transport, no Perl or shell-script commands, no credential helper.
  A planted hook still owns its repository. A second GPL program. A child now has the network of its parent.
- **Follow-up.** The port and its patches; the `repository` key and the `create-tree` kind; `git.cmd` and
  `help git`; the system `gitconfig`; items 7 and 10; a room example in `docs/tour.md`.

## Invariants

- **INV-0339-1.** git started where the shell's table holds an enclosing directory that has a `.git` directory
  receives a `tree` entry on the nearest such directory, with no more rights than the shell holds there, and on
  no directory above it; for a `.git` file, the home directory and the root the line is refused
  and git is not started; started elsewhere it
  receives none; the search never looks outside the shell's table. *Check:* a host test of the planner with nested
  repositories, a repository above a room's edge, one under a read-only part of the table, a `.git` that is a
  file, the home directory as a repository (the line refused, git not started), and `-C`.
- **INV-0339-2.** No network rule comes from a repository's content: `git fetch` on a line with no `+net`, in a
  room with none, has no network connection whatever the repository's configuration says. *Check:* a host test
  of the planner, and an in-QEMU script against the runner's server with a remote configured and no grant.
- **INV-0339-3.** In a clone, commit, log and diff of the test repository, and in `git config` outside any
  repository, git and its children name no path outside their entries. *Check:* the in-QEMU script reads the
  report count (ADR-0153 rule 11) and expects zero.
- **INV-0339-4.** A child of git holds a network scope equal to its parent's, holds git's own directory to read
  only, and holds no entry the parent lacks. *Check:* an in-QEMU script with a hook that tries a second host, a
  write to git's configuration, a path outside the repository, and a `.git/config` replaced by a link object that
  points at git's global configuration followed by `git config` in the repository; each is refused.
- **INV-0339-5.** git accepts a server only with a certificate that the system's roots, the clock and the name
  validate, and runs no program and reads no certificate that its configuration or environment names for the
  transport. *Check:* the script of INV-0310-4's kind against the runner's expired and wrong-name servers with
  `http.sslVerify=false`, `GIT_SSL_NO_VERIFY`, `GIT_SSL_CAINFO` and `GIT_SSH_COMMAND` set; and a test repository whose
  configuration sets `credential.helper` and `core.askPass`, with `SSH_ASKPASS` set on the line, asserting that
  the prompt comes from git on `/dev/tty` and no child is started for it.

## Open questions

- Option B, C or D: how much of the repository the line gives without a word.
- git over ssh: a way for a started `ssh` to have its own directory (ADR-0341's open question), or an ssh
  transport inside git's process.
- Whether repository-scope keys that name programs (the monitor, the hooks path, the pager, the editor) should
  be ignored unless the person turns them on in the global configuration, so that a planted configuration runs
  nothing.
- Whether a remote's host should be offered more smoothly: for example the shell reading the remote's URL only
  to word the hint before git starts, which makes no grant.
- A key agent for tokens (ADR-0228 Option D).

## Revisit triggers

- The architect declines the `repository` key: Option B.
- People type `+net any` for git: the remote question needs a better answer than a word per line.
- git's Rust requirement (announced for git 3.0) arrives before a Rust `std` build of ports exists.
- An agent or ssh transport exists: credentials stop being typed.
