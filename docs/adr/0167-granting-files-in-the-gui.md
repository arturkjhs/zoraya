# ADR-0167: Granting files and resources in the GUI

- **Status:** accepted
- **Date:** 2026-11-03
- **Depends on:** ADR-0002, ADR-0003, ADR-0013, ADR-0040, ADR-0050, ADR-0052, ADR-0053, ADR-0055, ADR-0093, ADR-0094, ADR-0097, ADR-0160, ADR-0165, ADR-0168
- **Evidence:** CP-01, CP-02, CP-24, DM-009, DM-039, GR-004, GR-008, X-1, alternatives-postmortem.md#keykos--eros--capros-and-coyotos, desktop/survey.md#capdesk-and-e, desktop/survey.md#polaris, desktop/survey.md#eross-trusted-window-system, desktop/survey.md#macoss-sandboxed-open-panel, desktop/survey.md#xdg-desktop-portal, desktop/survey.md#spoofing-and-the-trusted-path

## Context
An application reaches only what it is given (ADR-0002, CP-01); its launcher routes handles (ADR-0053); on the command line the shell is where a person grants a program a directory or a file: ADR-0153 (accepted) makes the operands a person types the grant, with a kind per operand from the command's description (`read`, `write`, `create`, `remove`, `remove-tree`, `rename`, `tree`), explicit `+r PATH` and `+w PATH` grants, a start-up record (`zoraya_abi::native::Startup`) carrying the namespace table, a `grants` command that shows the whole truth, and a `REPORT` channel through which a refused path becomes a hint. The desktop needs the same thing for "Open" and "Save": a way for a person to pick a file for an application that cannot name files. The survey (`desktop/survey.md#capdesk-and-e`, `desktop/survey.md#polaris`, `desktop/survey.md#eross-trusted-window-system`, `desktop/survey.md#macoss-sandboxed-open-panel`, `desktop/survey.md#xdg-desktop-portal`) finds one pattern five times: a trusted chooser outside the application shows the dialog, the person's choice is the grant, and the application receives access to that one file and nothing else. Miller's "bundle authority with designation" is the principle; CapDesk did it in E; Polaris replaced applications' own dialogs with its own and copied the chosen file into the confined account; EWS noted that a forged dialog "cannot forge possession of the necessary file system capability", so the chooser needs no trusted path of its own; macOS "displays open and save panels in a separate process, and extends your app's sandbox to include the selected URLs"; Flatpak's portal makes "the selected files ... accessible to the application". The KeyKOS lesson is the cost of not doing this: legacy guests got no capability benefit (`alternatives-postmortem.md#keykos--eros--capros-and-coyotos`, X-1). GR-008 records that programs which open paths late are where capability systems hurt; DM-039 is the path race the pattern removes. Measured: nothing on Zoraya. Assumed: the first applications (ADR-0168) need open, save and pick-a-directory, and nothing else.

## Decision drivers
1. An application never names a file it was not given and cannot enumerate what it was not given (CP-01, DM-009, GR-004).
2. The person's ordinary gesture is the grant: no prompt, no permission dialog (`desktop/survey.md#capdesk-and-e`, `desktop/survey.md#polaris`).
3. The chooser cannot be forged usefully: a fake one yields nothing (`desktop/survey.md#eross-trusted-window-system`).
4. One grant mechanism with the shell's (TASK-18): the same handle, the same rights, whether given at launch or at run time.
5. Rights only narrow (CP-02, ADR-0040): read-only unless the person chose to save.
6. No new kernel object: channels, directory and file connections suffice (ADR-0050, ADR-0055).

## Considered options

### Option A: The application's own file dialog over an ambient filesystem (Linux desktops with GTK's chooser in-process)
- **Description:** The toolkit's chooser runs inside the application, which can open any path its user can.
- **Evidence for:** Simple; the dialog can be tailored by the application; no service.
- **Evidence against:** DM-009: the application already has everything, so the dialog grants nothing and a bug or a hostile program reads every file; DM-039; it is what ADR-0002 forbids natively.
- **Cost:** None now; everything later.
- **Precedent:** Every Unix desktop without a sandbox.

### Option B: A trusted chooser service that returns a handle (the powerbox: CapDesk, macOS's open panel, the portal)
- **Description:** A session service, `chooser`, holds the volume root connection and a compositor client channel. An application holds a channel to it, given at launch by the launcher. `Open`, `Save` and `PickDirectory` requests make the chooser show its own window; when the person confirms, the reply carries a file or directory connection cloned from the root with narrowed rights (ADR-0055's `clone`), plus the display name; cancel gives nothing (`desktop/survey.md#capdesk-and-e`, `desktop/survey.md#macoss-sandboxed-open-panel`, `desktop/survey.md#xdg-desktop-portal`).
- **Evidence for:** Drivers 1 to 6. The handle is the same kind the shell gives at launch (driver 4); the application never sees a path (driver 1); the compositor marks the chooser's window as a system window (ADR-0160), and a fake chooser drawn by an application cannot produce a handle (driver 3).
- **Evidence against:** The chooser is a trusted component holding the root; its UI is fixed, and an application cannot add its own options beyond what the protocol offers; "recent files" and "reopen at next launch" need the chooser to remember grants (macOS's bookmarks), not the application.
- **Cost:** *(estimate)* A 1,500-line program over `zoraya-ui`, a 100-line protocol crate, 50 lines in the launcher.
- **Precedent:** macOS's App Sandbox (production), Flatpak portals (production), CapDesk (research).

### Option C: Copy and synchronise (Polaris)
- **Description:** The chooser copies the chosen file into a directory the application already holds, and copies changes back when the application writes (`desktop/survey.md#polaris`).
- **Evidence for:** Works with applications that only know paths, which is how Polaris ran unmodified Windows programs.
- **Evidence against:** Two copies that can diverge; a copy of a large file for every open; it exists to retrofit onto programs that cannot take handles, which Zoraya's native applications can.
- **Cost:** *(estimate)* Option B plus a synchroniser.
- **Precedent:** Polaris.

### Option D: Per-application namespaces built at launch only (Plan 9, Fuchsia's launcher)
- **Description:** The launcher gives each application the directories it may use, once; there is no run-time chooser; an "Open" dialog browses what the application already has (GR-004, `alternatives-postmortem.md#keykos--eros--capros-and-coyotos` for the legacy-guest shape).
- **Evidence for:** No service, no protocol; the shell's grants are exactly this.
- **Evidence against:** The person must know in advance which directories a program will need, which is the complaint GR-008 records (tcpdump's DNS), and either grants too much (a home directory) or relaunches.
- **Cost:** *(estimate)* None beyond the launcher.
- **Precedent:** Plan 9 namespaces, Fuchsia's launcher-built namespaces (GR-004).

## Recommendation
Recommended: **Option B**, with Option D's launch-time grants as the other half of the same mechanism. It is a recommendation, not a decision.

- **Two moments, one grant, one vocabulary: ADR-0153's.** At launch, the panel (ADR-0168) builds the same start-up record `zosh` builds (ADR-0153 rule 8, `zoraya_abi::native::Startup`): the entries come from the application's description (ADR-0156) applied to what the person did (a file opened from the file manager is the description's first path operand, with its kind, which is `read` unless the program is a base-system program of the image, as ADR-0153's Decision says; the six of ADR-0168 are; a drop the same), plus the entries every GUI launch adds (below). At run time the chooser gives what the person picks as an entry of the same kinds: `Open` is a `read` entry on the chosen file; `Save` is a `create` entry, "create or replace this one name" (ADR-0153's Decision), on the parent directory narrowed to the chosen name with ADR-0153's `narrow` request, or the whole parent until `narrow` exists, exactly as the shell does; `PickDirectory` is a `read` entry on the directory, or a `tree` entry when the request asked for `write` and the dialog said so. Rights are ADR-0153's table, row for row; the connection is a `zoraya-proto-file` connection the service checks (ADR-0055 `clone`, ADR-0153's `narrow`). The reply names the entry as `grants` would word it (`read`, `create or replace NAME`, `change anything in`), and the panel's launch record and tooltip use the same words.
- **Protocol** (`zoraya-proto-chooser`, ADR-0052). Application to chooser: `Open { title, filters, multiple }`, `Save { title, suggested_name, filters }`, `PickDirectory { title, write }`. Reply: `Chosen { entries[] }`, each entry a connection, its display name and its kind in ADR-0153's words (at most 64 `[assumption]`), or `Cancelled`. The application's runtime (`zoraya-rt`) adds each entry to its namespace table under a synthetic absolute path of its own (`/chosen/N/NAME`, N a counter: no entry shares a prefix with another, so ADR-0153 rule 2's merging never applies, and the display name is a label the program shows, never a path it resolves), so that a program written against ADR-0153's table and one written against the toolkit see the same thing. One request in flight per connection; a second is refused. A title is UTF-8 of at most 128 bytes and is shown inside the chooser's own window with the chooser's own heading "Open a file for *application name*", where the name comes from the launcher, not the request, so that a request cannot claim to be another program.
- **The chooser process.** Started by `init`'s session table (ADR-0097) with the volume root, a compositor client channel and a manager-side mark that makes every window it creates a *system window* (ADR-0160's `bg.frame.system` tint); the compositor centres a system window on the display, not over the requesting application, because no message may name another client (ADR-0093) and the chooser does not know which window asked. It browses the volume with ADR-0055's directory listing, shows names as UTF-8 (ADR-0013), lets the person navigate, create a folder, type a name for `Save`, and confirm or cancel. It holds no state about applications beyond the open requests; "recent files" is a follow-up that lives in the chooser.
- **The chooser as a sheet, and the mark an application cannot reproduce.** With `chooser.style = sheet` (ADR-0161; the second mist direction shows it, the first and the others keep the centred system window) the chooser's dialog is ADR-0160's *sheet* kind: it slides out from under the title bar of the window that asked, centred on that window, moved and stacked with it, with no close or minimise buttons of its own and no title bar; it closes by Cancel, Open or Escape. The compositor attaches it to the right window by the tag the panel issued with the application's chooser channel (ADR-0160's `CreateSheet { tag }`), so the chooser still never learns which client asked and no client ever names another. The *trusted-UI mark* is three things an application cannot draw, all of them the compositor's: (1) the sheet begins with a strip in `bg.frame.system` that carries the system emblem (a Z on a rounded square in that tint) and the heading "Open a file for *application name*"; the chooser's own buffer begins below the strip, so even the chooser does not paint it; (2) while a sheet is open, the top bar (ADR-0168) shows the same emblem and heading in its middle, in a region of the bar the compositor paints and masks out of the panel's buffer; (3) the sheet overlaps the owner's title bar line: a client's pixels never leave its body (INV-0160-1), so a thing that starts above the body line and reaches into the bar is not the client's. A window that paints a sheet-shaped picture inside its body can mimic (1) in its own pixels but not (2) or (3), and the system tint and the emblem are never given to a client (INV-0167-4). The mockup's `screen_chooser_sheet` in `tools/mockups/src/scene.rs` is the reference drawing. With `chooser.style = window` the mark is the system tint of the whole frame, as before. Under ADR-0172 ("glow means trust", the `clear-*` mockups, `clear_chooser` in `tools/mockups/src/clear.rs`) the sheet is drawn in the trusted material of ADR-0160 instead of the tint, with the same strip, emblem and heading, and the sentence under the list shows the grant's text form beside its words: "edit will be given this file, to read:" and `+r ~/project/plán.txt edit`, the line that would do the same in `zosh`; the bar shows the heading while the sheet is open, as before.
- **Rooms** (ADR-0172). A launch record in an untrusted room carries no chooser channel: its programs can be given a file only by a drop or by the person's `+r` line in `zosh`, each confirmed in the compositor's own card (ADR-0172 point 6), and never ask. In a trusted room the chooser is as above, and the chooser reports each `Chosen` to the compositor as `Granted { tag, words }` so that the window's frame shows the new entry (ADR-0172 point 4); the heading names the application and the window's badge and the dock's filled chip name the room (ADR-0172).
- **What an application can never do.** List a directory it was not given; open a name it was not given; learn the path of what it was given (it gets a display name); read another window (ADR-0093); request the system tint; keep a grant across launches (until the chooser remembers it on the person's behalf, follow-up); escalate a read grant to write.
- **Relation to the shell: explicit points of agreement and difference with ADR-0153.** (1) The vocabulary is ADR-0153's: kinds, rights, `narrow`, the `Startup` record, the `REPORT` channel and the `grants` wording; this ADR adds no right and no kind. (2) ADR-0153 rule 1 lists what a command receives from the shell ("nothing else: no volume root, no console"); a GUI launch adds four entries that have no shell counterpart: the compositor client channel, the chooser channel (not in an untrusted room, ADR-0172), `/system/fonts` read-only (ADR-0162) and the application's data directory (a per-application directory the panel creates under the volume) as a `tree` entry, and under ADR-0172 the room's entries before them; the settings program alone receives a fifth, a channel to the panel, and `/config` from the panel's own table (ADR-0169); the panel's tooltip shows them with the rest. (3) ADR-0153 rule 11's refused-path report: GUI applications carry the same `REPORT` channel; the panel reads it when the application ends, or when its window is closed, and shows the hint in the window list's tooltip, as the path the program tried and "open it through the chooser, or in the shell: +r DIR", since ADR-0153 rule 11's form (`to allow it: +r DIR LINE`) has no command line to repeat here; opening the file through the chooser is the GUI's grant. (4) `cwd none` and the current directory: a GUI application has no current directory; the data directory takes that place, the `Startup` record's current directory is the data directory's absolute path, and nothing is readable by default beyond it. (5) Descriptions: a GUI application's `.cmd` description (ADR-0156) gives the panel its name and its operand kinds for "Open with" and drops (an icon comes from the panel's own table by program name; ADR-0156's format gains no key); a program without one is launched with the four GUI entries only. GUI descriptions are embedded in their programs, which are in the system image, as ADR-0156 allows for native programs, so INV-0153-6 holds: nothing on the volume designates.
- **Drag and drop** from the file manager (ADR-0168) into an application is the same grant made by a drop, routed through the compositor as EWS routes paste (`desktop/survey.md#spoofing-and-the-trusted-path`): ADR-0170 decides it, with this ADR's entries as what a drop carries.

**Tensions with accepted ADRs.** *ADR-0053* "a process has what it was handed": the chooser hands handles at run time, which is still a handle the launcher's chain produced (the chooser got the root from `init`); no name registry appears. *ADR-0055* `clone` with narrowed rights and *ADR-0153*'s `narrow` are relied on as written. *ADR-0153 rule 1* is extended by the four GUI entries (point 2 above), a stated difference, not a change to the shell's rule. *ADR-0097*: one more entry in the session table.

### Effect of the vision
For target 2 this is the mechanism that makes an agent's file access visible and chosen by a person; an agent's sandbox gets a chooser channel or not, and without one it has only what its launcher gave. A supervisor that wants to approve grants automatically would hold the chooser's manager side, a later capability (CP-24's shape). Target 3 wants recent files, bookmarks and "open with": chooser state, no change to applications. Networking: a remote file is a connection like any other. Threads: none.

### Deferred to stage 6
POSIX programs reach files through the namespace table (ADR-0107); a POSIX program started from the desktop gets a table built by the launcher from the same grants, so `tcc` opened on a file from the file manager sees that file under a path the table gives it. The chooser is not available to POSIX programs in stage 7.

## Consequences
- **Positive.** Open and Save work as people expect, and grant exactly one file; the pattern is proven in production twice.
- **Negative.** A trusted service holding the root; a fixed dialog; no persistence of grants yet.
- **Follow-up.** `chooser`, `zoraya-proto-chooser`, the launcher's data directory, recent files, drag and drop (ADR-0170).

## Invariants
- **INV-0167-1.** `zoraya-proto-chooser` and `zoraya-proto-gui` have no message that carries a path, and the only names they carry are display names no party resolves (the runtime enters a chosen entry under a path of its own); an application reaches a file only through a `zoraya-proto-file` connection it holds (ADR-0055's `open` with a relative path under such a connection is use of a grant, not a grant). *Check:* host test over the ordinals and field kinds of the chooser and GUI protocol crates (no string field is resolved as a path or a name, with a test that the runtime's table lookup never sees a display name), plus INV-0013-5's existing check that a relative path never escapes its connection.
- **INV-0167-2.** The chooser replies `Chosen` only after a confirming user action in its own window: a request with no pointer or keyboard event from the compositor never produces a connection. *Check:* host test of the chooser's logic against a fake compositor that sends no input, with a deadline; and one that sends a click on Cancel.
- **INV-0167-3.** A connection returned for `Open` cannot write, and one for `Save` or `PickDirectory` carries exactly the rights of ADR-0153's table for its kind (`create` or `read` or `tree`), nothing more. *Check:* in-QEMU test opening a file through the chooser driven over QMP and asserting `AccessDenied` on write; host test comparing the rights the chooser passes to `clone` and `narrow` with ADR-0153's table, row for row (the same test data INV-0153-2 uses).
- **INV-0167-4.** No client can obtain the system window tint, a sheet, the system emblem, the trusted material or a pixel in the bar's trusted-mark region: the compositor applies and paints them only for connections its manager marked. *Check:* host test sending every client ordinal and asserting the tint, the sheet count and the bar's pixels never change; the GUI test reads the chooser's frame colour, or the sheet's strip and the bar's middle when the direction uses the sheet.

## Open questions
- How `init`'s session table and the panel share the launching of applications (ADR-0168 decides).
- Whether the data directory per application should be created lazily.
- Whether the panel's tooltip is enough of a `grants` for the GUI, or a "What this program has" window is needed.

## Revisit triggers
- A program that needs a grant the chooser cannot express (a device, the network).
