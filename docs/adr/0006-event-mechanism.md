## Context

CP-08 asks for one waitable-object model through one port or queue; X-4 is the conflict between a completion-native design (CP-08, GR-009), the readiness semantics POSIX needs (`pselect`, `poll`) and a small attack surface (CP-09, DM-025). DM-026 (readiness vs completion) is *contested*. This ADR decides the native primitive for waiting on several things at once: a handle becoming readable or writable, a process exiting, an interrupt arriving, a timer expiring. The TASK-02b event timelines are its primary input.

**Division of labour with ADR-0004.** ADR-0004 defines what the events *are* (exit records, request signals, dispositions, job-wide delivery, exceptions). This ADR defines how a thread *waits* for them and how `libposix` implements POSIX waits, including the `MAKEFLAGS` jobserver. ADR-0004's "wait point" is this ADR's port wait.

**What is measured.**

- Serial builds make no readiness call at all: no `poll`, `select`, `ppoll`, `pselect6` or `epoll_*` in any T0–T3 core trace; `ppoll` appears only in busybox sh's line editor (222 calls, comparison run) (`task-02/conflict-impact.md#x-4-…`). GNU make imports `pselect` for the jobserver; it is M3's only DM-023 site (`task-02/callsite-analysis.md#feature-6-…`).
- Parallel GNU make adds exactly one kind of readiness call: `pselect6(4, [3], NULL, NULL, NULL, {sigmask=[]})`, one fd (the jobserver read side), no timeout, empty signal mask; 1 to 100 calls per build (W8 `-j4`: 72–100). SIGCHLD is blocked everywhere else and unblocked only inside this call, so the wait means "token *or* child exit". Most waits end by child exit: 55–60 of 72–100 per W8 `-j4` build, 20–22 of 55–57 in W2 `-j4`. Every interruption is followed by `rt_sigreturn` returning `EINTR`. No `poll`, `select`, `epoll_*` or `waitid` appeared in any TASK-02b run (`task-02b/parallel-surface.md#new-syscalls-and-argument-patterns`; `task-02b/conflict-impact.md#x-4-…`).
- After a ready `pselect6`, a non-blocking `read` takes the token and can fail with `EAGAIN` when another make took it first: 9 times in two W8 `-j4` fifo runs (`task-02b/parallel-surface.md#new-syscalls-and-argument-patterns`).
- `wait4` grows from 40 to about 135 (W2) and 78 to about 226 (W8): make polls `wait4(-1, WNOHANG)` after every wake-up; blocking `wait4(-1, 0)` remains for final reaps (`task-02b/parallel-surface.md#new-syscalls-and-argument-patterns`).
- Jobserver mechanics: FIFO style (the 4.4.1 default) creates `/tmp/GMfifo<pid>` with `mknodat`, the top make opens the read side `O_RDONLY|O_NONBLOCK` and the write side `O_WRONLY`, sub-makes open it by path from `MAKEFLAGS` and set `O_NONBLOCK` with `fcntl`; pipe style uses `pipe2` with flags 0 and publishes `--jobserver-auth=3,4`, with `-2,-2` appended for non-recursive recipes; tokens are single `+` bytes; token reads per build: 34–38 (Lua), 2 (W8 `-j2`), 17–26 (W8 `-j4`); pipe-style fds 3 and 4 are inherited only by recursive makes, with close-on-exec toggled around those spawns (`task-02b/parallel-surface.md#new-syscalls-and-argument-patterns`; `task-02b/callsite-analysis.md#1-jobserver-gnu-make`).
- Each job spawned while another runs gets a "bad stdin": a pipe whose write end is closed, `dup3`'d to fd 0 in the child (`task-02b/parallel-surface.md#new-syscalls-and-argument-patterns`).
- Six libc functions are new to the lower bound under parallelism: `kill`, `mkfifo`, `pselect`, `stpncpy`, `ttyname`, `writev`; all were already imported (`task-02b/parallel-surface.md#new-libc-functions-interposer-lower-bound`).
- State at interrupt time (W9, delay 1.5 s): leaf makes blocked in `pselect6`; top and level-1 makes in blocking `wait4(-1)`; dash waiting for the foreground job; 4 recipes writing files (`task-02b/event-timelines.md#state-when-the-interrupt-arrives-…`).
- dash waits for children with `sigsuspend` + SIGCHLD + `wait4`, never with a readiness call; background jobs and pipelines use the same mechanism; `wait4(WNOHANG)` drains the rest (`task-02b/event-timelines.md#w10-…`; `task-02b/callsite-analysis.md#2-readiness-waiting-and-child-reaping`).
- pdpmake makes no readiness call at any `-j` because it is serial (`task-02b/parallel-surface.md#concurrency-actually-achieved`).
- M7 estimate: `pselect` + blocked SIGCHLD is `restructure`, about 10 lines, "one wait over two handles"; token handling is `direct` (a counting semaphore or token pipe passed explicitly); the auth string is `emulate` because other programs read it (`task-02b/callsite-analysis.md#1-jobserver-gnu-make`). TASK-02's M3 had estimated the same site at about 60 lines (`task-02/callsite-analysis.md#feature-6-…`); M7, which read the code with the event model in hand, supersedes it, and the 6× difference shows how rough both estimates are.

**What is assumed.** Readiness needs beyond the toolchain (line editors, `less`, terminal multiplexers, network software) were out of scope. Whether other jobserver clients (ninja, cargo) use `poll` is unmeasured. Throughput of one wake-up per child exit plus one per token at high `-j` is unmeasured (`task-02b/conflict-impact.md#x-4-…`, Unknown). Nothing was measured on our kernel.

**Forces from TASK-01.** `select`/`poll` cost grows with the watched set; epoll keyed registrations to the open file description instead of the fd, so closing an fd does not remove a registration and stale events arrive (DM-023, *mistake*); kqueue deletes registrations on close and covers processes, signals, timers and vnodes in one queue (DM-023, DM-130). POSIX and Linux AIO were niche and buggy; io_uring fixed that and became 60 % of kCTF exploit submissions in a year, because a second asynchronous path to most of the kernel must replicate every check (DM-024, DM-025, CP-09). Completion models commit a buffer per pending read and clash with cancel-by-drop (DM-026, GR-009); readiness cannot express disk I/O (DM-029). NT's `WaitForMultipleObjects` is capped at `MAXIMUM_WAIT_OBJECTS` handles (64, `[outside evidence: Win32 documentation]`); Zircon's one-shot async waits can miss an edge; both still need a second API for data I/O (DM-130). QNX builds asynchronous patterns from pulses on synchronous IPC (GR-018). Timeouts must be monotonic by type (CP-20). Hubris has no kernel queues at all (`alternatives-postmortem.md#hubris`). Redox added io_uring-like rings late and gained 14× on NVMe in a benchmark that bypassed the filesystem, which the postmortem infers means the default path was slow (`alternatives-postmortem.md#redox`, marked as inference there).

## Decision drivers

1. **The toolchain's only multiplexed wait is "one pipe readable OR any child exited"** (`task-02b/conflict-impact.md#x-4-…`, "Out: the POSIX layer needs a general readiness multiplexer for the toolchain"). Either native model serves it ("Rules in either native model for the toolchain").
2. **Child exit must be waitable in the same wait as I/O readiness** (DM-130; `task-02b/callsite-analysis.md#1-jobserver-gnu-make`: the `pselect`+SIGCHLD construction "exists only because 'child exited' is a signal and 'token available' is an fd").
3. **Interrupt must be waitable in the same wait too** (ADR-0004 rule 2: a delivered request is a signal on the process's own handle; the W9 state shows every make blocked in a wait when the interrupt arrived).
4. **Registrations belong to the handle, not the object, and vanish on close** (DM-023's epoll lesson; CP-02 handles can be duplicated).
5. **Small attack surface** (CP-09, DM-025): no shared-memory submission ring in the first release; rings, if ever, must be capabilities that name their objects and operations.
6. **Cancellation without `EINTR`** (CP-10, DM-027, DM-059): a blocked wait ends by deadline, by a queued user packet or by handle close.
7. **The personality must emulate `pselect` with atomic-mask semantics and non-blocking `read` with `EAGAIN`** on pipes and FIFOs (`task-02b/conflict-impact.md#x-4-…`, "Out: …"), plus `sigsuspend` and `wait4(WNOHANG)` (`task-02b/callsite-analysis.md#2-…`).
8. **`MAKEFLAGS` must keep working** in both styles: fd numbers at fixed slots (ADR-0003 INV-0003-6) and a FIFO path in `/tmp` (ADR-0002 rule 5) (`task-02b/conflict-impact.md#x-1-…`).
9. **Completion I/O for files is wanted eventually** (CP-08, DM-029, GR-009) but is *contested* as the native model (DM-026) and not needed by the data. The wait primitive must be able to carry completions later without a second queue model (DM-130 cost: NT and Zircon each needed a second API).

## Considered options

### Option A: POSIX readiness plus signals (baseline)

- **Description:** `select`/`poll`/`pselect` on fd sets, `SIGCHLD` for child exit, `EINTR` to break waits, timers by `SIGALRM` or `timeout` arguments. Exactly what GNU make and dash use today.
- **Evidence for:** Every measured program works unchanged; the only readiness user needs one fd (driver 1). Stateless `select` adds no kernel state and is easy to reason about (DM-023, "Why it was chosen"). The programs' constructions (`pselect` with atomic mask, `sigsuspend`) are correct and were observed to behave correctly in every run (`task-02b/parallel-surface.md#interrupted-system-calls`).
- **Evidence against:** It requires signals (ADR-0004 Option A, rejected). Child exit, timers and signals are outside the fd model and need retrofits (DM-130, *mistake*). Cost grows with the interest set (DM-023). Files are always "ready" (DM-029). `EINTR` at every call site (DM-027). The make jobserver's masking code exists only because of this split (driver 2).
- **Cost:** *(estimate)* No emulation. The native stack inherits DM-023, DM-027 and DM-130.
- **Precedent:** Unix. Works, with the catalogue.

### Option B: Completion queue as the native primitive (io_uring-style rings)

- **Description:** Threads submit operations (read, write, wait-for-exit, wait-for-request, timer) to a submission ring and collect completion records from a completion ring, both in shared memory. "Readiness" is expressed as a submitted read that completes when data arrives; child exit as a submitted wait that completes with the exit record. Precedents: io_uring (GR-009, DM-025), IOCP (GR-009), Redox Rings (`alternatives-postmortem.md#redox`).
- **Evidence for:** One model for files, pipes and processes from the start (CP-08, DM-029); batching cuts syscalls, which matters more after speculation mitigations (GR-009); Redox measured 14× on NVMe after adding rings (`alternatives-postmortem.md#redox`). The research files' own relevance notes argue for doing this now: DM-024 says native async I/O "has to be part of the design from day one and cover all operations. Bolting it onto a synchronous VFS produces exactly this outcome", and DM-029 says that because our filesystem will be a service from the start, "file and network I/O can share one asynchronous model". The toolchain's wait is expressible as two pending operations (a token read and a wait-any on children) (`task-02b/conflict-impact.md#x-4-…`, "So does a completion-native model"). A Rust async runtime fits a completion queue (GR-009 relevance).
- **Evidence against:** io_uring is the main exploit target of its era because the ring is a second unfiltered path to the kernel and seccomp cannot see into it (DM-025, CP-09); double fetches return by design on shared rings (DM-160, X-5). Completion commits a buffer per pending read and clashes with cancel-by-drop futures (DM-026, GR-009). The personality needs readiness anyway (`pselect`, driver 7), so the ring would carry poll-style ops as io_uring does, which is both models. The data shows no throughput need: 1–100 waits per build (driver 1).
- **Cost:** *(estimate)* Kernel: the largest option; every operation gets an asynchronous path with cancellation (DM-024's lesson). Security review per opcode (CP-09). Library: readiness emulation over completions. Performance: best for high-throughput I/O, irrelevant for the measured workloads.
- **Precedent:** Windows IOCP (decades, limited to I/O ops), io_uring (fast; disabled by Google in production, DM-025), Redox Rings (2026, bypassing the filesystem in the benchmark).

### Option C: Handle signals and a port (Zircon ports, NT waitable objects, kqueue as the Unix-but-not-POSIX precedent)

- **Description:** Every kernel object exposes a small set of *signals* (byte stream: `READABLE`, `WRITABLE`, `PEER_CLOSED`; process: `TERMINATED`, `REQUEST_PENDING`; job: `TERMINATED`, `SUSPENDED`; timer: `EXPIRED`; channel: `READABLE`, `PEER_CLOSED`; user objects: `USER_0..n`). A *port* is a kernel object that collects *packets*. A thread subscribes `(port, handle, signal mask, key)` and waits on the port with a deadline; when a subscribed signal is asserted the port queues a packet `{ key, signals }`. Subscriptions are persistent and level-triggered (a packet is available while the signal is asserted and the subscription is armed), with an edge option; they are keyed to the *handle* and removed when it is closed. User packets can be queued to a port by any holder of it. Timers are objects. Data transfer is a separate, synchronous or non-blocking call on the handle. NT's `WaitForMultipleObjects` on object handles is the older form (GR-003, DM-130); kqueue is the Unix form that covers processes, signals and timers in one queue and deletes registrations on close (DM-023, DM-130).
- **Evidence for:** It is the model the M7 mapping used and found to *remove* code in make: "one blocking wait on {token semaphore, child-exit events}" (`task-02b/callsite-analysis.md#1-jobserver-gnu-make`, `#what-the-mapping-exercise-shows-estimate`). Child exit, requests, readiness and timers are the same kind of thing (drivers 2, 3; CP-08; DM-130). Keying to the handle and removing on close is kqueue's correct answer to epoll's mistake (driver 4, DM-023). No shared-memory ring, so the attack surface is the syscall boundary with copy-in once (CP-09, CP-11, DM-160). Readiness is native, so `pselect` is a thin mapping (driver 7). Cancellation is a user packet or a close (driver 6). Zircon has shipped this on Nest Hubs (`alternatives-postmortem.md#fuchsia--zircon-incl-starnix`).
- **Evidence against:** It is a readiness model: regular files are "always ready" again unless a completion mechanism is added for them (DM-029, DM-026 pro-completion position). NT caps `WaitForMultipleObjects` at 64 handles and Zircon's one-shot waits can miss an edge (DM-130 cost); the design must avoid both. Per-wait packets cost one syscall per event, which the completion camp says is the overhead to remove (DM-026). It needs a second mechanism for bulk asynchronous I/O later (DM-130, "Both systems still need a second API").
- **Cost:** *(estimate)* Kernel: signal state per object type, port with a ready list, subscription table per handle, timers; a few thousand lines. Library: `pselect`/`poll`/`sigsuspend`/`wait*`/`nanosleep` over `port_wait`; thin. Performance: O(events) per wait; one syscall per data transfer. Compatibility: every measured scenario (walkthrough below).
- **Precedent:** NT (object waits, 30 years; IOCP added beside them), Zircon (ports plus channels; Starnix emulates `poll`/`epoll` on them), FreeBSD kqueue (2000; still the BSD/macOS event API).

### Option D: Synchronous IPC with notification objects (seL4, QNX pulses)

- **Description:** Threads block in a synchronous receive on an endpoint; asynchronous events are *notifications*, a word of signal bits that a thread can wait on together with its endpoint; servers deliver "pulses" for readiness and exit (GR-018, DM-018, `alternatives-postmortem.md#qnx`).
- **Evidence for:** Minimal kernel objects; the kernel never buffers data (GR-018); priority inheritance across calls is natural (GR-018, CP-18). QNX has carried a full POSIX personality on this for 30 years (`alternatives-postmortem.md#qnx`). seL4's verified kernel has only this (`alternatives-postmortem.md#l4-family-and-sel4`).
- **Evidence against:** Synchronous rendezvous is "clearly the wrong way" to synchronise across cores and forces multithreaded servers (DM-018, GR-018 cost); a server cannot wait for clients and interrupts without notifications, which seL4 had to add (DM-018). A notification is a word of signal bits with no payload `[outside evidence: seL4 manual]`, so "which child exited" needs a second query, and the word's width bounds the distinct sources per waiter. QNX's own asynchronous patterns are built from pulses, which is Option C's packet by another name (GR-018). T0–T2 are single-threaded (`task-02/posix-surface.md#key-observations`); a design that assumes server threads does not fit the hosted programs.
- **Cost:** *(estimate)* Kernel: smallest. Library and services: every readiness source becomes a server that sends pulses; the toolchain's "pipe readable" becomes an IPC from the pipe service. Performance: IPC-bound (DM-018: implementation-dependent).
- **Precedent:** QNX (production), seL4 (verified; needs Linux VMs for general software), Hubris (static, single-purpose).

## Recommendation

**Recommendation (not a decision): Option C**, specified as follows, with Option B kept open as a later *addition* delivered through the same port (driver 9), never as a second queue.

**Native ABI.**

1. **Signals per object type.** The `abi` crate defines one signal enum per waitable type; every kernel object type is waitable or is marked `NotWaitable` explicitly. Byte streams (pipes, FIFOs, terminals, sockets later): `READABLE`, `WRITABLE`, `PEER_CLOSED`. Process: `TERMINATED`, `REQUEST_PENDING` (ADR-0004), `SUSPENDED`. Job: `TERMINATED` (no live processes), `SUSPENDED`. Timer: `EXPIRED`. Channel: `READABLE`, `PEER_CLOSED`. Event object (user-created): `USER_0..7`, set and cleared by holders with the `signal` right. Regular files: `NotWaitable` in the first release (DM-029 acknowledged; completion for files is the Option B addition).
2. **Port.** `port_create() -> Port`. `port_subscribe(port, handle, signals, key, mode)` with `mode ∈ { Level, Edge }`, persistent until `port_unsubscribe(port, key)` or the handle is closed. `port_wait(port, deadline, &mut [Packet]) -> n` blocks until at least one packet is available or the deadline passes; returns as many packets as fit. `port_queue(port, Packet::User(..))` posts a user packet from any thread holding the port. A `Packet` is `{ key, kind: Signal{asserted} | User{data} | Completion{..} (reserved) }`. The kernel keeps a ready list per port so `port_wait` costs O(packets returned), not O(subscriptions). A `Level` subscription yields a packet on each wait while the signal is asserted; an `Edge` subscription yields one packet per assertion. There is no cap on subscriptions other than memory charged to the holder's job (CP-14).
3. **Single-object wait.** `object_wait_one(handle, signals, deadline)` is a convenience with the same semantics, for the serial case.
4. **Deadlines.** Every blocking call takes a `Deadline`, a monotonic instant or `Infinite` (CP-20); there is no relative-timeout argument type.
5. **Cancellation.** A blocked `port_wait` returns `Cancelled` when another thread closes the port handle it is waiting on, returns `DeadlineExceeded` when its deadline passes (rule 4), and returns normally when a user packet is queued. Nothing else ends a wait except the process itself ending (a `Terminate` disposition or `job_kill`, ADR-0004); there is no `Interrupted` status in the `abi` status vocabulary (CP-10, DM-027).
6. **Data transfer.** `stream_read` / `stream_write` on byte streams are synchronous and take a `nonblocking` flag; a non-blocking call that would block returns `WouldBlock`. Readiness plus non-blocking transfer is the whole readiness contract.
7. **Reserved: completions.** A later ADR may add submitted operations whose results arrive as `Completion` packets on the same port (CP-08). Any such addition must enforce the caller's handle rights per operation and must not use a shared-memory submission ring without a capability naming its objects and operations (CP-09, DM-025). Nothing in this ADR depends on it.

**Personality implementation (`libposix`).** Each POSIX process has one port, created by `libposix` at startup and, because `Port` is non-duplicable (ADR-0003 rule 3), created afresh in a `fork()` child by the `fork()` wrapper. Every POSIX fd that wraps a byte stream, and every child process handle, is subscribed for the duration of a wait call and unsubscribed on return; ADR-0004's dispositions decide which sources a given wait includes.

- **`pselect(nfds, r, w, e, timeout, sigmask)`:** for each fd in the sets, subscribe its handle for `READABLE`/`WRITABLE`/`PEER_CLOSED` (Level) with the fd number as key; if `sigmask` unblocks a signal that has a handler, make its source visible: for SIGCHLD, subscribe every child process handle for `TERMINATED`; for request-mapped signals, subscribe the process's own handle for `REQUEST_PENDING`; set a timer if `timeout` is given; `port_wait`. On fd packets: fill the sets and return the count. On a child or request packet: run the handler (ADR-0004) and return `EINTR`, which is the measured `ERESTARTNOHAND` → `rt_sigreturn(EINTR)` behaviour. Unsubscribe the temporary subscriptions on return. `select` and `poll` are the same without the mask.
- **`sigsuspend(mask)`:** subscribe the sources of every unblocked signal with a handler (children for SIGCHLD; own handle for requests), `port_wait(Infinite)`, run the handler, return `EINTR`.
- **`wait4(pid, status, options)`:** `WNOHANG`: `object_get_signals` on the child's handle, read the exit record if `TERMINATED`, no wait. Blocking: `object_wait_one` on that child, or `port_wait` over all children for `pid = -1`; also subscribe request sources if a handler could interrupt it (the W9 top-make case: the wait returns the interrupt packet, the handler runs, and the original `wait4` is never resumed, as measured). `WUNTRACED`: also `SUSPENDED` on the child's job. The exit record maps to `status` per ADR-0004.
- **`nanosleep`, `pause`, `alarm`:** a timer object subscribed to the port, plus signal sources as above.
- **Non-blocking fds:** `O_NONBLOCK` is a `libposix` flag per fd that selects the `nonblocking` flag on `stream_read`/`stream_write`; `WouldBlock` → `EAGAIN`.
- **Jobserver, pipe style:** `pipe()` → a byte-stream pair at fds 3 and 4; `write` of N−1 tokens; `fcntl(F_SETFD)` toggling becomes "include fds 3 and 4 in the spawn handle list at slots 3 and 4" for recursive makes only (ADR-0003 rule 1, INV-0003-6); `--jobserver-auth=3,4` is then true in the child; `-2,-2` needs nothing. `pselect6([3])` as above; the non-blocking `read` after readiness returns `WouldBlock` → `EAGAIN` when a sibling took the token, as measured.
- **Jobserver, FIFO style:** `mkfifo("/tmp/GMfifoN")` → `libposix` resolves `/tmp` through the namespace table (ADR-0002 rule 5) to the session's temporary directory and asks that directory's service to create a FIFO node; `open(path, O_RDONLY|O_NONBLOCK)` and `open(path, O_WRONLY)` return handles to the same byte-stream object; sub-makes open it by path from `MAKEFLAGS` through their own namespace table, which shares the session's `/tmp` entry. The FIFO node must implement POSIX open semantics (a non-blocking read-side open succeeds at once; a write-side open with an existing reader succeeds at once; `unlink` removes the name while open handles stay valid). `fcntl(F_SETFL, O_NONBLOCK)` is a `libposix` flag. The rest is as pipe style.
- **Bad stdin:** `pipe()` + close of the write end + `dup3` to fd 0 → a byte stream with `PEER_CLOSED` at slot 0 in the handle list.

**Scenario walkthrough.** Every TASK-02b scenario, with the native expression (what a program written against the port would do) and the personality expression (what `libposix` does for the unmodified program).

No readiness anywhere. | `posix_spawn` → `spawn`; `wait()` → `object_wait_one`; pdpmake `system()` likewise (M4). No port needed beyond the one wait. Interrupted-system-call semantics as measured (`task-02b/parallel-surface.md#interrupted-system-calls`) are reproduced where POSIX programs asked for them (`pselect6` with its mask, `sigsuspend`, abandoned `wait4`) and are absent natively (rule 5).

**Why C.** Drivers 1–8 are all met by C with thin personality code; B meets them at the cost of the largest kernel surface and the documented exploit record, for a throughput benefit the data does not call for; D fits a verified microkernel but moves every readiness source into a server and assumes threaded clients the hosted programs are not; A is the mistake catalogue. Driver 9 is why C reserves a completion packet kind rather than ruling completions out: DM-026 is contested and DM-029 is real, and the port is where completions should land when they come. DM-024's warning against "bolting on" asynchrony is answered by the shape, not the timing: the thing Linux bolted on was a second queue beside a synchronous VFS; here the port is the only queue from day one, the filesystem is a service that can complete operations into it, and no synchronous in-kernel VFS exists to retrofit. What is deferred is the submission side, until a measured workload needs it.

**Principles this recommendation strains.** CP-08 asks that asynchronous I/O "cover all operations, including file I/O, from the start"; this recommendation defers file completions (rule 7) because the data shows no need and CP-09/DM-025 show the risk. That is X-4 resolved toward readiness-first, which the architect should weigh against CP-08's wording. CP-09 is satisfied by having no ring.

## Consequences

- **Positive.** One wait primitive for I/O, exit, requests and timers; make's `pselect`+mask construction becomes one subscription set; `EINTR` and masks are personality-only. Registrations die with the handle (DM-023 fixed by construction). No shared-memory ring in the TCB.
- **Negative.** Regular files are not waitable at first (DM-029 stays, in the personality's "always ready" form). One syscall per data transfer. A later completion addition must be designed against the port without a second queue. Level-triggered persistent subscriptions need a ready list per port that is correct under concurrent close, which is the epoll-shaped kernel code the DM-023 lesson warns about; the invariants below pin its behaviour.
- **Follow-up work.** `abi` signal enums per object type, `Port`, `Packet`, `Deadline`. FIFO nodes in the temp-directory service with POSIX open semantics. `libposix` `pselect`/`sigsuspend`/`wait4` over the port. A prototype rerun of W2-j, W8, W9 and W10 as the acceptance test. A measurement of wake-ups per second at `-j` above 4 (unmeasured).

## Invariants

- **INV-0006-1.** Every kernel object type in the `abi` crate either defines a signal enum or is marked `NotWaitable`. *Check:* a compile-time trait bound in `abi` (`impl Waitable for T` or `impl NotWaitable for T`) plus a test enumerating object types.
- **INV-0006-2.** No native blocking call takes a signal mask, an fd/handle array to scan, or a relative timeout; every blocking call takes a `Deadline`. *Check:* a lint over `abi` signatures: parameters of blocking calls are drawn from `{ Handle, Port, Deadline, &mut [Packet], flags }`.
- **INV-0006-3.** `port_wait` cost is independent of the number of idle subscriptions. *Check:* a benchmark test that measures the median latency of 10,000 `port_wait` calls each returning one packet, once with 1 idle subscription and once with 10,000, and asserts the second median is at most 1.5× the first (`[assumption]`: the 1.5 bound is a starting value for the architect to change).
- **INV-0006-4.** Closing a handle removes all its port subscriptions; no packet keyed to a closed handle is ever delivered afterwards. *Check:* a test that subscribes, closes, asserts the signal on the underlying object through another handle, and waits with a short deadline expecting no packet.
- **INV-0006-5.** A `Level` subscription cannot miss an assertion that happens between `port_subscribe` and `port_wait`. *Check:* a test that asserts the signal before subscribing and expects a packet on the first wait.
- **INV-0006-6.** A blocked `port_wait` returns when a user packet is queued or when the port handle is closed by another thread; no other call unblocks it. *Check:* tests for both, plus a lint that the `abi` status enum has no `Interrupted` variant.
- **INV-0006-7.** `libposix`'s `pselect` returns `EINTR` only if a handler ran, and a wait on an fd set never returns because of a signal that is ignored or blocked. *Check:* `libposix` unit tests with each disposition.
- **INV-0006-8.** The ready list honours handle rights: a subscription requires the `wait` right on the handle, and a handle without it cannot be subscribed. *Check:* kernel test with a duplicated handle lacking the right.
- **INV-0006-9.** A FIFO node in the temp-directory service satisfies the three POSIX open behaviours listed above. *Check:* a service test reproducing GNU make's open sequence (`O_RDONLY|O_NONBLOCK` then `O_WRONLY`, then a sub-make's `O_RDONLY` with `O_NONBLOCK` set afterwards).

## Open questions

- Wake-up rate at high `-j`: one packet per child exit plus one per token; unmeasured above `-j4` (`task-02b/conflict-impact.md#x-4-…`, Unknown). Measure on the prototype with W8 at `-j16`.
- Other jobserver clients (ninja, cargo) and their readiness calls (`poll`?): unmeasured; `poll` maps to the same port, so the question is only whether they need anything beyond pipes and FIFOs.
- Interactive line editors (`ppoll` in busybox sh, 222 calls): a terminal handle with `READABLE` covers it, but no T0 core program needed it; confirm when a line-editing shell enters scope.
- When and how file completions are added (rule 7): a separate ADR after a measured need (for example a build that is disk-bound on uncached reads).
- Edge vs level for the personality: `poll`/`select` are level; whether `libposix` ever needs `Edge` is open.

## Revisit triggers

- A measured in-scope workload is disk-bound and would benefit from asynchronous file I/O: add completions through the port (rule 7) with its own ADR.
- `port_wait` syscall overhead is measured to dominate a parallel build at the `-j` the host supports: consider batching (several transfers per syscall) before considering a ring.
- A jobserver client in scope needs an object type with no signal set: extend rule 1.
- The ready-list implementation shows races under concurrent close (INV-0006-4 failures): reconsider Edge-only one-shot subscriptions (Zircon's choice) with an explicit re-arm.
