# ADR-0304: Signals with threads: per-thread masks, thread-directed signals, and which thread takes a process's request

- **Status:** proposed
- **Date:** 2026-11-12
- **Depends on:** ADR-0004, ADR-0006, ADR-0046, ADR-0104, ADR-0105, ADR-0106, ADR-0300, ADR-0301, ADR-0302
- **Evidence:** CP-10, DM-004, DM-017

## Context

ADR-0106 decided signals in `libposix` for one thread. Delivery is at wait points (every `port_wait` the library makes)
and, when a handler is installed for a request-mapped signal, at the entry of every library function that makes a native
call (item 5: `process_take_request` first). The process's request queue and dispositions are the kernel's, per process
(ADR-0004, `Requests` in `process.rs`); the mask, the pending set and the handlers' state are the library's
(ADR-0106 item 2). Its "Effect of the vision" paragraph already says: "Threads: `sigprocmask` becomes per thread and the
pending set per process, as POSIX says; the poll stays per call."

POSIX with threads: dispositions are per process; the signal mask is per thread; a signal directed at a process goes to one
thread that does not block it; `pthread_kill`, `raise` and signals generated by a thread's own action (`SIGPIPE` on its
write) are directed at the thread; `sigwait` takes a signal for the calling thread. DM-004 records that a process-directed
signal "goes to an arbitrary thread that has not blocked it" and that this is why a library cannot own a signal; DM-017
and CP-10 are why Zoraya has no asynchronous handler and takes a request only at a wait or a library entry.

New facts with threads: every thread that waits has its own port (ADR-0302 item 5) and may subscribe `REQUEST_PENDING` on
the process's own handle (`SELF`) at the same time as others; `REQUEST_PENDING` is level triggered (ADR-0106 item 3), so a
request wakes every thread that is subscribed. `thread_interrupt` (ADR-0300 item 5) wakes one thread's wait without any
kernel signal.

## Decision drivers

1. One thread runs a handler, once per request, and POSIX's rule on who may (a thread that does not block it).
2. A signal is never lost between the kernel's queue and a thread (ADR-0106 driver 1).
3. A handler runs only where the thread holds no library lock (ADR-0302 item 10), so a handler may call anything, as
   make's does (ADR-0106 driver 2).
4. The hot path pays nothing for a process without handlers (ADR-0106 driver 4, INV-0106-2).
5. No wake of every thread for a request that a thread can take, if avoidable: a thundering herd is bounded by the
   128 threads but should not be the normal case.

## Considered options

### Option A: POSIX's rules in the library: per-thread mask, thread-pending and process-pending sets, first taker routes

- **Description:** As recommended below.
- **Evidence for:** Drivers 1 to 4; it is musl's model with the kernel's role played by the library and the port.
- **Evidence against:** The routing is in the library: a request taken by a thread that blocks the signal must be handed
  to another, which costs a `thread_interrupt` and a second poll.
- **Cost:** *(estimate)* 350 lines in `signals.rs` and its host tests.
- **Precedent:** Linux and musl (the kernel picks the thread).

### Option B: Every process-directed signal goes to the first thread; `pthread_kill` is the only other route

- **Description:** The main thread (or the thread that installed the handler) takes all requests.
- **Evidence for:** Trivial; deterministic.
- **Evidence against:** A program whose main thread blocks the signal and has a thread in `sigwait` for it (the common
  "signal thread" pattern) never receives it; a main thread in a long compute loop delays `SIGTERM` handling that another
  thread could do.
- **Cost:** *(estimate)* 80 lines.
- **Precedent:** Early thread libraries.

### Option C: A fresh thread runs each handler (NT's console control handler, DM-017)

- **Description:** On a request the library starts a thread to run the handler.
- **Evidence for:** No async-signal-safety constraint on the handler; no interruption of any running thread.
- **Evidence against:** The handler cannot interrupt a wait of the thread that should see `EINTR`; make's handler needs to
  run on the thread that waits (ADR-0106 driver 2); it spends a thread and a stack per signal.
- **Cost:** *(estimate)* 200 lines and a thread per signal.
- **Precedent:** Windows console events (DM-017).

## Recommendation

**Recommendation (not a decision): Option A.** In detail, as additions to ADR-0106's numbered items:

1. **State.** Per thread, in the thread table (ADR-0302 item 4): the mask (64 bits; `SIGKILL` and `SIGSTOP` never set) and
   the thread-pending set. Per process: the dispositions (the kernel's, and the library's copy of handler addresses), the
   process-pending set, and `handlers_installed`. A new thread starts with its creator's mask, as POSIX says (musl passes
   it through `rt_sigprocmask` at the thread's start, which the shim stores).
2. **Thread-directed signals.** `pthread_kill(t, n)` (musl calls `tkill`, routed to `zoraya_posix_tkill`), `raise(n)`
   (which is `pthread_kill(self, n)`) and the signal a write's `PeerClosed` makes (`SIGPIPE`, ADR-0106 item 8) go to the
   thread-pending set of the target, are delivered at the target's next wait point or library entry if unblocked there,
   and, if the target is another thread, are followed by `thread_interrupt(target)` so a blocked target wakes. `n = 0`
   only checks that the thread exists (`ESRCH` for an ended thread). A thread-directed signal to a thread that blocks it
   stays pending in that thread until unblocked.
3. **Process-directed requests.** A request arrives on the process's request queue (`kill` of this process, `job_signal`,
   a terminal key). The thread that takes it (`process_take_request`, a `REQUEST_PENDING` wake or an entry poll)
   follows ADR-0106 item 4 for the number, then:
   (a) if the taker has the signal unblocked, it handles it itself (item 6 of ADR-0106 unchanged);
   (b) otherwise the signal enters the process-pending set and the taker chooses the receiver: the thread of lowest tid
   that has the signal unblocked and is blocked at a wait point if there is one, else the lowest tid with it unblocked; it
   calls `thread_interrupt` on that thread and goes on with its own call;
   (c) if no thread has it unblocked, it stays in the process-pending set, and any thread that unblocks it
   (`pthread_sigmask`, `sigsuspend`, `sigwait`) takes it at once from that set.
   A thread entering a wait or a library call checks, in this order, its thread-pending set, the process-pending set
   (for signals it has unblocked), then the kernel's queue.
4. **Who subscribes.** A thread subscribes `REQUEST_PENDING` on `SELF` at a wait point only if some signal it has
   unblocked has a handler installed (ADR-0106 item 3, per thread). A process with handlers but every thread blocked has
   no subscriber, and the request waits in the kernel queue until a thread polls or unblocks. `SIGCHLD`'s
   sources, the children's process job handles, are subscribed by the thread that waits (`wait*`, `sigsuspend`, `pselect`)
   in its own port; a `TERMINATED` packet of a child runs the handler by rule 3 like any request. Every waiting thread that
   subscribed wakes on a level signal; each then tries `process_take_request`, one gets the request and the rest find
   `NotFound` and wait again. That herd is bounded by the number of threads that wait with an unblocked handler and is
   the price of having no signal thread (open question).
5. **`sigwait`, `sigtimedwait`, `sigsuspend`, `pause`.** Per thread, with the thread's mask: the thread waits on its port
   with `REQUEST_PENDING` subscribed even though the signal is blocked (as ADR-0106 item 3 subscribes them for
   `sigsuspend`), takes requests for the awaited set only, and returns the number. A thread in `sigwait` for a signal is
   the receiver of rule 3(b) before any thread that does not wait.
6. **Handlers** run on the thread that delivers, with that thread's mask (plus `sa_mask`, and the signal unless
   `SA_NODEFER`), at the wait point or entry, and never while the thread holds the library lock or `MEM_LOCK`
   (ADR-0302 item 10): the wrapper calls the delivery function before taking the lock and after each wait, with the lock
   released. The `EINTR` of ADR-0106 item 6 is that thread's only.
7. **Default actions** are unchanged in kind and are the process's: a signal whose disposition is `Terminate` with
   `SIG_DFL` ends the whole process in the kernel whatever any thread's mask (ADR-0106 item 2's stated deviation now
   covers all threads); `SIG_IGN` drops it; the stop and continue signals stop the whole process through the broker
   (ADR-0105), which parks every thread (ADR-0300 item 7).
8. **Faults** are not signals (ADR-0106 item 12): a fault in any thread ends the process with `Fault`.
9. **`sigprocmask`** in a threaded process is `pthread_sigmask` (the POSIX text leaves it unspecified; musl does this).
10. **`SIGCANCEL`** is not a signal number here (ADR-0305): the numbers 32 to 34 that musl reserves stay unused.
11. **An early return of a futex wait or a sleep is not an `EINTR`.** `thread_interrupt` makes `futex_wait` and
    `sleep_until` return early with `Ok` and the value 1 (ADR-0300 item 5); it also fires when the interrupt only
    re-routes a signal (item 3(b)) or carries a cancel (ADR-0305). So the shim's `zoraya_posix_futex`, after a
    `futex_wait` that returned the value 1, and the `nanosleep` wrapper, after a `sleep_until` that did, run delivery with
    the library lock free (item 6: the thread-pending set, then the process-pending set for signals it has unblocked, then
    the kernel's queue) and give musl one of three results. (a) A handler ran on this thread: `-EINTR`. musl's
    `__timedwait_cp` passes `EINTR` up, so `sem_wait` returns `EINTR` with a handler having run, as ADR-0106 item 6
    and INV-0106-3 require; `pthread_cond_wait` and the mutex loops treat it as a spurious wake `[read from musl 1.2.5's
    __timedwait.c; the step checks]`. (b) The thread is cancelled and cancellation is in musl's masked mode
    (`PTHREAD_CANCEL_MASKED`, which `pthread_cond_wait` expects to see as `-ECANCELED` from `__syscall_cp_c`): `-ECANCELED`,
    never `-EINTR`, because musl would re-wait with the one-shot cancel flag spent and lose the cancel (ADR-0305 item 2
    for the deferred case). (c) Nothing for this thread (the interrupt only re-routed a signal to another thread, or
    its flag was left over from an interrupt that a port packet had already served): return 0, a spurious wake, and
    musl's loop re-checks the word and waits again. A `read` or `waitpid` wrapper does the same at its own waits
    (ADR-0302 item 9): it resumes the wait in case (c) and returns `EINTR` only in case (a).

**Tensions with accepted ADRs.** *ADR-0106 item 2* ("the library's pending set, one bit per signal") becomes per process plus
per thread. *ADR-0106 item 5* (a poll at entry when a handler is installed) polls per calling thread. *ADR-0006
INV-0006-7* ("`pselect` returns `EINTR` only if a handler ran") holds for the thread that waits: a `thread_interrupt` that
only re-routes a signal makes the receiving thread poll and, if it finds nothing for it, wait again without `EINTR`;
item 11 is that rule for the futex shim, where musl's own callers (`sem_wait`, `pthread_cond_wait`) see the result.

## Consequences

- **Positive.** Programs with a signal thread (the usual pattern), with `pthread_kill`, and with per-thread masks behave as
  on Linux; make and dash are unchanged (one thread, same code paths).
- **Negative.** A request wakes every thread that subscribed; a request to a process with all threads in compute loops waits
  for the next library entry of any of them (ADR-0106's limit, per thread now). The routing makes a second
  poll.
- **Follow-up.** The signal state in `signals.rs` grows a per-thread part; the host model of ADR-0106 is extended with two
  threads.

## Invariants

- **INV-0304-1.** A process-directed request is handled by exactly one thread, and that thread had the signal unblocked, in every
  interleaving of two to four threads with random masks. *Check:* a host model test in `zoraya-posix` (`signals`) over the
  routing rule with a fake kernel queue.
- **INV-0304-2.** A signal blocked in every thread stays pending and is delivered once by the first thread that unblocks it. *Check:*
  an in-QEMU `libposix` test with two threads.
- **INV-0304-3.** A handler never runs on a thread that holds the library lock. *Check:* a `libposix` test whose handler calls
  `open`, `write` and `malloc`, installed while another thread holds a long wait; no deadlock in 1000 rounds.
- **INV-0304-4.** `pthread_kill(t, n)` on a thread blocked in `read`, `futex_wait` or `nanosleep` wakes it, and `EINTR` is returned to
  it only when a handler ran. *Check:* an in-QEMU `libposix` test with each wait.
- **INV-0304-5.** A process with no handler installed makes no `process_take_request` call and no `thread_interrupt` call outside
  the functions ADR-0106 INV-0106-2 lists, with any number of threads. *Check:* INV-0106-2's host test with the
  thread table populated.
- **INV-0304-6.** A `SIGTERM` with `SIG_DFL` ends a process whose threads all block it, with `WTERMSIG` 15. *Check:* an in-QEMU test.
- **INV-0304-7.** A `sem_wait` in a thread whose process has a handler installed does not return `EINTR` unless a handler ran
  on that thread (INV-0106-3): a `thread_interrupt` sent only to re-route a signal to another thread returns 0 from the
  shim and the wait resumes. *Check:* an in-QEMU `libposix` test: thread A in `sem_wait` with `SIGUSR1` blocked, thread B
  unblocked in a compute loop that polls, a `kill` taken by A's wake and routed to B, 1000 rounds; A's `sem_wait` never
  returns until `sem_post`.
- **INV-0304-8.** A thread in `pthread_cond_wait` or `pthread_mutex_lock` that is interrupted without a handler or cancel
  re-checks its word and waits again, and with a handler returns to its caller as musl's code defines. *Check:* an
  in-QEMU `libposix` test that counts `futex_wait` calls and handler runs for each of the two outcomes.

## Open questions

- Whether a signal thread inside the library (one thread that waits for requests and routes them) is better than the herd;
  decide when the stress test measures the herd.
- Real-time signals and `sigqueue` stay excluded (ADR-0005).

## Revisit triggers

- A measured delay of a `SIGTERM` handled by a compute-bound threaded server (ADR-0004's Option D).
- A program that relies on `SIGEV_THREAD` timers (excluded with timers).
