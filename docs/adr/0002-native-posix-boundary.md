# ADR-0002: Boundary between the native ABI and the POSIX personality

- **Status:** proposed
- **Date:** 2026-10-25
- **Depends on:** ADR-0001
- **Evidence:** CP-01, CP-02, CP-04, CP-05, CP-06, CP-07, CP-10, CP-21, CP-22, CP-25, CP-27, X-1, X-2, X-3, X-8, X-15, DM-001, DM-003, DM-005, DM-006, DM-009, DM-017, DM-019, DM-039, DM-041, DM-057, DM-085, DM-095, DM-097, GR-001, GR-003, GR-004, GR-005, GR-008, GR-018, GR-019, task-02/posix-surface.md#tiers-as-measured, task-02/posix-surface.md#libc-symbols-per-tier-m1, task-02/posix-surface.md#linux-syscall-surface-m2, task-02/posix-surface.md#absolute-paths-chosen-by-programs, task-02/callsite-analysis.md#feature-3-global-paths-path-cwd, task-02/callsite-analysis.md#feature-5-identity-and-permissions, task-02/conflict-impact.md#x-1-capability-only-access-cp-01-cp-02-vs-ease-of-posix-porting-cp-27, task-02/conflict-impact.md#x-2-no-fork-cp-05-vs-hosting-the-c-toolchain, task-02/conflict-impact.md#x-3-no-asynchronous-interruption-cp-10-vs-posix-signal-semantics, task-02/method.md#tiers-runs-and-sets, task-02b/conflict-impact.md#x-1-capability-only-access-vs-posix-porting, task-02b/conflict-impact.md#x-15-environment-as-configuration, task-02b/parallel-surface.md#new-syscalls-and-argument-patterns, alternatives-postmortem.md#qnx, alternatives-postmortem.md#fuchsia--zircon-incl-starnix, alternatives-postmortem.md#exokernel-mit-aegis--xok, alternatives-postmortem.md#keykos--eros--capros-and-coyotos, alternatives-postmortem.md#redox

## Context

The native ABI is our own design: handles, no ambient authority, explicit process construction, no asynchronous interruption (CP-01, CP-05, CP-10). POSIX exists only to host existing software, first of all a C toolchain (CP-27). This ADR decides *where POSIX lives* and *what it may ask of the kernel*. ADR-0003 to ADR-0006 refine the process, signal, scope and event parts inside this boundary.

**What is measured.**

- The POSIX surface the toolchain needs is small and bounded: tier T1 (dash, GNU make, tcc, toybox/busybox applets) calls 134 libc functions dynamically and imports at most 248 in minimal builds, 8–15 % of musl's exports; T2 (plus autoconf `configure`) is 189/291 (`task-02/posix-surface.md#libc-symbols-per-tier-m1`). Underneath, T0–T2 use 59 distinct Linux syscalls cumulatively (`task-02/posix-surface.md#linux-syscall-surface-m2`).
- The programs open global paths named in their *input* after start-up: makefiles, `#include` lines, configure scripts, `$PATH`. tcc alone opened 5,294 header paths under `/usr/include`. Relative opens outnumber absolute ones (19,007 vs 13,921). The literal paths in code are few: `/bin/sh`, `/dev/null`, `/dev/tty`, `/dev/urandom`, `/tmp`, `/etc/passwd`, `/etc/group`, `/etc/profile`, `/proc/self/exe` (`task-02/conflict-impact.md#x-1-capability-only-access-cp-01-cp-02-vs-ease-of-posix-porting-cp-27`).
- Every measured run executed in a mount namespace whose `/bin` was replaced per set, and all core workloads passed there (`task-02/method.md#tiers-runs-and-sets`; `task-02/conflict-impact.md#x-1-…`, "A per-process view of the global namespace was enough"). That is the measurement setup, not a capability-mode test, but it shows these programs tolerate a launcher-bound namespace.
- `$PATH` is resolved in user space already: 2,922 of 3,002 successful `execve` calls used an absolute path because the shells and musl's `execvp` walk `$PATH` themselves (`task-02/posix-surface.md#linux-syscall-surface-m2`).
- cwd is part of the programs' meaning: GNU make's `-C`, `CURDIR`, `$(realpath)`; dash's `cd`/`pwd` (`task-02/callsite-analysis.md#feature-3-global-paths-path-cwd`, emulate).
- Only shells fork; everything else spawns (ADR-0003). Signals in non-interactive builds are SIGCHLD only (ADR-0004). Parallel make adds one readiness call and the `MAKEFLAGS` jobserver protocol, which in the default FIFO style is a global name in `/tmp` (`task-02b/conflict-impact.md#x-1-capability-only-access-vs-posix-porting`).
- `environ` is imported by every measured program; `getenv` sites are almost all `direct`, but `MAKEFLAGS` carries fd numbers or a FIFO path that other programs read, so the environment is part of an inter-program protocol, not only configuration (`task-02/conflict-impact.md#x-15-…`, `task-02b/conflict-impact.md#x-15-environment-as-configuration`).
- Identity: the only privilege changes are set-uid drops at startup of full toybox/busybox binaries, all `direct` and removable by a config switch; root checks select behaviour; `/etc/passwd` and `/etc/group` were opened 3 times in total (`task-02/callsite-analysis.md#feature-5-identity-and-permissions`).

**What is assumed.** Nothing was measured on our kernel. Per-syscall IPC cost, the memory cost of fork emulation (X-6) and the behaviour of third-party jobserver clients are unmeasured (`task-02b/conflict-impact.md#open-questions-the-data-frames-but-cannot-answer`).

**Forces from TASK-01.** Every alternative OS that wanted real software built a compatibility layer, and its cost depended on how much POSIX state had to be shared and protected (`alternatives-postmortem.md#summary-across-systems`). The Exokernel's ExOS left the process map, fd tables, sockets, TTYs and mount table in unprotected shared memory, which "pulls much of a conventional kernel back in" (`alternatives-postmortem.md#exokernel-mit-aegis--xok`). Starnix keeps fd tables, pid allocation and AF_UNIX state in a user-space runner and names signals, futexes and inotify as its hard parts (`alternatives-postmortem.md#fuchsia--zircon-incl-starnix`). QNX shows POSIX as a library over message passing in production for 30 years (`alternatives-postmortem.md#qnx`, GR-018). KeyKOS legacy guests ran but got none of the capability benefit (`alternatives-postmortem.md#keykos--eros--capros-and-coyotos`), which is the X-1 question.

## Decision drivers

1. **The personality must not pull ambient authority back into the native ABI.** CP-01, DM-009 (confused deputy), DM-039 (path TOCTOU), DM-041 (global mount namespace). X-1 is the conflict.
2. **The measured working set of global names is small and enumerable**: the workload tree, `/usr/include`, `/usr/lib`, `/bin/sh`, `/dev/null`, `/dev/tty`, `/tmp`, two `/etc` files (`task-02/conflict-impact.md#x-1-…`, "Rules in"). A launcher can bind it.
3. **Names come from data, not code**, so a capability-only process model *without a name-resolution layer* cannot run the toolchain unmodified (`task-02/conflict-impact.md#x-1-…`, "Out"; GR-008 Capsicum tcpdump).
4. **Shared POSIX state is the hard part**: pids, process groups, sessions, the controlling terminal, `/tmp` names, and cross-process `kill` (`alternatives-postmortem.md#exokernel-mit-aegis--xok`, `#fuchsia--zircon-incl-starnix`; DM-003, DM-005, DM-070). It must live somewhere that is protected and not in each process's own memory.
5. **Only two POSIX behaviours need kernel help that native programs never use:** fork-without-exec in the shell (1,169 no-exec forks in core runs, `task-02/conflict-impact.md#x-2-…`) and, possibly, asynchronous handler execution (X-3; data shows it is only needed at wait points, ADR-0004). Everything else is library or server work.
6. **Per-call IPC cost is the risk of a server design**: DM-018 (Mach), the Starnix RFC's own warning about syscall-trapping cost and WSL1 filesystem performance (`alternatives-postmortem.md#fuchsia--zircon-incl-starnix`). 19,007 relative opens and 5,294 header opens per tcc self-build mean path resolution is the hot path (`task-02/conflict-impact.md#x-1-…`).
7. **Scope stays fixed** (CP-27). The boundary must make it visible when a new POSIX feature needs a new kernel facility.
8. **Hardware address spaces are the isolation boundary** (CP-15, GR-019). The personality cannot rely on language safety to separate POSIX processes from each other.

## Considered options

### Option A: POSIX is the kernel ABI (baseline, "do what Linux does")

- **Description:** The kernel implements POSIX process, signal, path and identity semantics natively. "Native" programs are POSIX programs. Redox is the nearest Rust precedent: a microkernel with a Unix-like scheme model and POSIX in relibc, but the kernel still has fork-shaped process semantics (`alternatives-postmortem.md#redox`).
- **Evidence for:** Zero translation cost; the toolchain, autoconf and every third-party program work as on Linux. Redox runs many POSIX programs and several COSMIC apps after ten years (`alternatives-postmortem.md#redox`). The "always a compatibility layer" pattern (`alternatives-postmortem.md#summary-across-systems`) suggests that the layer will be needed anyway, so making it the kernel saves building it twice. DM-020 and DM-026 are *contested*, so byte streams and readiness are defensible native choices.
- **Evidence against:** It imports the catalogue: fork (DM-001), fd inheritance (DM-002), pid reuse (DM-003), signals (DM-017, *mistake*), ambient authority (DM-009), path races (DM-039), global namespace (DM-041), environment (DM-085, *mistake*). It contradicts CP-01, CP-05, CP-06, CP-10 and CP-21 outright. Redox's own book says monolithic code is "just moved to user-space daemons" and self-hosting is still incomplete (`alternatives-postmortem.md#redox`). MINIX 3 competed with Linux on Linux's terms and stalled (`alternatives-postmortem.md#minix-3`).
- **Cost:** *(estimate)* Lowest compatibility cost. Highest long-term cost: every TASK-01 mistake becomes ours and permanent under CP-13/X-10. Kernel complexity of signals, process groups and sessions (DM-070) lands in the TCB.
- **Precedent:** Linux, BSDs, Redox, MINIX 3. Works for compatibility; none of them escaped the catalogue.

### Option B: Pure library personality in each process (library OS)

- **Description:** Each POSIX process links `libposix`, which maps POSIX calls onto native handles. There is no personality server. Shared POSIX state (pids, groups, `/tmp`) is either absent, replicated by convention, or kept in shared memory. Precedents: ExOS on the Exokernel, QNX's libc-over-messages for the data path (`alternatives-postmortem.md#exokernel-mit-aegis--xok`, `#qnx`), relibc on Redox.
- **Evidence for:** No IPC hop on the data path; `open`/`read`/`write`/`stat` become direct operations on handles, which matters for the 19,007 relative opens and 5,294 header opens (`task-02/conflict-impact.md#x-1-…`). QNX shows that a POSIX library over native primitives performs in production (`alternatives-postmortem.md#qnx`). Xok/ExOS ran unmodified Unix programs about as fast as BSD (`alternatives-postmortem.md#exokernel-mit-aegis--xok`). Most of the 663 M3 call sites are `direct` (`task-02/callsite-analysis.md#overview`), which is library work.
- **Evidence against:** ExOS's unsolved problem was exactly the shared state: process map, fd tables, TTYs, mount table in unprotected shared memory (`alternatives-postmortem.md#exokernel-mit-aegis--xok`). The toolchain needs that state: `kill(pid)`, `getpid()` in `MAKEFLAGS`, process groups for Ctrl-C (`task-02b/event-timelines.md#w9a-ctrl-c-run-w9-int-d15-r1`), `/tmp/GMfifo<pid>` opened by name from sibling processes (`task-02b/parallel-surface.md#new-syscalls-and-argument-patterns`). A pure library has no protected place for a pid table or a FIFO namespace. Mutually distrusting POSIX processes would share writable tables, which CP-15 forbids.
- **Cost:** *(estimate)* Lowest per-call cost. The shared-state problem either forces a server back in (Option D) or weakens isolation between POSIX processes.
- **Precedent:** Exokernel (research; the shared-state fix was never built), QNX (library plus resource managers, which is in fact a hybrid), Redox relibc (over a kernel that already has Unix process semantics).

### Option C: User-space personality server (Starnix-style)

- **Description:** One personality server per session (or per machine) owns all POSIX state and mediates every POSIX syscall. Client processes trap or message into it. Starnix translates Linux syscalls into Fuchsia protocol messages and keeps fd tables, pid allocation and AF_UNIX state itself (`alternatives-postmortem.md#fuchsia--zircon-incl-starnix`).
- **Evidence for:** All shared state is in one protected place, which solves Option B's problem and matches CP-15. Unmodified binaries run; Starnix exists because source-level "POSIX Lite" was not enough for important software (`alternatives-postmortem.md#fuchsia--zircon-incl-starnix`). The personality can be restarted or replaced as a component (CP-17). Signals, process groups and the controlling terminal are naturally implemented where the pid table is.
- **Evidence against:** Per-syscall cost. The Starnix RFC expected its first syscall-trapping design to be too slow and cited WSL1's filesystem performance as a warning; five years later the release notes still list syscall and clock performance work (`alternatives-postmortem.md#fuchsia--zircon-incl-starnix`). Mach's user-level Unix server is the historical case of services moving back into the kernel for the same reason (DM-018). Our hot path is path resolution and file I/O during compiles. A server also concentrates a large trusted component, as X11 and win32k did for the GUI (DM-079, DM-081).
- **Cost:** *(estimate)* Highest per-call cost unless the data path bypasses the server. Highest fidelity. Moderate implementation size, concentrated in one component. Whether Starnix is fast enough in any product is unverified (`research-log.md#unresolved-questions`).
- **Precedent:** Starnix (active, performance work ongoing), Mach's Unix server (abandoned for co-location), MINIX 3's PM/VFS servers (POSIX implemented by two servers, which could not be restarted; `alternatives-postmortem.md#minix-3`).

### Option D: Library for the data path, a session broker for shared POSIX state, and two capability-gated kernel facilities (combination)

- **Description:**
  - **`libposix` in each POSIX process** implements files, directories, pipes, memory, stdio, time, locale, environment, cwd, `$PATH` search and `posix_spawn` directly on native handles. The fd table is library state: an fd is an index into a table of native handles (GR-001 is the model being emulated).
  - **A per-session POSIX broker** (an ordinary user-space component) owns the POSIX *global namespaces*: the pid table (pid ↔ process handle), process groups and sessions, the controlling terminal and foreground group, the session's `/tmp`, and the name-to-object table for FIFOs and other named POSIX objects. `kill`, `getpgrp`, `setpgid`, `tcsetpgrp`, `waitpid(-1)` on non-children and `mkfifo` go through the broker. The broker is on the control path only, never on `read`/`write`/`open` of ordinary files.
  - **A per-process namespace table** (Plan 9 / Fuchsia style, GR-004, DM-006 "Fuchsia has no global root"), constructed by the launcher: a list of (path prefix → directory or object handle) entries. `libposix` resolves every path against it, lexically, with `..` handled in the library as Fuchsia does. `/` is the table, not a kernel object.
  - **Two kernel facilities reserved for the personality**, each enabled by a job policy bit that native jobs do not get: (1) copy-on-write address-space snapshot for `fork` emulation (ADR-0003); (2) nothing else is required by the data today. Asynchronous thread interruption is *not* included; ADR-0004 shows the measured signal uses are all at wait points. It is listed as a revisit trigger.
  - **Native-visible process facts the personality relies on but that are native anyway:** exit records with a reason field on the process object (CP-06, ADR-0004), job trees with group interrupt and kill (CP-07, ADR-0004), a waitable port (ADR-0006).
- **Evidence for:** It follows the measured split. Data-path calls are the volume (opens, reads); control-path calls are rare (15 `TIOCSPGRP`, a handful of `kill`, `setpgid` only in W5/W9: `task-02/posix-surface.md#linux-syscall-surface-m2`, `task-02b/parallel-surface.md#new-syscalls-and-argument-patterns`). The shared state that ExOS could not protect is exactly the broker's content, and it is small. QNX is this shape: libc in the process, resource managers for shared objects (`alternatives-postmortem.md#qnx`). The namespace table matches "a POSIX personality that resolves global names inside a per-process namespace constructed by its launcher" which the data rules in (`task-02/conflict-impact.md#x-1-…`). `$PATH` already resolves in user space (driver 3). Keeping fork emulation behind a job policy bit keeps CP-05 intact for native code and makes X-2's cost visible as one facility.
- **Evidence against:** It is three things instead of one, so the boundary is more surface to specify. Any POSIX feature that needs cross-process state the broker does not have becomes a new broker protocol (scope pressure, CP-27). Whether the capability benefit survives inside the personality once it has the namespace is the unanswered KeyKOS question (`task-02/conflict-impact.md#x-1-…`, Unknown). The pid table in a broker makes `kill` an IPC round trip and reintroduces DM-003's race *inside the personality* (pid reuse), which must be managed by the broker holding the process handle (CP-06) and never reusing a pid while any POSIX process in the session could still name it.
- **Cost:** *(estimate)* Library: the bulk of the 134–291 functions, mostly thin. Broker: a few thousand lines `[assumption]`, one IPC round trip per control-path call. Namespace table: resolution in the library, lexical; cost per `open` is a prefix match plus one handle-relative open. Kernel: one CoW snapshot facility plus the job policy bit. Compatibility: everything in T0–T2 that is `direct` or `emulate` in M3 is covered; `restructure` sites are program patches, not personality work.
- **Precedent:** QNX (production, 30 years), Fuchsia's fdio plus Starnix (the fdio part is the library; Starnix adds the server for binary compatibility), Plan 9 namespaces (ideas adopted widely).

## Recommendation

**Recommendation (not a decision): Option D**, with the following boundary definitions. Each is a rule the other ADRs build on.

1. **Where POSIX lives.** Files, pipes, memory, stdio, time, locale, environment, cwd, `$PATH` search, `posix_spawn`, non-blocking I/O and readiness waits are implemented by `libposix` in the process, on native handles. Pids, process groups, sessions, the controlling terminal, `/tmp` naming and named POSIX objects live in a per-session POSIX broker. Nothing POSIX-specific lives in the kernel except the facilities in rule 3.
2. **How a POSIX process is identified.** A POSIX process is a native process whose job has the `posix` policy bit and whose startup handles include a broker channel and a namespace table. The broker assigns its pid when it is created through the broker's spawn protocol; a POSIX process spawned directly by a native program without the broker has no pid and cannot be the target of `kill`. (This is the analogue of Fuchsia's launcher supplying startup handles, GR-005, DM-002.)
3. **Kernel facilities the personality may require and native programs never see.** (a) Copy-on-write snapshot of a process's address space into a new process in the same job, including the calling thread's register state, gated by the job's `posix` policy bit (ADR-0003). (b) None other is justified by the measurements. In particular there is no asynchronous thread interruption (CP-10 holds natively; ADR-0004) and no kernel pid table (CP-06). Any new facility requires a superseding ADR and must be gated the same way.
4. **How POSIX and native processes interact.** *Files and pipes:* both hold native handles to the same filesystem and pipe objects; a POSIX fd is an index into `libposix`'s handle table; passing a file from native to POSIX code is passing the handle at spawn (startup handle at a numbered fd slot) or over a channel. *Process handles:* a native parent that spawns a POSIX child through the broker receives the child's process handle and reads its exit record like any native child's; the exit record's reason/detail fields carry "terminated by signal N" (ADR-0004). A POSIX parent waiting for a native child sees it as a pid only if the broker registered it. *Byte streams:* native byte-stream objects are what `pipe()` returns; the native IPC primitive may carry handles and framing (GR-002), but `libposix` exposes only the byte view.
5. **How POSIX global namespaces map onto handles.** `/` is the per-process namespace table of (prefix → handle), built by the launcher from what it holds; for the toolchain the table is the measured working set (`/`-rooted workload tree, `/usr/include`, `/usr/lib`, `/bin` with `sh`, `/dev/null`, `/dev/tty`, `/tmp`, `/etc/passwd`, `/etc/group`). `/tmp` is a directory handle to a per-session temporary directory owned by the broker. `$PATH` stays an environment string; `libposix` resolves it against the table exactly as shells already do. `/dev/tty` is the session terminal handle entry (CP-25). `/dev/null` is a null object entry. `/proc/self/exe` is answered by `libposix` from the process's own image handle. cwd is `libposix` state: a directory handle plus the canonical path by which it was reached through the table, so that `getcwd`, `realpath` and `CURDIR` return strings (answering the X-1 unknown by construction, not by measurement). Names are UTF-8 at the native boundary (CP-22); how `libposix` maps POSIX byte names that are not valid UTF-8 is an open question (X-8), unmeasured.
6. **Identity.** There is no uid/gid in the native ABI (CP-03). `libposix` reports a fixed per-session identity for `getuid`/`geteuid` (never 0, so root checks take the unprivileged path), and `/etc/passwd` and `/etc/group` are ordinary files in the namespace for `getpw*`/`getgr*`. `setuid`/`setgid` fail. This matches the data: all privilege changes were `direct`, no-op drops (`task-02/callsite-analysis.md#feature-5-identity-and-permissions`). File modes are stored and reported by the filesystem service as POSIX metadata; the personality does not enforce them against the identity, the handle's rights do (CP-02). *Conflict noted:* this violates nothing in CP but it means `chmod` is advisory for native code, which the architect should know.
7. **Environment.** `libposix` provides `environ` from the explicit environment vector passed at spawn (CP-21, X-15). `MAKEFLAGS` fd numbers work because the broker's spawn protocol places handles at requested fd slots; `MAKEFLAGS` FIFO paths work because `/tmp` is shared within the session.

Why D over C: per-call cost on the data path is the documented failure mode of server personalities (DM-018, Starnix's own warning), and the data shows the data path is where the volume is. Why D over B: the data also shows the shared state cannot be avoided (process groups for Ctrl-C, pids in `MAKEFLAGS`, FIFO names), and ExOS shows what happens when it is left unprotected. Why D over A: A contradicts five candidate principles and makes the TASK-01 catalogue permanent under CP-13.

**Principles this recommendation strains.** CP-01 (no ambient authority) is kept for the native ABI but the personality's namespace table is, from the POSIX program's view, ambient: anything in the table can be opened by name. That is the X-1 tradeoff accepted deliberately, bounded by the table's contents. CP-05 (no fork) is kept natively and relaxed for `posix` jobs by rule 3(a); that is X-2 accepted deliberately for one program class.

## Consequences

- **Positive.** The native ABI stays free of pids, signals, global paths and fork. The personality's needs are visible as one kernel facility and one broker. Data-path performance is library-direct. The measured working set gives the launcher's namespace table a concrete default.
- **Negative.** Three components to specify and keep consistent (library, broker, kernel policy bit). The broker is a session-wide trusted component for POSIX processes. `kill` and process-group operations cost an IPC round trip (rare in the data, but unmeasured on our kernel). Pid reuse becomes a broker policy rather than a kernel guarantee.
- **Follow-up work.** ADR-0003 (spawn and fork), ADR-0004 (events and signals), ADR-0005 (scope), ADR-0006 (wait primitive). A broker protocol specification. A namespace-table format in the `abi` crate. A measurement of path-resolution cost through a prefix table on the prototype. A decision on byte names vs UTF-8 (X-8).

## Invariants

- **INV-0002-1.** No native syscall takes a pid, uid, gid, signal number or absolute path string as an argument. *Check:* a lint over the `abi` crate's syscall argument types; the types `Pid`, `Uid`, `Gid`, `Signal` and `AbsolutePath` do not exist in `abi`.
- **INV-0002-2.** Every kernel facility that is usable only by `posix` jobs is tagged in the `abi` crate with a `#[personality_only]` attribute, and the kernel rejects it with a permission error for jobs without the policy bit. *Check:* an `abi` lint that the attribute set equals the list in this ADR (currently one entry), and a kernel test that calls each tagged facility from a non-`posix` job and expects the error.
- **INV-0002-3.** `libposix` performs no IPC to the broker on the `open`, `read`, `write`, `close`, `stat`, `lseek`, `mmap` or `pipe` paths. *Check:* a test that runs a file-only workload under a tracing broker and asserts zero broker messages.
- **INV-0002-4.** Path resolution in `libposix` never escapes a namespace-table entry: `..` at an entry's root resolves to the entry's root. *Check:* a unit test over the resolver with adversarial paths.
- **INV-0002-5.** A POSIX process's startup handle set contains exactly the handles listed in the namespace table plus the broker channel plus numbered fd slots; nothing else is inherited. *Check:* a test that spawns a POSIX process through the broker and enumerates its handles.
- **INV-0002-6.** The native process exit record has a reason field distinct from the exit code, and `libposix` maps `WIFSIGNALED` from it, never from the code. *Check:* a type in `abi` (`ExitRecord { code, reason, detail }`) and a round-trip test through `waitpid`.

## Open questions

- Path-resolution cost of a prefix table in the library on our kernel: prototype measurement on W1 (5,294 header opens).
- Memory cost of fork emulation under strict commit (X-6): measure dash RSS at fork points in W4 (unmeasured; `task-02/conflict-impact.md#x-6-…`).
- Byte names that are not UTF-8 (X-8): no workload exercised them. Research: what do archives in the toolchain's inputs contain?
- Whether third-party jobserver clients (ninja, cargo) accept both jobserver styles, and so whether `/tmp` FIFOs must be supported or pipe style suffices (`task-02b/conflict-impact.md#x-1-…`, Not shown).
- Does the broker need to be per session, per user, or per machine? Nothing in the data distinguishes these; the per-session choice follows from the controlling terminal being per session (DM-070).

## Revisit triggers

- A measured T1/T2 workload needs a kernel facility beyond rule 3(a): reopen rule 3 with a superseding ADR.
- Path resolution through the namespace table is measured to cost more than a small fraction of W1 run time `[assumption: threshold to be set by the architect]`.
- A required program (ADR-0005 scope) needs asynchronous handler execution outside wait points (ADR-0004 revisit trigger).
- The broker becomes a bottleneck or a large trusted component: reconsider Option C's full-server shape or splitting the broker.

## Architect's decision
