# ADR-0161: The design system and its tokens

- **Status:** accepted
- **Date:** 2026-11-03
- **Depends on:** ADR-0052, ADR-0093, ADR-0095, ADR-0160, ADR-0162, ADR-0164
- **Evidence:** CP-21, CP-23, DM-086, DM-087, alternatives-postmortem.md#haiku--beos, desktop/survey.md#macos-and-apples-human-interface-guidelines, desktop/survey.md#gnomes-hig-and-libadwaita, desktop/survey.md#what-makes-a-desktop-coherent, desktop/survey.md#design-tokens-and-motion, desktop/survey.md#hinting-and-antialiasing

## Context
"Beautiful in the macOS sense" is the architect's direction: one design system applied everywhere, good typography, calm and consistent visuals, smooth motion. Stage 5 has one colour for the background, one for the frame, one bitmap font and no spacing rules. Stage 7 adds frames (ADR-0160), a toolkit (ADR-0165), several applications (ADR-0168) and a scale factor (ADR-0164). Every coherent desktop in the survey has three things in common (`desktop/survey.md#what-makes-a-desktop-coherent`): one type scale with named styles, one colour vocabulary with light and dark values and semantic names, and rules written down to the character. Apple's text styles are a fixed table of weight, size and line height, its colours are semantic and adapt to appearance, and its guidance is "avoid hard-coding system color values" (`desktop/survey.md#macos-and-apples-human-interface-guidelines`). GNOME's libadwaita names every colour once in a stylesheet and tells applications to reuse those names, with light and dark values side by side; its palette is five steps per hue (`desktop/survey.md#gnomes-hig-and-libadwaita`). Haiku's rule is "control labels should always be in the system plain font and size" (`alternatives-postmortem.md#haiku--beos`). The Design Tokens Community Group's format names what such a vocabulary contains: colour, dimension, font family and weight, duration, cubic Bézier, number, and composites for typography and shadows (`desktop/survey.md#design-tokens-and-motion`).

The architect decides visual questions by looking, so this ADR fixes the *shape* of the system (what the tokens are, where they live, how code uses them) and leaves the *values* to the mockups in `docs/research/desktop/mockups/`, whose three directions, the second version of mist made from the architect's breakdown of the first, and the three variants of the "Clear boundaries" concept (ADR-0172) were seven token files of the same shape; after the architect's choice one remains in the tree, `clear-field/tokens.txt`, and the others are in the branch's history (the mockup README names the commit). Measured: nothing on Zoraya. Assumed: the values in the mockups' token files.

## Decision drivers
1. Every component takes every colour, size, radius, shadow and duration from one place; nothing is hard-coded (CP-21 for configuration applied to appearance; `desktop/survey.md#macos-and-apples-human-interface-guidelines`).
2. Light and dark are two value sets of one vocabulary, switchable at run time (`desktop/survey.md#gnomes-hig-and-libadwaita`).
3. Values are data a person can read and change in one file, typed and checked (CP-23, against DM-086's opaque store and DM-087's unchecked text).
4. The mockup tool and the implementation read the same data, so what the architect approved is what ships.
5. Deterministic rendering stays possible: no token implies a blur, a gradient or an animation that a screendump test cannot reproduce exactly (ADR-0095 driver 3).
6. Small: a tokens crate of a few hundred lines, no external format.

## Considered options

### Option A: A stylesheet per toolkit, CSS-like, loaded at run time (GTK and Qt on Linux)
- **Description:** Each toolkit reads a stylesheet in its own language (GTK CSS, Qt style sheets) with selectors over widget classes; themes are files a person installs.
- **Evidence for:** Flexible; themes without recompiling; the GNOME vocabulary is in exactly such a stylesheet (`desktop/survey.md#gnomes-hig-and-libadwaita`).
- **Evidence against:** A CSS parser and a cascade are a large hostile-input surface in every client; two toolkits give two stylesheet languages, which is how Linux desktops diverge (`desktop/survey.md#what-makes-a-desktop-coherent`); selectors invite per-widget exceptions that break driver 1.
- **Cost:** *(estimate)* A few thousand lines for a parser and cascade.
- **Precedent:** GTK, Qt.

### Option B: Constants in each component's source (the stage 5 way, and Haiku's early look)
- **Description:** Each crate names its colours and sizes as constants in Rust.
- **Evidence for:** Nothing to build; the compiler checks types.
- **Evidence against:** Driver 1 fails on the second crate; light and dark need a second set of constants in every crate; the architect cannot change a value without reading Rust.
- **Cost:** None now, a redesign later.
- **Precedent:** `zoraya-compositor` and `zoraya-term` today.

### Option C: One tokens crate built from one data file, light and dark side by side
- **Description:** `zoraya-tokens`, `no_std`, `#![forbid(unsafe_code)]`, no dependencies, includes `tokens.txt` at compile time and parses it with a `const fn` into typed tables (as `zoraya-font` parses its glyphs). The file holds every token of the vocabulary below, with a light and a dark value for each colour. Every GUI crate takes a `&Theme` and reads tokens by name; the compositor, the toolkit, the terminal and the mockup tool read the same file. Semantic names in the manner of Apple and libadwaita (`desktop/survey.md#macos-and-apples-human-interface-guidelines`, `desktop/survey.md#gnomes-hig-and-libadwaita`).
- **Evidence for:** Drivers 1 to 6. A `const` parse fails the build on a bad value (driver 3). The direction the architect chooses is a file, and changing a value later is editing one line.
- **Evidence against:** A second theme at run time means a second file compiled in (light and dark are in one; a person's own theme needs ADR-0169's setting to pick between compiled sets, or a run-time parser later). Everything is in logical pixels, so a token cannot express a per-display value.
- **Cost:** *(estimate)* 300 lines of parser and tables, 150 lines of data.
- **Precedent:** The DTCG format's model of tokens (`desktop/survey.md#design-tokens-and-motion`); libadwaita's named colours; ADR-0095's compile-time glyph tables.

### Option D: A fixed system look with no vocabulary (BeOS, classic Mac OS)
- **Description:** The system draws every control one way from code; applications have no say, and there is one appearance.
- **Evidence for:** Maximal consistency; nothing to configure (`alternatives-postmortem.md#haiku--beos`).
- **Evidence against:** Dark mode and scale (driver 2, ADR-0164) are then code changes; Haiku itself grew an Appearance panel.
- **Cost:** *(estimate)* Smallest until the first second appearance.
- **Precedent:** BeOS.

## Recommendation

### Decision

Accepted with a change (architect, 2026-11-03): the vocabulary gains `room.untrusted.edge`, the width of the edge in `room.untrusted` that the compositor draws on every window of an untrusted room, field or no field (ADR-0172 point 6, INV-0172-10); the mockup file sets it to 2. The recommendation below is otherwise as accepted.

Recommended: **Option C**. It is a recommendation, not a decision. The values are the architect's choice among the mockup directions; the vocabulary is:

The vocabulary is exactly the set of names the mockup file defines (`docs/research/desktop/mockups/clear-field/tokens.txt`, checked by the mockup tool's test; the six deleted files defined the same names but `room.untrusted.edge`); listed here by group:

- **Identity and fonts**: `name`, `appearance` (which set a direction is shown in), `font.ui`, `font.ui.medium`, `font.mono`, `font.mono.bold` (the font files, ADR-0162).
- **Colours** (each with a `light:` and a `dark:` value, `#rrggbb`): `wallpaper.a`, `wallpaper.b`, `wallpaper.c`, `wallpaper.d` (the procedural wallpaper, below), `room.1` to `room.4` and `room.untrusted` (ADR-0172's rooms: under the rule "colour means a room" these are the only saturated colours of a `clear` direction, INV-0161-5), `glow` (the light of the trusted material, below), `bg.desktop`, `bg.window`, `bg.view` (text fields, lists), `bg.panel`, `bg.frame`, `bg.frame.focused`, `bg.frame.system` (ADR-0160's trusted tint), `bg.control`, `bg.control.hover`, `bg.control.pressed`, `bg.selection`, `bg.overlay` (the switcher), `fg.text`, `fg.text.secondary`, `fg.text.disabled`, `fg.text.on-accent`, `fg.text.on-selection`, `accent`, `border`, `border.strong`, `shadow`, `success`, `warning`, `error`, `button.close`, `button.minimise`, and the terminal's `term.bg`, `term.fg` and its eight colours `term.black` to `term.white` (the bright eight are derived by the terminal until a direction wants them as tokens).
- **Type scale** (logical pixels): `text.caption 11`, `text.body 13`, `text.heading 15`, `text.title 17`, `text.large 22`, `text.mono 13` `[assumption, Apple's and GNOME's scales are the model; the quiet direction uses 12]`; line heights come from the font's metrics; `text.body` is the control label size everywhere, as Haiku's rule says.
- **Spacing and shape**: `space.unit 4` (every gap and padding is a multiple of it), `padding.control`, `padding.window`, `padding.terminal` (the terminal's inset, larger in the second mist), `gap.controls`, `control.height`, `radius.control`, `radius.window`, `radius.popup`, `radius.shape` (`circle`: a quarter circle; `smooth`: a continuous corner, a superellipse of exponent 2.9 spanning 1.6 radii so that the curve runs into the straight edge without a visible kink, the same on all four corners, as the second mist shows), `frame.height`, `frame.border`, `frame.border.focused` (`accent` or `none`, ADR-0160), `frame.separator` (`yes` or `no`), `frame.grip`, `frame.buttons` (`circles`, `squares` or `glyphs`: a cross and a dash, coloured on the focused window and on hover, grey elsewhere), `panel.height`, `panel.position`, `desktop.layout` (`taskbar`: one bar at the bottom; `dock`: a thin top bar of `bar.height` and a floating dock of `dock.icon`-pixel icons with `dock.padding` and `dock.radius`, ADR-0168), `chooser.style` (`window` or `sheet`, ADR-0167), `settings.style` (`plain` or `cards`, ADR-0168), `concept` (`classic` or `clear`: which set of screens the mockup tool draws) with `screens` (their names, in order), `room.style` (`none`, `edge`, `band` or `ground`: how a window carries its room's colour, ADR-0160) with `room.edge` (the edge's width) and `room.untrusted.edge` (the width of the edge in `room.untrusted` that every window of an untrusted room carries in every `room.style`, ADR-0172 point 6, INV-0172-10), `field.padding` and `field.gap` (ADR-0172's fields: how far a field extends past a room's windows, and the least distance between two fields and from the bar's and the dock's strips), `room.hue-distance` (degrees of hue: no trusted room colour lies within it of `room.untrusted`, INV-0161-6), `screens.2x` (which screens the mockup tool renders at scale 2). The architect chose the `clear-field` file on 2026-11-03 (the Field variant, dock B); it is the reference for `tokens.txt`, and the dock it describes is: icons on tiles of neutral material (`bg.control` towards `glow` and towards `border` or `shadow`, an inner light and an inner shadow of one pixel, a `border` edge, `radius.control × 2` corners, the glyph embossed), one dot per room under a running application in the room's colour, the untrusted application ringed in `room.untrusted`, a divider, then the rooms as chips (the current one filled with its colour at a low alpha) and `+`; the icon cells are equal, the chips as wide as their text; a hovered icon's name and line in a tooltip of the trusted material over the dock, which never changes its height or cells for a hover; in the show-commands mode a line under every icon and chip, and only then does the dock grow (ADR-0168).
- **Shadows**: `shadow.window.blur`, `shadow.window.offset`, `shadow.window.alpha` and the same three for `shadow.popup`, with the `shadow` colour; `shadow.window.layers` (1 to 3) draws the window shadow as that many shadows at a growing fraction of the blur and offset, each with a fraction of the alpha, which is how a large shadow stays soft near the window; `shadow.window.unfocused.alpha` is the alpha of an unfocused window's shadow (ADR-0160's focus signal when the border is not it); a blur is drawn by the compositor with a fixed integer kernel so that it is deterministic (driver 5), and a blur of `0` turns it off (the quiet direction).
- **Wallpaper and translucency**: `wallpaper` is `flat` (the desktop is `bg.desktop`) or `gradient`: the compositor computes the wallpaper itself from `wallpaper.a`, `.b` and `.c`, a diagonal gradient with two soft blobs, pure arithmetic per pixel (the mockup tool's `scene::wallpaper` is the reference), so that there is no image file, no decoder and nothing foreign. `blur.panel` and `panel.alpha` give the translucent bar, dock and switcher of ADR-0160 and ADR-0168: the compositor keeps a *blurred copy* of the wallpaper, computed once whenever the wallpaper changes (at start, on a theme change, on a scale change), never per frame: three box passes per channel of radius `blur.panel / 3` with the edge pixels repeated, in integer arithmetic (deterministic, driver 5). Drawing a bar is then one read of the blurred copy and one blend with `bg.panel` at `panel.alpha` per pixel, the cost of a solid panel. *Measured* in the mockup tool's `blur_cost` test on the architect's M4, one thread, release build, 2026-11-03: 32 ms for 1024 × 768 at radius 24, 185 ms for 2048 × 1536 at radius 48. The same arithmetic in the compositor under QEMU's TCG is slower by a factor the first stage 7 task measures; being once per change it may cost a second at scale 2 without a visible effect, while the memory is one more framebuffer (3 MiB at scale 1, 12 MiB at scale 2, four bytes per pixel). A direction with `wallpaper = flat` needs no copy: a bar over a flat colour is a blend with that colour. `wallpaper = deep` is the `clear` directions' wallpaper: the diagonal gradient, four blobs (`wallpaper.c`, `wallpaper.d`, a darker `.a`, a lighter `.b`), a faint fold and a vignette (the tool's `wallpaper_deep`); `rooms` is `deep` with the rooms drawn as fields in their colours around their windows under ADR-0172 point 5 (only between rooms, the union of the padded windows clipped to the work area, cut back from each other by `field.gap`, recomputed at every commit of a move), which the compositor draws into the wallpaper's copy when rooms or their windows change, one signed-distance pass over the field's bounding box.
- **The trusted material** (ADR-0172's "glow means trust"; ADR-0160 says where it is used): `glow.alpha` (the inner light: a band from the top edge of a third of the height, at most 48 pixels, from half the alpha to nothing, and a one-pixel rim inside the edge at the alpha), `glow.halo` and `glow.blur` (a halo around the surface, the shadow's drawing with the `glow` colour and no offset), over the glass (a blur of what is under the surface at `blur.panel`, tinted with `bg.overlay` at `panel.alpha`). Every part is deterministic integer arithmetic (driver 5). *Measured* in the mockup tool's `glow_cost` test on the architect's M4, one thread, release build, 2026-11-03, for a 640 × 372 logical surface (the switcher's) over a wallpaper, blur radius 36, halo blur 22: at scale 1 the blur of the region under it (364 thousand physical pixels, the surface plus the blur's margin) takes 11.5 ms, the halo 2.0 ms and the inner light 0.3 ms; at scale 2 (1.46 million pixels) 40 ms, 9 ms and 1.2 ms. The blur is the cost, and it is paid when the surface opens and when something under it commits, not per frame: a surface that stays while nothing under it changes is a copy. The halo and the rim are the surface's own shape and are cached per size. So the material costs about one window's worth of compose time per open under the host; under QEMU's TCG the factor is the one the first stage 7 task measures for the wallpaper blur, and the same remedy applies: a direction with `glow.blur = 0` and `blur.panel = 0` draws the tint alone.
- **Motion**: `motion.short 100`, `motion.medium 200`, `motion.long 300` (milliseconds) and two curves `ease.standard 0.2 0 0 1` and `ease.decelerate 0 0 0 1` `[assumption; Material's published values, desktop/survey.md#design-tokens-and-motion]`, used for the switcher, minimise and popups; `0` durations (the quiet direction) and `gui.motion = no` (ADR-0169) disable all of them, which is also what the screendump tests run with.
- **Icons** are not tokens but a rule: symbolic, monochrome, drawn on a 16-pixel grid with 2-pixel strokes, recoloured from `fg.*` tokens, at 16 and 32 logical pixels only; named icons live in `zoraya-icons` as paths rasterised by ADR-0162's rasteriser (the same scan-line code draws glyph outlines and icon outlines). The mockups' panel icons are hand-drawn illustrations and do not follow this rule.
- **The file**: `crates/zoraya-tokens/tokens.txt`, one token per line, `name = value`, with `light:` and `dark:` prefixes for colours; comments with `#`. It is the chosen direction's file, and the mockup tool reads the same format with its own small parser, so the two cannot drift: a host test parses every file in `docs/research/desktop/mockups/` with both parsers and compares the token sets with the vocabulary above.
- **Antialiasing**: text and icons are drawn with 8-bit coverage and no hinting (`desktop/survey.md#hinting-and-antialiasing`); the tokens choose nothing else about rendering.

**Tensions with accepted ADRs.** *ADR-0095*: text drawn with coverage is not "either the text colour or the background", so the GUI test's exact glyph match changes: the terminal keeps a monospace grid and the runner matches each cell against the glyph bitmaps rendered by the same crate at the same size, still exactly, since rendering is deterministic (ADR-0162). *ADR-0093*'s background and frame colours become tokens.

### Effect of the vision
None on the choice. Target 2 needs `bg.frame.system` to distinguish windows of trusted programs, which is a token here. Target 3 wants person-installed themes, which is a run-time parser over the same file format at a later cost of a few hundred lines. Networking and threads: none.

### Deferred to stage 6
Nothing here depends on POSIX. A POSIX program's output appears in the terminal, which draws it with these tokens.

## Consequences
- **Positive.** One file decides the look; light and dark are one switch; the mockups and the implementation cannot disagree.
- **Negative.** Every GUI crate takes a theme parameter; a person's own theme waits for a run-time parser.
- **Follow-up.** `zoraya-tokens`, `zoraya-icons`, the mockup README's token tables moved into `tokens.txt` once the architect chooses; the wallpaper and blur code moved from the mockup tool into the compositor's crate once a direction with them is chosen.

## Invariants
- **INV-0161-1.** No GUI crate (`zoraya-compositor`, `zoraya-term`, `zoraya-ui`, the applications) contains a colour literal or a duration literal, and every logical size it draws with is a `Logical` value, a newtype whose constructors are private to `zoraya-tokens` and whose arithmetic keeps the type. *Check:* a host script run by `make test` that greps those crates for `0x[0-9a-fA-F]{6}` colour literals and for `Duration::from_millis` outside the tokens crate, with an allow-list only for test files; the compiler enforces the `Logical` rule, since a bare integer cannot become a `Logical` outside the tokens crate.
- **INV-0161-2.** The light and dark sets define exactly the same token names, and every token the code names exists in the file. *Check:* a host test of the `const` parser over `tokens.txt` and over every direction file under `docs/research/desktop/mockups/`, plus the compile-time failure of a missing name.
- **INV-0161-3.** Every text foreground on its background meets a contrast ratio of at least 4.5 to 1 in both sets, the backgrounds the compositor composes included (a field's header, a tinted title bar, a chip over the material, the tooltip; the mockup README's table, printed by the tool's `clear_field_text_contrast` test) (`fg.text` on `bg.window`, `bg.view`, `bg.control`; `fg.text.on-accent` on `accent`; `fg.text.on-selection` on `bg.selection`). *Check:* a host test computing the WCAG relative-luminance ratio from the token values `[outside evidence: WCAG 2.1 contrast formula]`.
- **INV-0161-6.** No trusted room colour (`room.1` to `room.4`) lies within `room.hue-distance` degrees of HSL hue of `room.untrusted`, in either set: the untrusted hue is reserved. *Check:* the mockup tool's test over every `concept = clear` file (`direction_files_are_complete_and_readable`); the same test over `tokens.txt`.
- **INV-0161-5.** In a `clear` direction no colour token outside `room.*`, `button.*`, `term.*`, `success`, `warning` and `error` has a saturation above 0.4 (HSL), in either set: colour means a room. *Check:* the mockup tool's test over every `concept = clear` file; the same test over `tokens.txt` once a `clear` direction is chosen.
- **INV-0161-4.** Rendering with the tokens is deterministic: two renders of the same scene at the same scale give identical bytes, on the host and in QEMU. *Check:* a host test rendering a scene with `zoraya-ui` and `zoraya-text` twice and comparing, on the host and in the test kernel; the GUI screendump test comparing two dumps of an idle desktop. (The mockup tool shows the same coverage model in `f32`; its own reproducibility is a fact about the tool, not this invariant.)

## Open questions
- The values: decided by the architect from the mockups.
- Whether 4.5 to 1 is the right contrast bound for the dark direction's secondary text.
- Whether the shadow blur is worth its compose cost under TCG: measured by the first stage 7 task; the same for the one-time wallpaper blur, whose host cost is above.

## Revisit triggers
- A person-installed theme: a run-time parser.
- A second display with a different density (ADR-0164).

## Architect's decision

Accepted 2026-11-03, with one change: the token `room.untrusted.edge`, the README's reserved two-pixel
untrusted edge, is adopted. The compositor draws it on every window of an untrusted room, also when no field
is drawn (one room on screen, a maximised window); no trusted room colour may produce it (ADR-0172 point 6,
INV-0172-10). Decided by the architect; recorded by an agent at the architect's request.
