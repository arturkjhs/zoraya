# ADR-0172: Rooms: named sets of grants that programs run in, shown by the compositor

- **Status:** accepted
- **Date:** 2026-11-03
- **Depends on:** ADR-0002, ADR-0003, ADR-0046, ADR-0053, ADR-0055, ADR-0097, ADR-0107, ADR-0150, ADR-0153, ADR-0155, ADR-0156, ADR-0157, ADR-0160, ADR-0161, ADR-0167, ADR-0168, ADR-0169, ADR-0170, ADR-0171
- **Evidence:** CP-01, CP-02, CP-05, CP-07, CP-23, CP-24, CP-28, X-1, DM-009, DM-079, GR-016, desktop/survey.md#capdesk-and-e, desktop/survey.md#polaris, desktop/survey.md#spoofing-and-the-trusted-path, desktop/survey.md#eross-trusted-window-system, shell/survey.md#capability-shells-and-grant-syntax, alternatives-postmortem.md#genode, alternatives-postmortem.md#plan-9--inferno

## Context
The architect's concept for stage 7, "Clear boundaries", asks the interface to show what other systems hide: who has access to what. Four rules follow, and this ADR gives them their object. *Colour means a room*: saturated colour is used for rooms only; everything else is neutral. *Glow means trust*: one material, light through blurred glass, is drawn only by the compositor, for the chooser, the handing out of grants, the switcher and the system bar, and no application can draw it. *Everything has its text*: every element and gesture has a form in `zosh`, the grants on a window are written in ADR-0153's syntax (`+r ~/project`, `+w notes.txt`), a drop shows what it gives in the same words, and a "show commands" mode shows the `zosh` line for any gesture. *Calm by default*: restraint is the ground; colour and light work because they are rare.

A *room* is the set of grants in which programs work: a project, the person's own things, an untrusted room for programs the person does not vouch for (later, agents). Zoraya already has the two halves: a job is an inescapable containment unit that ends everything in it (ADR-0003, ADR-0046, CP-07), and a launch is a table of entries the launcher built from what the person designated, in words `grants` prints (ADR-0153, ADR-0107, CP-05). The shell builds such a table per line (ADR-0153 rule 1), the panel per application (ADR-0168, ADR-0167 point 2). What is missing is a *named, persistent, shared* set of grants that both launchers use, and a display of it that the program cannot forge. EWS showed why the display must be the server's: "there is no label that the display server can apply on a window border that cannot be visually forged by a client" unless the server draws the border itself (`desktop/survey.md#spoofing-and-the-trusted-path`, `desktop/survey.md#eross-trusted-window-system`). CapDesk made the act of designation the grant and showed it (`desktop/survey.md#capdesk-and-e`); Polaris ran each application in its own restricted account (`desktop/survey.md#polaris`). A colour per security domain on a border the domain cannot draw is what Qubes OS does for its qubes `[outside evidence: Qubes OS's coloured window borders, drawn by the trusted GUI domain]`. Genode's subsystems are child trees with explicit routing of every resource (`alternatives-postmortem.md#genode`); Plan 9 assembles a namespace per process but shows it nowhere (`alternatives-postmortem.md#plan-9--inferno`).

Measured: nothing. Assumed: that three to six rooms is a working day, that a room's grants are directories and files (ADR-0153's kinds) and nothing else in stage 7, and that the compositor can draw a few words per frame at the rates of ADR-0160.

## Decision drivers
1. What a window can reach is visible on the window, drawn from the real record and never from the application (CP-24, GR-016's caveat that privileged GUI powers must be explicit; DM-079; `desktop/survey.md#spoofing-and-the-trusted-path`).
2. One object in the shell and the desktop: a room is the same set of grants whether entered by `room NAME` in `zosh` or by a launch from the panel, in ADR-0153's words, so that everything has its text (CP-23: configuration attributable; `shell/survey.md#capability-shells-and-grant-syntax`).
3. A room is a containment unit: its programs are in its job, and ending the room ends them (CP-07, ADR-0046).
4. A room can hold only what its creator held, and a program in a room only what the room and the person's gesture gave it (CP-01, CP-02, CP-05, DM-009).
5. The person's own work stays neutral; colour appears only where a boundary is, and an untrusted room is told apart by construction, not by a label a program could imitate.
6. No new right and no new kind of entry (ADR-0153).

## Considered options

### Option A: No rooms: per-launch grants only (the Unix baseline with sandboxes)
- **Description:** Every launch gets what its line or gesture designated (ADR-0153, ADR-0167), nothing is named or persistent, and the desktop shows nothing of it; a sandboxed application on Linux keeps an ambient home directory `[outside evidence: Flatpak's default filesystem access]`.
- **Evidence for:** Nothing to build; ADR-0153 already works this way at the shell.
- **Evidence against:** Driver 1 fails (nothing is shown); driver 2 fails (a project's grants are retyped per line, `+r ~/include` every time); no containment unit for a group of programs (driver 3); an untrusted program is indistinguishable (driver 5).
- **Cost:** None now; the retyping forever.
- **Precedent:** Every Unix desktop; Flatpak's portals grant per file with no grouping.

### Option B: Domains as separate sessions (Qubes-style)
- **Description:** A room is a separate session with its own filesystem view, broker and shell (ADR-0097, ADR-0104), and the compositor colours windows by session.
- **Evidence for:** The strongest isolation; proven in Qubes `[outside evidence]`; the compositor's colour is per connection, which it already knows.
- **Evidence against:** A session per room is a shell, a broker and a temporary service per room (ADR-0107), and a file shared between rooms needs a copy or a mount; a project room that is "my home directory plus `~/include`" does not fit; driver 2 fails since the shell's `+r` on a line is not a session.
- **Cost:** *(estimate)* Large: a session launcher and a cross-session file path.
- **Precedent:** Qubes OS; Polaris's accounts (`desktop/survey.md#polaris`), which cost a copy-and-sync mechanism.

### Option C: Rooms as named grant sets with a job, built by the launchers, shown by the compositor
- **Description:** A room is a record (name, `untrusted`, colour, grants in ADR-0153's words) in one file; the panel and `zosh` both read it and build launch tables from it as they build them today, in a sub-job per room; the compositor is told the room and the record with every client and draws them.
- **Evidence for:** Drivers 1 to 6: the mechanisms exist (ADR-0153's table and `narrow`, ADR-0046's jobs, ADR-0160's frames, ADR-0168's launch records), so a room is a few hundred lines in each launcher and in the compositor; the shell's `room` and the desktop's overview are two views of one file (CP-23).
- **Evidence against:** The room's job is per launcher unless the shell talks to the panel (open question); a room's grants are directories and files only; the file is a fourth one in `/config` beside ADR-0157's three.
- **Cost:** *(estimate)* The record parser (shared, `no_std`, 150 lines), `room` in `zosh` (300 lines), the panel's room launches and the overview (500 lines), the compositor's labels and grouping (400 lines).
- **Precedent:** CapDesk's launched caplets with their granted files (`desktop/survey.md#capdesk-and-e`); Genode's subsystems (`alternatives-postmortem.md#genode`).

### Option D: Rooms as namespaces (Plan 9's `bind` per process group)
- **Description:** A room is a namespace assembled at launch from mounts and binds; programs see paths, the display shows nothing.
- **Evidence for:** Plan 9's model is small and flexible (`alternatives-postmortem.md#plan-9--inferno`).
- **Evidence against:** Driver 1 fails by design; the namespace is ambient inside the group (CP-01's X-1 tradeoff is bounded by the table in ADR-0002, and this would widen it); nothing names a room.
- **Cost:** *(estimate)* Small, and it leaves the concept unbuilt.
- **Precedent:** Plan 9, rio.

## Recommendation

### Decision

Accepted with a change (architect, 2026-11-03): every window of an untrusted room carries, in addition to the measure `room.style` gives, an edge of `room.untrusted.edge` pixels (ADR-0161; two in the mockups) in `room.untrusted`, drawn by the compositor whether or not a field is drawn: with one room on screen and on a maximised window too. No trusted room colour produces it: the edge is drawn for the `untrusted` record only. Points 5 and 6 and INV-0172-10 state it. The recommendation below is otherwise as accepted.

Recommended: **Option C**. It is a recommendation, not a decision; the direction and its mockups (`docs/research/desktop/mockups/clear-*/`) are not accepted by this ADR.

1. **What a room is.** A record `NAME [--untrusted] [--colour N] GRANT...` on one line of `/config/rooms`, in ADR-0150's word syntax, where each `GRANT` is a literal `+r PATH` or `+w PATH` as ADR-0153 rule 3 writes them, with `~` as ADR-0150 rule 8 reads it. The file is read and written by the shared `no_std` settings crate of ADR-0157 (a second file of the same word syntax; defaults none; a bad line is reported once and skipped, ADR-0157 rule 5). The `home` room needs no line: it is the person's own, the session's table as `init` and the panel hold it (ADR-0097, ADR-0168's INV-0168-2), shown as `home` with no colour; the launch record of a window in it is still shown. The mockups' rooms are `project` (`+w ~/project`, `+r ~/include`) and `agent-1` (`--untrusted`, `+w ~/sandbox/agent-1`).
2. **Rooms and jobs.** A room is entered by a launcher, which creates a sub-job of its own job for the room (ADR-0003's `spawn` group, ADR-0046), and every program launched in the room runs in a sub-job of that job with its own job as ADR-0153 rule 1 gives it; the launcher keeps the room's job handle. Ending a room is `job_kill` on that job: everything in it ends (ADR-0046's `job_kill` closes the tree). The panel's room job and a shell's room job for the same room are two jobs with the same grants until the open question below is settled; the rooms overview shows the panel's, `jobs` the shell's. `untrusted` is a fact of the record the launcher applies (point 6), not a kernel policy bit: the kernel has no rooms.
3. **In `zosh`.** `room` is a builtin (it acts on the shell's own authority and state, ADR-0155 rule 8):
   - `room` lists the rooms with their grants, marks the current one and the untrusted ones;
   - `room NAME` enters: the prompt becomes `NAME {cwd}> ` (the setting `shell.prompt` gains `{room}`, empty outside a room), the current directory becomes the room's first `+w` directory `[assumption]`, and every following line runs in the room's job with the room's grants added to its table as if the person had written them before the command, under every other rule of ADR-0153 (resolution, paths from values, link objects, refused paths); `room --leave` returns to `home`;
   - `room NAME COMMAND...` runs one line in the room and stays where it was;
   - `room new NAME [--untrusted] GRANT...` creates the room; each `GRANT` is resolved against the shell's own table, so a room holds only what its creator held (driver 4, CP-02); `room add NAME GRANT`, `room drop NAME GRANT`, `room remove NAME` (refused while the room has programs unless `--kill`); every change is written atomically (ADR-0157 rule 4) and shown at once in the panel's overview;
   - `grants` shows a room's entries with `(room NAME)` after the right, as the mockup's terminal shows; `jobs` shows the room of each job.
   *Agreement and difference with ADR-0150 to ADR-0158, point by point.* (1) ADR-0150: `room`'s arguments are words of its syntax; `~` and quoting as there; nothing new in the grammar. (2) ADR-0153 rule 3 says a grant is "a literal `+r` or `+w` token before the command name, written in the source; the value of a variable or substitution is never a grant": a room's grants are literal `+r`/`+w` tokens too, written by the person in `/config/rooms` through `room new`, never from a value; what changes is *where* they are written, which is a stated difference, and `grants` shows them so that nothing is hidden. (3) ADR-0153 rule 1's "nothing else" holds: a line in a room receives the room's entries and its own designations, no root, no console. (4) ADR-0153 rule 4 (paths from values designate only inside the current directory or an explicit grant on the line): inside a room the room's grants count as grants on the line, so `rm $old` can reach `~/project` in the project room and not `/config`; stated. (5) ADR-0155 rule 8: one more builtin; its options and errors follow the shared crate. (6) ADR-0156: `room`'s description declares its operands; the `GRANT` words are not path operands and get no automatic designation. (7) ADR-0157: `/config/rooms` is a fourth file beside `settings`, `start.zosh` and `history`, in the same word syntax and crate; its rule 1 ("`/config` holds the configuration of whoever is given it") places rooms with the session's configuration, so a sandbox launcher that hands a narrower `/config` hands narrower rooms. (8) ADR-0152 and ADR-0151: a pipeline or a function inside a room runs in the room; a function body's own `+r`/`+w` add to the room's as they add to a line's.
4. **In the desktop.** The panel (ADR-0168) launches every application *into* a room: the current room, shown by the dock's filled chip, or the room chosen in the rooms overview; the launch record is the room's entries plus the four GUI entries of ADR-0167 point 2 (three for an untrusted room, point 6) plus what the gesture designated (an opened file, a drop). The panel tells the compositor the room with the client: `AddClient { room, untrusted, colour, entries[] }`, where each entry is the record's words (`+w ~/project`, `+w notes.txt`), a change to ADR-0168's `AddClient` under ADR-0052. Grants made later reach the compositor from two more trusted sources only: the chooser reports each `Chosen` as `Granted { tag, words }` on its manager-marked connection (ADR-0160's tag), and a drop is the compositor's own event (ADR-0170). So the compositor's list per window has three sources, the panel, the chooser and itself, and no client message touches it (INV-0172-1). The terminal's room is the room its shell was launched in; a shell that enters another room with `room NAME` tells its terminal with the `Title` message's sibling `Room { name }` (ADR-0168's out-of-band channel, a new ordinal), and the terminal passes it to the compositor through the panel, which checks the name against the record before the frame changes `[assumption: the shell is trusted for its own room; a lie would only mislabel its own window toward *less* authority, since the shell's table is unchanged]`.
5. **What the compositor draws**, all of it from its records, in ADR-0161's tokens: the room's colour on the frame, in the measure the direction chooses (`room.style`: a thin edge, the tinted title bar or the tinted window ground, ADR-0160); a badge with the room's name and the word `untrusted`; the window's grants as pills in ADR-0153's words, the room's folded into the badge when they do not fit beside the title; on hover of the pills a card in the trusted material with every entry, its right in `grants`' words, where it came from (`room project`, `operand FILE`) and the line that made the record (`room project edit notes.txt`); the switcher grouped by room with the rooms' grants on the group line (ADR-0160); the rooms overview (System+R) in the trusted material, one card per room with its windows, its grants, `Enter`, and a `New room` form whose text form is shown beside it; the dock's room chips (the rooms, the current one filled, `+` for a new one; a press enters the room; the bar carries no room badge, ADR-0168) and the dots under the dock's icons, one per room an application has windows in; and the *fields* on the wallpaper (`wallpaper = rooms`, the chosen Field variant). A field is not a region of the screen: it is drawn by the compositor around a room's windows, and only between rooms. Its rules: (a) a field is drawn only when two or more rooms have windows on screen (`home` counts); with one room there is no field and the title bar's tint carries the room (an untrusted window its edge too, point 6); (b) a room's field is the union of its windows' rectangles each grown by `field.padding` (ADR-0161), with corners of `radius.window` plus the padding, clipped to the work area between the bar and the dock's strip (the dock's height in its current state: in the show-commands mode, where the dock grows, the strip grows with it and the fields are recomputed, ADR-0168), `field.gap` from each and from the screen's edges, so that every tinted pixel is within the padding of a window of that room and none lies in the bar or the dock's strip; its header (the name, the word `untrusted`, the grants) sits on a small neutral ground at the top of the field, above its top-most window; (c) where two rooms' padded shapes come within `field.gap` of each other, each field is cut back by the other's shape grown by the gap: two fields never share a pixel and a neutral seam of at least the gap runs between them; (d) the field is recomputed from the windows' rectangles at every commit of a move or a resize, so a window dragged out of its field takes its field with it (the shape splits or joins; there is no edge to cross) and after any move, resize or maximise the fields equal those computed from the new rectangles; (e) a maximised window fills the work area and contributes no shape: its room shows on its title bar only, and the other rooms' fields are drawn under it as usual. The field is drawn into the wallpaper's copy when rooms or their windows change, one signed-distance pass over its bounding box, never per frame.
6. **Untrusted rooms.** A launch record in an untrusted room has no chooser channel: its programs receive only the room's entries, their operand from the launch, and drops; a drop or a paste (ADR-0170) into an untrusted window is delivered only after the person confirms it in a card of the trusted material that shows the grant's text; the word `untrusted` is on every frame, badge, group and card of the room, and its colour is `room.untrusted`, which no other room can be given; every window of the room carries an edge of `room.untrusted.edge` pixels (ADR-0161) in that colour inside its border, in addition to the measure `room.style` gives, drawn by the compositor whether or not a field is drawn, with one room on screen and on a maximised window too, and drawn for untrusted rooms only, so that no trusted room colour produces it (INV-0172-10); the refused-path hints of ADR-0153 rule 11 from its programs are shown by the panel in the window's hover card with the `+r` line that would allow them, which the person may run in `zosh` or do by a drop. A room is `untrusted` from its creation; it cannot be made trusted later (make a new room).
7. **Colours.** `room.1` to `room.4` and `room.untrusted` (ADR-0161, light and dark values each); a new trusted room takes the lowest free slot, recorded as `--colour N` in its line so that it keeps it; `home` has none; the fifth trusted room repeats a slot and is told apart by its badge (open question). The untrusted hue is reserved: no trusted room colour lies within `room.hue-distance` degrees of hue (ADR-0161, 60) of `room.untrusted`, in either set (INV-0161-6), so that orange means untrusted and nothing else. Colour is used for nothing else in the interface (the four rules): controls use the neutral `accent`, icons are monochrome, the frame's buttons are the only other coloured pixels, and only on the focused window. Text is never in a room's colour where the colour does not keep 4.5 to 1 on its ground (the badge's name, the chips' word `untrusted`, the overview's and the switcher's room names are in `fg.text` beside a coloured dot or band; the mockup README has the table).
8. **Everything has its text.** Every gesture the compositor and the panel own has a `zosh` line, and the "show commands" chord (System+?) draws it beside the element in the trusted material (ADR-0160): a launch `room NAME edit FILE` (or `edit FILE` in `home`), close `kill NAME`, minimise `bg NAME`, the chooser's and a drop's grant `+r PATH edit`, a setting `settings KEY VALUE`, the rooms overview `room`, a layout switch `settings gui.keyboard-layout ua`, a dock icon its launch line (`edit FILE`) and a chip its `room NAME`, in a tooltip over the hovered icon and under every icon and chip in the show-commands mode (ADR-0168). Focusing a window has no line: `fg` is the shell's foreground job (ADR-0155), not window focus, so the switcher carries none (open question). The table is one list in the compositor (INV-0172-5); the panel's tooltip of ADR-0168 becomes the hover card of point 5.

**Tensions with accepted ADRs.** *ADR-0153 rule 3*: a second place where literal grants are written (`/config/rooms`), stated in point 3 (2). *ADR-0157*: a fourth file in `/config`, same syntax and crate (point 3 (7)). *ADR-0155 rule 8*: `room` joins the builtins. *ADR-0097* and *ADR-0053*: nothing changes in who starts what; a room's job is a sub-job of a launcher, as every job is. *ADR-0046*: used as written. *ADR-0093*: `AddClient` carries the room and the entries, and the chooser's `Granted` is a manager-side message, new ordinals under ADR-0052. The proposed ADR-0160, ADR-0161, ADR-0167, ADR-0168 and ADR-0170 are changed by this ADR where they say so.

### Effect of the vision
Target 2 is what rooms are for: an agent is a program in an untrusted room, its window says so and shows what it holds, a supervisor sees every grant made to it as a line, and a room's end is one `job_kill`. Target 3 gains "projects" as a first-class thing people already think in. Networking: a `+net HOST` grant (CP-28) is one more word in a room's line. Threads: none.

### Deferred to stage 6
A POSIX program launched in a room gets a namespace table built by the launcher from the room's entries (ADR-0107, ADR-0153 rule 10); the toolchain set is added as today. The broker and the session stay one; rooms are tables and jobs, not sessions.

## Consequences
- **Positive.** The boundary is visible and forgery-proof; a project is typed once; an untrusted program is contained by construction and looks it; the shell and the desktop show one truth in one syntax.
- **Negative.** A fourth configuration file; the compositor keeps a record per window and draws text in frames; a room's job is per launcher for now; four colours.
- **Follow-up.** The rooms crate; `room`; the panel's overview and room launches; the compositor's labels, grouping and "show commands"; ADR-0170's confirmation for untrusted rooms.

## Invariants
- **INV-0172-1.** Every pixel that states a room or a grant (the frame's colour, badge and pills, the hover card, the drop and confirmation cards, the switcher's groups, the rooms overview, the dock's dots and chips, the fields, the show-commands tags) is composed from the compositor's own records, which change only through the manager channel (`AddClient`), the chooser's `Granted` and the compositor's own `Drop`; no client message changes them. *Check:* host test sending every client ordinal, including commits of buffers that imitate frames and cards, and asserting the records and the labelled pixels are unchanged; the GUI screendump test reads a window's badge and pills.
- **INV-0172-2.** A program launched in a room holds exactly the room's entries, the GUI entries of ADR-0167 point 2 (without the chooser channel in an untrusted room), and what the person's gesture designated, and no entry of another room. *Check:* host test enumerating the panel's launch records over rooms (INV-0168-1's harness); in-QEMU test that a program in an untrusted room cannot reach `~/project` and has no chooser channel to ask with.
- **INV-0172-3.** A drop or a paste into a window of an untrusted room delivers nothing until the person confirms in the compositor's own card; without input from the compositor, no `Drop` or `Paste` reaches such a window. *Check:* host test of the compositor's drop and paste paths against a fake input source that never confirms, with a deadline, and one that confirms.
- **INV-0172-4.** A `zosh` line in a room receives the room's entries and its own designations under ADR-0153's rules and nothing else; a room can hold only entries its creator's table covered; `grants` prints every room entry with `(room NAME)`. *Check:* host tests of the shell's table building over rooms, reusing INV-0153-2's and INV-0153-8's cases, and a test that `room new` with a path outside the creator's table is refused.
- **INV-0172-5.** Every gesture the compositor or the panel owns has a text form in one table, each text parses under ADR-0150's grammar, and the show-commands mode draws a tag for each gesture on screen. *Check:* host test that the table covers every input handler of the compositor and the panel (a lint over the handlers' names), a host test parsing each text with `zosh`'s parser, and the GUI test toggling the mode over QMP and reading the tags.
- **INV-0172-6.** A field is drawn only when two or more rooms have windows on screen; with the windows of one room, or none, no pixel of the wallpaper is tinted by a room's colour. *Check:* GUI screendump test opening windows in one room and then in a second, comparing the wallpaper's pixels against the computed wallpaper before and against the field's tint after.
- **INV-0172-7.** Every pixel tinted by a room's field is within `field.padding` of a rectangle of a window of that room, and no such pixel lies in the bar's strip or the dock's strip. *Check:* GUI screendump test that reads the tinted pixels of each colour and the windows' rectangles from the compositor and checks the distance and the strips.
- **INV-0172-8.** No pixel is tinted by two fields, and between a pixel of one field and a pixel of another there are at least `field.gap` pixels of neither, along any row or column. *Check:* GUI screendump test with windows of two rooms placed within the gap of each other, scanning rows and columns across the seam.
- **INV-0172-9.** After any move, resize or maximise, the fields equal those computed from the windows' new rectangles under points 5(a) to 5(e), and a maximised window contributes no shape. *Check:* GUI screendump test that drags a window out of its field, resizes one, maximises one, and compares each dump with a render of the computed fields; a host test of the field computation itself (the union, the clipping, the erosion) over random rectangles.
- **INV-0172-10.** Every window of an untrusted room carries an edge of `room.untrusted.edge` pixels in `room.untrusted` inside its border, whether or not a field is drawn (one room on screen and a maximised window included), and no window of a trusted room carries an edge in any room's colour: the edge is drawn for untrusted records only, so no trusted room colour produces it. *Check:* GUI screendump test that opens an untrusted window alone, then beside a trusted one, then maximised, and reads the pixels along each window's border at mid-height: `room.untrusted` to the edge's depth on every untrusted window, no room colour on a trusted one; the mockup tool's `untrusted_windows_carry_the_edge` test does the same over its `trust` scene, a one-window scene and a maximised one.

## Open questions
- Focusing a window has no `zosh` form: whether to give it one (a word for the compositor's focus, not the shell's `fg`), or to leave the switcher as the only gesture without text.
- One job per room across launchers needs a channel from the shell to the panel (or the panel to own every room job and the shell to ask it); until then two launchers in one room are two jobs.
- More than four trusted rooms: repeat colours, a fifth slot, or a limit.
- *(Check note, stage 7d, ADR-0001 rule 6.)* INV-0172-6 to -10's screendump checks run on the host against the real
  compositor's pixels (`zoraya-compositor`'s `tests_rooms.rs` and `tests_fields.rs`): the GUI runner cannot compute the
  wallpaper a field is compared with, and the GUI script reads the room's tinted title bar only. INV-0172-2's in-QEMU
  half and INV-0172-3 wait for untrusted rooms (refused until ADR-0056's quotas) and for ADR-0170's drops (7f).
  INV-0172-2 as a whole waits too: the only program a room launches in 7d is a terminal, whose shell holds the volume's
  root by ADR-0168 (INV-0168-2), so it holds more than the room's entries; `zoraya-panel`'s host test checks the
  record's handles and entries only, and a launch in an untrusted room is refused.
  INV-0172-4's host tests wait for the room's grants to move from `zosh` into `zoraya-shell`'s planner, where
  INV-0153-2's cases live; in 7d `zosh` adds them after the planner, and the GUI script shows `room`.
- Whether `home` should show the launch record's pills at all, or only coloured rooms should.
- Whether a room should remember its windows and restore them when entered (a session per room), which Option B would give.
- Whether a shell's `Room` message to its terminal is enough, or the shell should run a new terminal per room.

## Revisit triggers
- A program (an agent's supervisor) that needs to create rooms: a capability for `room new` over a channel.
- Networking: `+net` in a room's line.
- A measured cost of the compositor's labels at ADR-0160's frame rates.

## Architect's decision

Accepted 2026-11-03, with one change: the README's reserved two-pixel untrusted edge is adopted
(`room.untrusted.edge`, ADR-0161). The compositor draws it on every window of an untrusted room, also when no
field is drawn (one room on screen, a maximised window); no trusted room colour may produce it. INV-0172-10
states it, checkable by screendump. Decided by the architect; recorded by an agent at the architect's request.
