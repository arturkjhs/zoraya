# ADR-0160: Window management

- **Status:** accepted
- **Date:** 2026-11-03
- **Depends on:** ADR-0050, ADR-0052, ADR-0053, ADR-0093, ADR-0094, ADR-0097
- **Evidence:** DM-079, DM-082, DM-084, GR-016, CP-24, X-11, alternatives-postmortem.md#haiku--beos, alternatives-postmortem.md#plan-9--inferno, desktop/survey.md#server-side-and-client-side-decorations, desktop/survey.md#spoofing-and-the-trusted-path, desktop/survey.md#tiling-and-floating, desktop/survey.md#focus-and-stacking, desktop/survey.md#what-makes-a-desktop-coherent

## Context
Stage 5 gave Zoraya a compositor that places windows itself, draws a one-pixel frame, focuses on click and keeps F12 to cycle windows (ADR-0093, ADR-0094). A window cannot be moved, resized, minimised or closed by the person, has no title, and a client has exactly one surface. Stage 7 turns this into a desktop: several terminals and applications, each with windows the person arranges. The question is who draws what around a client's pixels, how the person moves, resizes, stacks, minimises and closes windows, how the keyboard reaches all of that, and how ADR-0094's focus rules extend.

The security question is the one the EROS window system answered (`desktop/survey.md#spoofing-and-the-trusted-path`): a client that draws its own frame can draw any frame, including another application's, and "there is no label that the display server can apply on a window border that cannot be visually forged by a client"; EWS has the server draw title bar and border in a fixed font and marks the focused window with a bright border while dimming the rest. The Linux desktops split on the same question (`desktop/survey.md#server-side-and-client-side-decorations`): GNOME requires client-side decoration for the sake of integration, KDE and Sway draw frames in the compositor, and the negotiation protocol lets the compositor "enforce a different mode" (DM-084 is the fragmentation this produced). Haiku, SerenityOS, macOS and Plan 9's rio draw the frame in the system (`desktop/survey.md#what-makes-a-desktop-coherent`, `alternatives-postmortem.md#haiku--beos`, `alternatives-postmortem.md#plan-9--inferno`).

What is measured: nothing on Zoraya beyond stage 5's figures (a full redraw at 759 frames per second under HVF, `docs/design.md`). What is assumed: that a frame of about 30 logical pixels and a few buttons cost the compositor nothing it cannot afford at those rates.

## Decision drivers
1. No client can spoof another's window, title or a system dialog (DM-079, DM-082, CP-24, `desktop/survey.md#spoofing-and-the-trusted-path`).
2. One look for every window, whatever toolkit or language drew its contents (`desktop/survey.md#what-makes-a-desktop-coherent`).
3. Only the person changes focus, position and stacking (ADR-0094 driver 1, GR-016).
4. The person can always reach any window and leave any window from the keyboard (ADR-0094 driver 2).
5. A hung client's window can still be moved, minimised and closed.
6. Small: a few hundred lines in the compositor, and no second protocol beside ADR-0093's.

## Considered options

### Option A: Client-managed windows and a separate window manager (X11, the older Linux baseline)
- **Description:** The display server knows only rectangles; any client, by convention the window manager, reparents windows into frames it draws, and clients ask for positions and focus through properties and events.
- **Evidence for:** Any policy can be implemented by swapping the window manager; decorations and tiling are ordinary programs.
- **Evidence against:** DM-079 and DM-082: the manager is a client like any other, so any client can do what it does, which includes reading and moving every window. X-11 records that the rich core froze policy anyway.
- **Cost:** *(estimate)* A conventions document the size of ICCCM, and the security model cannot be retrofitted.
- **Precedent:** X11 with every window manager ever written.

### Option B: Client-drawn frames with a decoration mode negotiated (Wayland with GTK's header bars, the current Linux baseline)
- **Description:** A client draws its own frame inside its surface, asks the compositor to move or resize it with the serial of a button press, and may ask for server-side decoration through a protocol the compositor may refuse (`desktop/survey.md#server-side-and-client-side-decorations`).
- **Evidence for:** The frame can hold the application's own controls, GNOME's argument for header bars; nothing in the compositor draws text, so it needs no font.
- **Evidence against:** A client can draw any frame, so the frame proves nothing (driver 1); two toolkits give two looks (driver 2, DM-084); a hung client's frame is dead (driver 5). Move and resize requests are still the client's to make; `set_minimized` has no readback (`desktop/survey.md#focus-and-stacking`).
- **Cost:** *(estimate)* Smallest compositor; the cost moves into every toolkit, which the decoration protocol's author calls "a lot of work".
- **Precedent:** GNOME Shell and Weston.

### Option C: Compositor-drawn frames, with the person's gestures as the only way to arrange windows
- **Description:** The compositor draws every frame: title bar with the title in its own font, close and minimise buttons, a border whose colour marks focus. The person moves a window by dragging its title bar, resizes it by dragging an edge, minimises and closes it with the buttons or reserved keys, raises it by clicking. The client supplies a title string and receives a size; it cannot position, raise, resize or decorate. This is what EWS did, and what Haiku, SerenityOS and KWin do (`desktop/survey.md#spoofing-and-the-trusted-path`, `desktop/survey.md#server-side-and-client-side-decorations`, `alternatives-postmortem.md#haiku--beos`).
- **Evidence for:** Drivers 1 to 5. The compositor already owns placement and focus (ADR-0093, ADR-0094), so this extends what exists. A frame drawn outside the client's pixels is the one label a client cannot forge, and a bright focus border plus dimmed others is EWS's answer to a client dimming itself.
- **Evidence against:** The compositor needs a text renderer for titles (ADR-0162's crate, or ADR-0095's bitmap font) and one more look to maintain; an application cannot put controls in its title bar. A client can still draw a fake frame *inside* its body; only the real frame's colour, its position outside the body and the trusted window tint of ADR-0167 tell them apart, as in EWS.
- **Cost:** *(estimate)* 600 lines in `zoraya-compositor` (frames, hit testing, drag states, the switcher), 100 lines of protocol, one font.
- **Precedent:** EWS (research), KWin, Haiku's app_server, SerenityOS's WindowServer, macOS's WindowServer (all in production except EWS).

### Option D: Borders only and a mouse menu (Plan 9's rio)
- **Description:** No title bars: a border whose colour marks the current window, and a button-3 menu with New, Resize, Move, Delete and Hide; windows are terminals (`alternatives-postmortem.md#plan-9--inferno`, `desktop/survey.md#focus-and-stacking`).
- **Evidence for:** The smallest possible window manager; no text in the compositor; the same spoofing protection as C for the border.
- **Evidence against:** No titles, so two terminals look alike; a three-button mouse and sweeping gestures that a person on a Mac trackpad does not have; nothing for the keyboard (ADR-0094 driver 2).
- **Cost:** *(estimate)* Smaller than C by the title bar and buttons.
- **Precedent:** Plan 9, 9front.

### Option E: Tiling (i3, sway)
- **Description:** The compositor arranges windows in a tree of splits, stacks and tabs; the keyboard moves focus and windows between slots; floating is the exception (`desktop/survey.md#tiling-and-floating`).
- **Evidence for:** No overlapping, so no spoofing by covering; every window is reachable from the keyboard by construction.
- **Evidence against:** Not the macOS or FreeBSD sense of unsurprising the architect asked for: a dialog or a chooser (ADR-0167) is a floating window; most people expect to drag windows. Haiku's Stack & Tile shows tiling can be added to floating later by a drag with a modifier.
- **Cost:** *(estimate)* As C plus a layout tree; it can be added on top of C later as a mode.
- **Precedent:** i3, sway, Haiku's Stack & Tile.

## Recommendation
Recommended: **Option C**, with Option E's tiling left as a later mode. It is a recommendation, not a decision.

- **Frame.** Every toplevel window has a frame drawn by the compositor from ADR-0161's tokens: a title bar of `frame.height` logical pixels with the title text, a close button at the left and a minimise button beside it, a border of `frame.border` pixels, and a drop shadow where the direction has one. The focused window's title bar is `bg.frame.focused`; every other window's title bar is `bg.frame`, and its body is drawn as committed (not dimmed: dimming client pixels would change what a screendump test compares; the frame is the signal). How the focused window is told from the others is the direction's choice, in tokens (ADR-0161): with `frame.border.focused = accent` the focused border is the accent colour and the others' the neutral strong border (the first mist, quiet and night); with `none` every border is the neutral `border` and the focus is shown by the shadow (`shadow.window.alpha` for the focused window against `shadow.window.unfocused.alpha`, in `shadow.window.layers` layers) and by the buttons, coloured on the focused window and `fg.text.disabled` grey on the others (`frame.buttons = glyphs`, the second mist); `frame.separator` says whether a line separates the title bar from the body. The accent colour is for controls; a direction with `none` never puts it on a frame. Under the "Clear boundaries" concept (ADR-0172, the `clear-*` mockups) the frame also carries the window's *room*, from the compositor's own record and never from the client: the room's colour in the measure `room.style` gives (`edge`: a `room.edge`-pixel border in the colour; `band`: the title bar tinted by it; `ground`: the window's ground tinted by it, the title bar more), a badge with the room's name and the word `untrusted`, and the window's grants as pills in ADR-0153's words at the right of the title bar (the room's grants only when they fit beside the title, since the badge names the room; all of them in the hover card ADR-0172 point 5 describes); a window of the `home` room has no colour. Saturated colour is used for nothing else on a frame: the buttons' colours on the focused window are the one exception, and `accent` is a neutral tone. The title text is the client's (`SetTitle`), so it is not part of the unforgeable label: what no client can forge is the frame's geometry outside its body, the two frame colours, the system tint below, and the panel's launch record (ADR-0168). *System windows* are the chooser's (ADR-0167) and any later dialog the session itself shows; they carry `bg.frame.system`, which no client can request; the settings program is an ordinary application. A third kind, the *bar*, exists only for the panel (ADR-0168): frameless, in a strip of the display the compositor reserves (windows are placed and tiled inside the rest), never covered, moved or closed, marked by the manager, not requestable by a client; "no always on top" below is about clients. The panel may hold two bars (`desktop.layout = dock`, ADR-0168: a thin bar at the top and a strip at the bottom holding the floating dock); the compositor draws the *glass* under a bar itself, the pre-blurred wallpaper of ADR-0161 tinted with `bg.panel` at `panel.alpha` and rounded with `dock.radius` where the bar asks for it, and composes the bar's buffer over it with that buffer's alpha channel, which only a bar-kind buffer has `[assumption: the fourth byte of ADR-0093's pixel format, ignored for every other kind]`. A fourth kind, the *sheet*, exists only for the chooser (ADR-0167, `chooser.style = sheet`): a system window the compositor attaches under the title bar of the window that asked, centred on it, moved and stacked with it and above it, with no buttons of its own; the compositor paints its system strip (the tint, the emblem and the heading) and the bar's trusted mark while it is open. The chooser creates it with `CreateSheet { tag }` on its manager-marked connection, where `tag` is an opaque number the panel issued when it created the application's chooser channel and registered the client (`AddClient`, ADR-0168), so that the compositor finds the owner's focused toplevel without any client naming another client (ADR-0093); the owner gets no input while its sheet is open. The title is drawn with ADR-0162's renderer in the UI font at the body size; until that crate exists, ADR-0095's bitmap font.
- **Client messages** (`zoraya-proto-gui`, new ordinals, ADR-0052). `CreateToplevel { width, height }` with one memory object replaces `Create` for windows and may be sent more than once per connection: a client can have several windows; `Create` stays for one surface per connection until every client has moved. `SetTitle { text }`, UTF-8, at most 256 bytes, validated. `CreatePopup { parent, x, y, width, height }` for menus and completion lists: a popup has no frame, is placed relative to its parent's body, is clipped to the display, is raised with its parent and closed when the person clicks outside it; a client may have at most 4 open. `Close` is a request from the client to close its own window. A client never sends a position, a size for an existing window or a stacking order.
- **Compositor events.** `Configure { window, width, height, scale, appearance }` is the one message that tells a client how to draw: the logical size the compositor gives it, the scale (ADR-0164) and the appearance record `{ theme, motion }` from the settings (ADR-0169), at creation, after every resize and whenever any of them changes; the client draws at that size and commits; the compositor shows the old pixels until the first commit at the new size, so a resize never shows garbage. ADR-0164 and ADR-0169 refer to this definition and add no field of their own. `CloseRequested { window }` when the person presses the close button or the reserved chord; the client may ask to save and then send `Close`. `Minimised { window, hidden }`. Focus and input events are per window, extending ADR-0094's `Focus`.
- **Placement and stacking.** A new window is placed as ADR-0093 says, cascaded, inside the display minus the panel (ADR-0168). Raise on button press in a window or its frame (ADR-0094), and when a window is restored from the panel. A popup is above its parent. There is no "always on top" and no client-requested raise.
- **Moving and resizing** are drags the compositor interprets: a press on the title bar moves, a press within `frame.grip` pixels of an edge or corner resizes, both with the pointer captured by the compositor until release, and the client sees nothing but the final `Configure`. A window may be dragged partly off the display but its title bar stays reachable. Minimum size 1 logical pixel of body; a client that wants more draws its content clipped.
- **Minimise and close.** The minimise button hides the window; the panel (ADR-0168) lists it and restores it; the switcher also shows hidden windows. The close button sends `CloseRequested`; if the client does not close within 5 s `[assumption]` the compositor offers "close anyway" in the frame, which ends the connection. Closing the last window of a client does not end the client; the client decides.
- **Keyboard.** One reserved modifier, the *system key* (Super, `KEY_LEFTMETA` or `KEY_RIGHTMETA`; the Command keys on a Mac keyboard under QEMU, where `tools/run-qemu.sh` now opens the window with `-display cocoa,left-command-key=on`: measured on 2026-11-03 with QEMU 11.1.2, both Command keys reach the guest as Meta and Command with a letter arrives as Meta plus the letter, by default and with the option, which pins it; with `left-command-key=off` the left Command key is swallowed and letters arrive bare; in no run did Cmd-Q, Cmd-W, Cmd-H or Cmd-M act on the host, and Cmd-Tab stayed the system's in every run; `docs/research/desktop/command-key.md`), replaces F12: every chord with it is the compositor's and never reaches a client, and one chord without it is reserved too, Alt+Tab, because macOS takes Cmd-Tab and Cmd-` before QEMU sees them while Option+Tab arrives whole (measured, `docs/research/desktop/command-key.md`). Chords in stage 7: Alt+Tab opens the switcher overlay (next window; with Shift previous; release of Alt chooses; the Option key on a Mac keyboard), System+W close, System+M minimise, System+Space switches the keyboard layout (ADR-0163), System+Left and System+Right tile the focused window to the left or right half (the first step of Option E), System+Enter opens a new terminal (ADR-0168), System+R opens the rooms overview and System+? the show-commands mode (ADR-0172). F12 stays as a backup for Alt+Tab, kept as long as the Mac is the one host, so that `make test-gui` can press one key over QMP and a keyboard without a usable Alt still switches. A client gets every other key as ADR-0094 says.
- **The switcher overlay** is drawn by the compositor above everything: one row per window with its title and a thumbnail of its copy, the chosen one highlighted; it is the "window-switching overlay" of the mockups. The thumbnail is the window's own pixels, which the compositor already holds (ADR-0093's copy), shrunk by averaging the source pixels under each thumbnail pixel (a box filter, as the mockup tool's `image_scaled` does), so it is true and costs one pass over the window's buffer when the switcher opens or the window commits while it is open. Under ADR-0172 the rows are grouped by room, with the room's badge and grants on the group line.
- **The trusted material.** The glass of the second mist (the blurred wallpaper under the bar, the dock and the switcher) becomes, under ADR-0172's rule "glow means trust", the one material the compositor alone draws: a blur of what is under the surface, tinted with `bg.overlay` at `panel.alpha`, a band of light from the top edge and a bright rim (`glow.alpha`), and a halo around it (`glow.halo`, `glow.blur`), all in ADR-0161's tokens, which also give the technique and its measured cost. It is used for the bar, the dock, the switcher, the rooms overview, the chooser's sheet (ADR-0167), the hover card of a window's grants, the drop and confirmation cards (ADR-0170, ADR-0172) and the show-commands tags, and for nothing a client asks for: a client's buffer is composed as committed, with no blur, light or halo, so the material cannot be imitated from inside a window (INV-0160-7 and INV-0167-4 cover the bar, the sheet and the tint; INV-0172-1 the cards). For a surface over the wallpaper only (the bar, the dock), the blur is the pre-blurred copy of ADR-0161; for one over windows (the switcher, the overview, a card), the compositor blurs the region under it when it opens and again when something under it commits, never per frame while it is still.
- **Show commands.** System+? toggles a mode in which the compositor draws, beside every element it or the panel owns, a tag in the trusted material with the `zosh` line the gesture means (ADR-0172 point 8 lists them); the bar says the mode is on and how to leave it. Nothing else changes while the mode is on; a client is not told. The `Focus` rules of ADR-0094 extend: focus changes by a button press on a window or its frame, by the switcher, by a restore from the panel, by the focused window's close or minimise (focus goes to the next window in stacking order), or by the focused client's end. A popup takes keyboard focus while open and returns it on close.
- **Hung clients.** Everything above is the compositor's, so a hung client's window moves, hides and closes. Its pixels stay the last commit.

**Tensions with accepted ADRs.** This ADR partly supersedes two accepted ADRs, in the sense of ADR-0001 rule 1, and says what changes. *ADR-0093*: "One per connection" (surfaces), "a one-pixel frame ... and no other decoration", "A client cannot position, raise or resize its window" (resizing now happens, driven by the person) and the one manager channel (a second manager endpoint for the panel, ADR-0168) change; the client messages of ADR-0093 stay and new ones are new ordinals (ADR-0052). *ADR-0094*: F12 becomes the system key's chords plus Alt+Tab, with F12 kept as the backup (INV-0094-1's "reserved key" becomes "reserved key or chord"); the rule "Keyboard focus ... changes only when the person presses a pointer button over a surface, presses the reserved key, or the focused surface's client goes" and INV-0094-2 gain four more causes, all the person's or the focused client's own: the switcher, a restore from the panel, the close or minimise of the focused window, and a popup of the focused client while it is open; INV-0160-2 restates the rule. *ADR-0096*'s terminal grid changes size on `Configure`, which it already supports through `Size`; the `Title` message ADR-0168 adds to the terminal protocol is a new ordinal of ADR-0096's protocol, out of band.

### Effect of the vision
For target 2 (untrusted code): every window of an agent is labelled by a frame the agent cannot draw, which is the EWS argument and the reason for Option C over B; a supervisor wanting a visible "this window belongs to agent X" label gets it from the frame's title and tint. Target 3 (a general desktop) wants tiling, workspaces and multiple displays, each a mode or a table in the compositor, at the cost of Option E's tree later. Networking: a remote window is a relayed client (ADR-0093), and its frame is still local. Threads: none.

### Deferred to stage 6
Nothing here depends on POSIX. A POSIX program's terminal is a window of the terminal client (ADR-0105), not a window of its own.

## Consequences
- **Positive.** One look; titles and dialogs a client cannot forge; a person can always move, hide and close a window; the keyboard reaches everything through one modifier.
- **Negative.** The compositor renders text and grows by frames, drags and the switcher; applications cannot put controls in the title bar; F12 is a transitional alias; a client that draws a fake frame inside its body is told apart only by position and colour, as in every system that draws frames.
- **Follow-up.** Tiling as a mode (Option E); workspaces; a clipboard and drag-and-drop ADR (EWS's traceable paste, `desktop/survey.md#spoofing-and-the-trusted-path`), number reserved: ADR-0170.

## Invariants
- **INV-0160-1.** No pixel of a window's frame depends on the client's buffer: the frame region of every window is composed only from the compositor's own drawing, whatever the client commits. *Check:* host test composing the same scene twice with two client buffers (all white, all black) and asserting the frame regions are identical and differ from both buffers; and the GUI screendump test checking the frame of the terminal window pixel by pixel.
- **INV-0160-2.** The client protocol has no message that sets a window's position, stacking order, decoration or focus; focus changes only by the person's actions (a button press on a window or its frame, the switcher, a restore from the panel, the close or minimise buttons and chords) or by the focused client's own `Close` of its focused window, a popup it opens while it has focus, or its end. *Check:* host test over every ordinal of `zoraya-proto-gui` sent by an unfocused client asserting that neither the focus nor any window's position or order changes, and over the listed causes asserting each changes exactly what is stated; this replaces INV-0094-2's test.
- **INV-0160-3.** A chord with the system key (System+R and System+? included), Alt+Tab and F12 never reach a client, and every window, hidden ones included, is reachable through the switcher from the keyboard alone. *Check:* host test of the routing with a client watching for the chords, and a host test that cycles the switcher over n windows with m hidden and sees each focused once; the GUI test presses Alt+Tab and F12.
- **INV-0160-4.** A client that stops reading loses nothing but its own events, and its window can still be moved, minimised and closed by the person. *Check:* host test with a fake channel that refuses writes for one client, driving a move, a minimise and a close through the compositor's input path.
- **INV-0160-5.** The size a client draws at is always a size the compositor sent in `Configure`, and the compositor shows a client's pixels at a new size only after the client commits at that size. *Check:* host test resizing a window and committing late, asserting the old pixels until the commit.
- **INV-0160-6.** A title is UTF-8 of at most 256 bytes and is drawn only inside the title bar, clipped, whatever its content. *Check:* host test with hostile titles (long, control characters, right-to-left marks, combining marks) against the title bar's rectangle.
- **INV-0160-7.** The bar kind, the sheet kind and the system tint are set only through the manager channel: no client ordinal creates a bar or a sheet, marks a window as a system window, paints into a bar's glass or its trusted-mark region, or raises a window above the bar. *Check:* host test sending every client ordinal and asserting the kinds, the bar's pixels and the stacking against the bar are unchanged.

## Open questions
- Whether `frame.height` of 28 logical pixels (36 in the second mist) and the button sizes suit a person: decided by the mockups.
- Whether a bar's translucency should be the compositor's glass under an alpha buffer (above) or a bar that draws its own pixels over a blurred copy the compositor hands it; the first keeps the blurred copy in one place.
- Whether the hover card and the show-commands tags need a kind of their own in the compositor, or are overlays like the switcher: the mockups draw them as overlays.
- Whether to dim unfocused windows as EWS does: it costs the screendump tests their exactness and is left out; the mockups show the undimmed form.
- Settled by measurement (`docs/research/desktop/command-key.md`): QEMU 11.1.2 sends `KEY_LEFTMETA` and `KEY_RIGHTMETA` for the Command keys by default and with `left-command-key=on`, which `tools/run-qemu.sh` now sets on macOS to pin it. The Option key produced no Meta; its code was not measured.
- Settled by measurement: Cmd-Tab and Cmd-` never reach the guest on macOS (macOS takes both before QEMU), Option+Tab arrives as Alt plus Tab, so the switcher is Alt+Tab with F12 as the backup; INV-0160-3's GUI test presses Alt+Tab and F12 over QMP.
- The 5 s "close anyway" delay is an assumption.

## Revisit triggers
- A client that needs a grab (a toolkit menu that must capture the pointer outside its windows): popups cover menus; if not, a grab capability.
- A measured frame rate where frame drawing or the switcher's thumbnails dominate compose time.
- A request for tiling or workspaces from the architect.

## Architect's decision

Accepted 2026-11-03. Decided by the architect; recorded by an agent at the architect's request.
